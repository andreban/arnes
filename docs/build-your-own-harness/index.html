A 10-chapter walk-through

Build Your Own Coding Harness

By the end of this book you will have built, from scratch, a working command-line coding agent: an interactive program that talks to a language model, runs tools on your behalf, edits your code, and survives long sessions. Each chapter ends with a working program that does something the previous one could not.

How to read this book

The text is language-agnostic. Every concept is described in plain prose, illustrated with diagrams, and made concrete with a small TypeScript snippet you can read like pseudo-code. Use TypeScript, Python, Go, Rust, OCaml — whichever is yours. The shape of the system is the same.

The harness is a small program sitting between the user and the outside world. That is all an agent is.

Snippets are short and meant to illustrate — not to be copy-pasted into a production codebase. They use Node 22+ / Bun built-ins (fetch, node:fs, process.stdin) and assume an LLM that exposes the now-standard streaming and tool-use API shape. The exact provider does not matter; we treat the model as a black box with a known contract.

In pi's code

Throughout the book, these callouts point you to where the real pi agent does the same thing in production. The callouts are optional — the book stands on its own — but if you want to see a battle-tested version of what you just built, that is where to look.

What this book deliberately does not cover

  • Picking a specific LLM provider. The book treats the model as a contract. Wiring up a particular vendor's SDK is mechanical and well-documented by them.
  • Multi-provider abstraction. Once your harness works against one provider, the abstraction layer is a small refactor. Pi's packages/ai is one good model to study afterwards.
  • Production hardening. Rate limits, retries, structured logging, telemetry — all important, all out of scope. The book aims for understanding, not operations.
  • Security boundaries. A coding agent that runs bash on the user's machine is a dangerous tool. We will discuss the shape of the problem in Chapter 4 but not solve it.

Prerequisites

  • Comfort with one mainstream programming language.
  • An LLM endpoint with streaming and tool-use support. Most modern providers fit.
  • A POSIX-ish terminal. Chapter 7 has some Windows-specific notes.
