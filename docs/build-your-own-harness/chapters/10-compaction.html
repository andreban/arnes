Compaction

A long enough session will eventually hit the model's context window. The naive failure is a hard wall: requests start being rejected, the user has to start over, the work is gone. Compaction is the technique that turns the wall into a smooth slope: when you are running out of room, ask the model to summarize what just happened, replace the history with the summary, and keep going.

The shape of the wall

Every model has a context window measured in tokens: 200,000 is common at the time of writing, larger windows exist, and the long tail of older or cheaper models sits well below. Each request sends:

  • The system prompt.
  • Every prior message in the conversation.
  • The tool declarations.

Tool results — long file contents, bash output — balloon the history much faster than the conversational text would suggest. Twenty turns of "agent reads a file, edits it, runs tests" can comfortably reach 100,000 tokens. At some threshold, you either compact or you fail.

A long tail of tool results becomes one compact summary, then a few preserved recent messages so the agent can continue smoothly.

The mechanism, end to end

Compaction is three steps. None of them require new infrastructure; you reuse the same LLM client and event system you already have.

  1. Decide it is time. Approximate the current token count. If it exceeds some threshold (say 75% of the model's window), trigger. The threshold should be high enough that you do not compact unnecessarily and low enough that the next user message cannot push you over.
  2. Ask the model to summarize itself. Send the full history plus a structured prompt asking for a summary of what has happened. The response is your replacement.
  3. Swap the history. Replace the long history with: the summary (as a single user-role message labeled clearly), the last K messages (to preserve recent context), and keep going.

Counting tokens (approximately)

Exact token counting requires the model's tokenizer. Approximating — 1 token per ~4 characters of English text, or per ~0.75 words — is good enough for a threshold check. The threshold is a soft trigger, not a hard contract; being off by 20% on the count is fine. 

function approxTokens(messages: Message[]): number {
  let chars = 0;
  for (const m of messages) {
    for (const block of m.content) {
      if (block.type === "text") chars += block.text.length;
      else if (block.type === "tool_result") chars += block.content.length;
      else chars += JSON.stringify(block).length;
    }
  }
  return Math.ceil(chars / 4);
}

const CONTEXT_LIMIT = 200_000;
const TRIGGER_AT    = 0.75;  // compact when 75% full

function shouldCompact(messages: Message[]): boolean {
  return approxTokens(messages) > CONTEXT_LIMIT * TRIGGER_AT;
}

If you have access to the model's actual tokenizer or to the usage field in API responses, use it instead. The approximation is for when you do not.

The summary prompt

The quality of compaction is the quality of the summary prompt. Vague prompts produce vague summaries that leave the agent confused about what it was doing. A good prompt asks for structured output: 

const SUMMARY_PROMPT = `
You are about to be replaced by a fresh instance of yourself, which will
inherit a summary of what we have discussed instead of the full transcript.

Produce that summary now. Include, in this order:

1. THE GOAL: What is the user trying to accomplish? One short paragraph.
2. KEY DECISIONS: List concrete decisions made so far (chosen approach,
   rejected alternatives, important constraints). Bullet list.
3. STATE OF THE WORLD: What files have been read, edited, or created? What
   commands have been run? Anything else the new instance needs to know
   about the state of the project. Bullet list with paths.
4. OPEN QUESTIONS: Anything that was raised and not resolved. Bullet list.
5. NEXT STEP: What is the very next action the new instance should take?
   One sentence.

Be specific. The new instance has none of the original context; assume it
will only know what you write here.
`.trim();

Run a fresh model call with the same history plus this as a final user message. The reply is the summary. 

async function compact(messages: Message[]): Promise<Message[]> {
  const summarized = await complete([
    ...messages,
    { role: "user", content: [{ type: "text", text: SUMMARY_PROMPT }] },
  ]);

  const summary = extractText(summarized);  // pull the assistant text out

  const KEEP_RECENT = 4;
  const tail = messages.slice(-KEEP_RECENT);

  return [
    {
      role: "user",
      content: [{ type: "text", text:
        "[compaction summary — the previous transcript was compacted to fit " +
        "the context window. The summary below stands in for it.]\n\n" + summary
      }],
    },
    ...tail,
  ];
}

Three details to notice:

  • The summary lives in a user-role message, not the system prompt. System prompts are for instructions, not facts. A clearly-labeled user message reads to the model as "context provided to me at the start of this conversation," which is exactly the right framing.
  • Keep the recent tail. Compacting all the way to the summary loses fidelity. The last few messages let the agent pick up mid-thought. A small K (say 4–8) is plenty.
  • The label matters. The bracketed prefix tells the model what it is reading. Without it, the model sometimes treats the summary as a continuation of the conversation rather than a replacement for it.

The user experience

Compaction is not invisible. The user will notice that you summarized; treat that as a feature, not a bug. Surface it:

  • Announce it. Print a one-line notice in the transcript: [compacted: 28 messages → 5, freed ~170k tokens]. Now the user knows why their session feels slightly different.
  • Persist the original. Your JSONL session log (Chapter 6) should keep every original message and record the compaction as its own row. The on-disk history is the truth; in-memory is a working set. --continue from a compacted session resumes with the in-memory state (summary + tail), not the raw log.
  • Make it manual too. A /compact command lets the user force compaction before the threshold — useful when starting a new sub-task and wanting a clean slate without losing the session.

Things that will go wrong

Even with a good summary prompt, compaction has failure modes worth anticipating:

  • The model loses thread mid-tool-call. If you compact in the middle of a turn where the assistant has emitted tool calls but you have not yet returned the results, the protocol breaks. Only compact between turns — after a clean end_turn or before the user's next message.
  • The summary becomes load-bearing for state. If the summary says "we decided to use snake_case" but does not say which file, the new instance forgets. Including a "files touched with their current relevant state" section in the prompt mostly fixes this.
  • Repeated compaction degrades quality. A session that compacts three times is summarizing summaries of summaries; loss compounds. For sessions long enough to need this, suggest the user start fresh and pass a brief recap manually.
In pi's code

Pi's compaction lives in packages/agent/src/harness/compaction.ts. The trigger threshold, the summary prompt, and the tail size are all configurable. Pi also implements branch summaries: when you fork a session (Chapter 6's tree model), the branch point gets a short summary so you can return to it later without paying the original context cost. The user-facing /compact command lives in the coding-agent package; it ties into the same primitive.

You are done

That is the whole stack. From "send some messages to an LLM" in Chapter 1 to "a multi-day coding session that survives context limits, persists across restarts, and can be extended without touching your codebase" in Chapter 10. Each layer was small. Together they are a real coding harness.

The shape of the thing is now permanent in your head:

  • A loop with two states (talk, run).
  • A vocabulary of typed content blocks (text, tool_use, tool_result).
  • A composed system prompt assembled from slots.
  • An event bus that everything optional subscribes to.
  • An append-only log as the source of truth.
  • A small host API for extensions, and a markdown-on-disk format for skills.

Most languages will give you a different idiom for each of those, but the decomposition is the same. Go build it.

What you have now

A complete coding harness. It edits files, runs commands, holds a session across days, presents a live TUI, accepts user-written extensions and skills, and gracefully outlives the model's context window. You can use it daily. You can give it to others. You can extend it without rewriting it. The next interesting thing you will build with it has nothing to do with this book.
