Chapter 1 · Part I

Streaming LLM client

Before tools, before sessions, before any of the things that make a coding agent useful, you need the one piece without which nothing else works: a small program that can talk to a language model and print its reply as it arrives.

The contract

Every modern LLM provider exposes roughly the same shape, and that shape is what we are going to lean on. You can think of the model as a black box with two interfaces:

Request

A conversation: an ordered list of messages, each tagged with a role (user, assistant, sometimes system), each carrying some content (text, for now).

Response

A stream of events describing the model's reply as it is generated: "a message started", "here is a chunk of text", "the message is done".

That is it. Provider differences (header names, exact JSON shapes, where the API key goes) are surface details. The shape is universal.

One request, many response events. The harness prints each text chunk as it arrives.

Messages

A message is a tuple of role and content. The content is a list of blocks — right now just text blocks, but the same list will hold tool calls in Chapter 2 and images, tool results, and thinking in later chapters. Plan for it now; you will thank yourself. 

type Role = "user" | "assistant" | "system";

type ContentBlock =
  | { type: "text"; text: string };

interface Message {
  role: Role;
  content: ContentBlock[];
}

Why a list of blocks instead of a single string? Because future content — tool calls, images, the model's "thinking" — will not fit in a string. A list of typed blocks scales; a string does not.

The stream

Most providers stream responses as Server-Sent Events (SSE) over HTTP. Each event is a JSON object terminated by a blank line. You parse the line, decide what kind of event it is, and act on it.

The events you care about right now:

EventWhat you do with it
message_startStart a fresh assistant message buffer.
text_deltaAppend the chunk to the buffer; print it to stdout.
message_stopThe reply is complete; push the buffered message onto the history.

The exact event names vary by provider. The shape does not.

Putting it together

Below is the entire client — in TypeScript, but in any modern language it is the same thirty-ish lines. 

async function* streamReply(messages: Message[]) {
  const res = await fetch(LLM_URL, {
    method: "POST",
    headers: { authorization: `Bearer ${API_KEY}`, "content-type": "application/json" },
    body: JSON.stringify({ model: MODEL, stream: true, messages }),
  });

  // SSE parsing: split the byte stream on blank lines, parse JSON, yield.
  const decoder = new TextDecoder();
  let buf = "";
  for await (const chunk of res.body!) {
    buf += decoder.decode(chunk);
    let i;
    while ((i = buf.indexOf("\n\n")) !== -1) {
      const frame = buf.slice(0, i);
      buf = buf.slice(i + 2);
      const line = frame.split("\n").find(l => l.startsWith("data: "));
      if (!line) continue;
      const payload = line.slice(6);
      if (payload === "[DONE]") return;
      yield JSON.parse(payload);
    }
  }
}

Now wrap it in a REPL. Read a line, append it as a user message, stream the reply while printing chunks, push the completed assistant message back onto the history. Repeat. 

const messages: Message[] = [];

const rl = readline.createInterface({ input: process.stdin, output: process.stdout });
for await (const line of rl) {
  messages.push({ role: "user", content: [{ type: "text", text: line }] });

  let buf = "";
  for await (const event of streamReply(messages)) {
    if (event.type === "text_delta") {
      process.stdout.write(event.text);
      buf += event.text;
    }
  }
  process.stdout.write("\n");

  messages.push({ role: "assistant", content: [{ type: "text", text: buf }] });
}

Run it. Type a question. Watch tokens stream in. Reply to its reply. You have a chat application. The hard part of every subsequent chapter is changing what happens between the request going out and the events coming in.

Three things to notice before moving on

  1. The model has no memory. Every request resends the full history. The "conversation" lives in your array, not on the server. This will be true for every chapter in the book.
  2. Streaming is a UX choice, not a correctness one. You could request a non-streamed response and print it after it lands. Streaming matters because waiting eight seconds in silence feels broken; watching text appear does not.
  3. You are already 80% of the way to "tool use." A tool call is just another kind of content block in the stream. We will add it in the next chapter and the parser stays almost the same.
In pi's code

Pi's equivalent of this chapter is packages/ai/src/stream.ts (the public stream() / complete() entry points) and the per-provider implementations in packages/ai/src/providers/. The big picture is the same: build a request, open a streaming connection, parse SSE frames into a typed event stream, accumulate into a final message. Pi adds normalized events across providers, cost accounting, and abort handling on top.

What you have now

A working chat REPL. You can hold a multi-turn conversation; tokens stream in as they are produced; history accumulates across turns. It does nothing except chat — but it is a real, live LLM application running in your terminal.
