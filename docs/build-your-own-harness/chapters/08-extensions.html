Extensions

Everything in your harness so far ships with the binary. That is fine for you, the author. But every user has a different workflow, different services, different little tools. Letting them extend the harness without forking it is what turns a useful CLI into a platform.

What is an extension?

An extension is a piece of code that, when loaded, gets to add tools, observe events, modify prompts, register commands, or contribute UI — without the harness knowing about it ahead of time. The shape that has emerged across editor-extension systems for thirty years is the same one that works here:

  1. The harness scans known directories for extension files.
  2. Each file exports a single register(host) function.
  3. The harness calls register at startup, passing a host object with the extension API.
  4. The extension uses the host to contribute things and subscribe to events.

No bespoke plugin manifest, no separate config language. The extension is a small program that talks to a small interface.

The harness owns the loop and the events. Extensions reach in through a small host API.

The host API

This is the contract you commit to. Keep it small and keep it stable; extensions written against it should keep working as your harness evolves. 

interface ExtensionHost {
  // contributions
  addTool(decl: ToolDecl, execute: (input: any) => Promise<string>): void;
  addCommand(name: string, handler: (args: string) => Promise<void>): void;
  appendSystemPrompt(text: string): void;
  contributeSkill(path: string): void;

  // event subscription
  on<E extends keyof EventMap>(event: E, handler: (e: EventMap[E]) => void): void;

  // cleanup
  disposable(fn: () => void | Promise<void>): void;

  // facts about the environment
  readonly cwd: string;
  readonly sessionId: string;
}

Four properties that make this work in practice:

  • One host per extension. Each register() call gets a fresh host bound to that extension. The host remembers what was contributed so the harness can attribute and dispose of it later.
  • Contributions are reversible. Every addTool has a matching removeTool the host can call on shutdown. The extension does not own the registry; the host does.
  • Events flow one way. Extensions can observe almost everything but should not block the loop indefinitely. Async handlers are fine; ten-second handlers are not.
  • The API is your version-1 contract. Once an extension relies on a method, you cannot remove it without breaking the extension. Take this seriously; resist clever shortcuts.

Lifecycle events worth exposing

Most extensions hook one or two events. The events you ship determine the range of useful extensions someone can write. A reasonable starter set:

EventUse cases
session_startLoad credentials, open connections, set per-session state.
before_agent_startInspect or mutate the system prompt for this run.
before_tool_callVeto a tool call (return an error result without executing); audit logs; confirmation prompts.
after_tool_callPost-process tool output; add structured metadata.
messagePipe transcript to an external sink: Slack, file, telemetry.
agent_endDesktop notification, save artefacts, run a checker.
session_shutdownCleanly close anything the extension opened.

Notice the symmetry with the agent-loop events from Chapter 3. That is not a coincidence: the extension system is just a way to let user code subscribe to the same events your TUI already subscribes to. You did the hard work earlier; you are wiring up a new consumer.

Loading extensions

The mechanics depend on your language. In Node/Bun with TypeScript-on-the-fly, you can load .ts files directly: 

const EXT_DIRS = [
  join(os.homedir(), ".pi", "extensions"),
  join(process.cwd(), ".pi", "extensions"),
];

async function loadExtensions(harness: Harness) {
  for (const dir of EXT_DIRS) {
    if (!await exists(dir)) continue;
    for (const entry of await fs.readdir(dir)) {
      if (!entry.endsWith(".ts") && !entry.endsWith(".js")) continue;
      const path = join(dir, entry);
      const mod = await import(path);
      if (typeof mod.register !== "function") continue;
      const host = harness.createHost(entry);
      await mod.register(host);
    }
  }
}

Two design choices worth being explicit about:

  • Global vs project. Honour both. Global extensions (~/.pi/extensions) follow the user everywhere. Project extensions (./.pi/extensions) are scoped to one repo. Project takes precedence on conflict.
  • Loading is sequential. Resist the urge to parallelize. Extensions can have side-effects on each other (registering the same command name); ordering is a feature, not a bug.

A small example end-to-end

Here is a complete extension that gives the agent a way to ask the user a question. The harness has the TUI; the extension just wires it to a tool. 

// ~/.pi/extensions/ask-user.ts

export async function register(host: ExtensionHost) {
  host.addTool(
    {
      name: "ask_user",
      description: "Ask the user a clarifying question and wait for their reply. " +
                   "Use sparingly; prefer to make a reasonable assumption and proceed.",
      parameters: {
        type: "object",
        properties: { question: { type: "string" } },
        required: ["question"],
      },
    },
    async ({ question }) => {
      const answer = await host.ui.prompt(question);  // blocks until user replies
      return answer || "(user did not answer)";
    },
  );
}

Drop that one file in ~/.pi/extensions/. Next time you start the harness, the agent has a new tool. No fork, no rebuild, no registry.

Extensions are code; treat them like code

An extension runs in the same process as your harness. It has full access to the user's filesystem, your process's environment, and the LLM's history. That is the deal: extensions are powerful precisely because they are not sandboxed.

Document the trust model clearly. The user is installing code, not data. Recommend they read extensions before installing. Suggest signing if your ecosystem grows. The pi runtime, for example, refuses to load extensions from npm packages by default unless the user passes an explicit --trust flag.

Declared, not just coded

Some kinds of extension are nicer as data than as code: guidelines, prompts, themes, skills. For those, surface a declarative contribution API: 

// extension contributes a markdown file, not a function:
host.contributeSkill("./skills/postgres-migrations/SKILL.md");
host.contributePromptTemplate("./prompts/code-review.md");
host.contributeTheme("./themes/dracula.json");

The harness handles all the filesystem walking, parsing, and registration. The extension author writes a tiny register() that points at the data. Skills are important enough to be the entire next chapter.

In pi's code

Pi's extension system lives at packages/coding-agent/src/core/extensions/. The host shape is in types.ts, the loader (filesystem scan + dynamic import + jiti-based TypeScript compilation) in loader.ts, and the event dispatcher in runner.ts. Pi exposes a much richer host (custom commands, keybindings, even custom UI components via pi-tui) and supports loading extensions from npm packages and Git URLs. Real examples live in packages/coding-agent/examples/extensions/.

What you have now

A harness that can grow without you. Power users can write a new tool in twenty lines, drop it in a folder, and use it. Teams can ship a shared extension that wires up their internal services. You, the harness author, no longer have to ship every feature anyone might ever want. The next chapter pushes this further: making capability addition possible without writing code at all.
