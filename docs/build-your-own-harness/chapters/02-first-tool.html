Chapter 2 · Part I

Your first tool call

The thing that turns a chatbot into an agent is one capability: the model can ask you to run code. This chapter is about making that round-trip work. After it, the model can answer questions it could not possibly know the answer to — like what is in a file on your disk right now.

What a tool actually is

A "tool" is not a special LLM feature. It is a function you describe to the model: a name, a one-line description, and a schema for its arguments. When the model decides the next thing to do is call that function, it says so in its reply — using exactly the same content-block stream you parsed in Chapter 1. You catch the tool-call block, you execute the function yourself, you send the result back as a new message. The loop continues.

The model never runs anything. You run it. The model just asks.

The round-trip: model asks, you execute, you report back, model answers.

Declaring tools

In the request, alongside the messages, you send a list of tool declarations. A declaration has three fields: 

interface ToolDecl {
  name: string;          // identifier the model will use
  description: string;   // one or two sentences: when to use, what it does
  parameters: JsonSchema; // shape of the input argument object
}

The description matters more than you might expect — it is the only thing the model uses to decide whether to call the tool. Write it like a docstring. Be specific. Mention edge cases.

Our first tool:

const readFile: ToolDecl = {
  name: "read_file",
  description: "Read the contents of a UTF-8 text file on the local disk. " +
               "Returns the entire file as a string. Use for source files, " +
               "configs, and logs. Do not use for binary files or files larger than 1 MB.",
  parameters: {
    type: "object",
    properties: {
      path: { type: "string", description: "Absolute or relative path to the file." },
    },
    required: ["path"],
  },
};

Two new content-block types

Chapter 1's content vocabulary was just text. To do tool calls you need two more block types: one for the model's request, one for your reply. The full vocabulary now looks like this: 

type ContentBlock =
  | { type: "text"; text: string }
  | { type: "tool_use"; id: string; name: string; input: unknown }
  | { type: "tool_result"; toolCallId: string; content: string; isError?: boolean };

tool_use blocks appear inside assistant messages: the model is calling a tool. tool_result blocks appear inside user messages (or a dedicated tool role — providers differ, but the meaning is the same): you are reporting the outcome back to the model.

The id field is the linkage. Each tool_use the model emits gets a unique id; the matching tool_result echoes that id back. In single-tool turns this is overkill, but as soon as the model starts emitting multiple tool calls in one reply (Chapter 3), you will need it.

Parsing tool calls out of the stream

The streamed events now include a few new shapes. Most providers expose tool arguments as a stream of partial JSON fragments, the same way text streams as partial fragments. You accumulate the fragments and parse the whole at tool_use_end: 

let pendingText = "";
const toolCalls: { id: string; name: string; input: string }[] = [];

for await (const event of streamReply(messages, [readFile])) {
  switch (event.type) {
    case "text_delta":
      pendingText += event.text;
      process.stdout.write(event.text);
      break;
    case "tool_use_start":
      toolCalls.push({ id: event.id, name: event.name, input: "" });
      break;
    case "tool_use_delta":
      toolCalls[toolCalls.length - 1].input += event.partialJson;
      break;
  }
}

const assistantMessage: Message = {
  role: "assistant",
  content: [
    ...(pendingText ? [{ type: "text", text: pendingText } as const] : []),
    ...toolCalls.map(c => ({
      type: "tool_use" as const,
      id: c.id,
      name: c.name,
      input: JSON.parse(c.input),
    })),
  ],
};
messages.push(assistantMessage);

Executing the tool

Look at the assistant message you just pushed. If it has any tool_use blocks, you have work to do. For each one: dispatch by name, run the matching function, capture stdout (and stderr, in spirit), pack it into a tool_result block. 

const executors: Record<string, (input: any) => Promise<string>> = {
  read_file: async ({ path }) => await fs.readFile(path, "utf8"),
};

const toolResults: ContentBlock[] = [];
for (const block of assistantMessage.content) {
  if (block.type !== "tool_use") continue;
  try {
    const output = await executors[block.name](block.input);
    toolResults.push({ type: "tool_result", toolCallId: block.id, content: output });
  } catch (err) {
    toolResults.push({
      type: "tool_result", toolCallId: block.id,
      content: String(err), isError: true,
    });
  }
}

if (toolResults.length) {
  messages.push({ role: "user", content: toolResults });
}

Two subtleties worth pausing on:

  • Errors are tool results, not exceptions. When a tool fails, you do not throw. You package the error message as a tool_result with isError: true and let the model decide what to do. Maybe it retries with different arguments. Maybe it apologizes and stops. That is the model's call, not yours.
  • You must send a result for every tool call. Even if a tool has no useful output, even if it errored. A missing result is a protocol violation in most providers and will be rejected.

Closing the loop (for now)

After sending the tool results back, you call the model again. It now has the file contents and can finish its answer. For this chapter we just call the model one more time and print the reply. In Chapter 3 we replace that fixed two-step with a real loop. 

// after pushing the user message containing tool_results:
for await (const event of streamReply(messages, [readFile])) {
  if (event.type === "text_delta") process.stdout.write(event.text);
}
In pi's code

Pi's read tool lives at packages/coding-agent/src/core/tools/read.ts. The declaration fields are richer (line ranges, image support, output truncation, prompt snippets) but the shape is exactly what we built here: a name, a description, a parameter schema, and an execute() function. The streaming-event parser that turns provider chunks into typed tool_use blocks lives in packages/ai/src/providers/.

What you have now

A chat REPL where the model can ask you to read one file before answering. Ask it "What does my package.json say my entry point is?" and watch the dance: the model calls read_file, you execute it, you feed the contents back, the model reads them and answers. You can ship this. It is genuinely useful. But it can only ask once before answering — and that is what the next chapter fixes.
