Chapter 5 · Part II

The system prompt

Up to this point your system prompt has probably been a hard-coded string at the top of the file. That is fine for one tool, in one directory, on one task. It stops working as soon as any of those vary. The system prompt wants to be assembled, not written.

What the system prompt actually is

The system prompt is the standing instruction set the model carries into every turn of every conversation. Unlike user messages, it is not part of the back-and-forth: it sits above the messages array and gets resent on every request. Its job is to answer four questions:

  1. Who am I? — the agent's identity and posture.
  2. What can I do? — the tools available right now.
  3. How should I behave? — the guidelines for how to use them.
  4. Where am I? — the current context (cwd, date, project).

None of those are constants. Tools change when an extension is loaded; guidelines change with which tools are active; the cwd is set per run; the project context is the file you walked into. The natural shape is a function that returns a string, not the string itself.

Think in slots

Below is the assembly we will build. Each labeled box is a slot the harness fills at run time. Some are static, some are computed, some come from disk.

Six independent inputs, one composed prompt. Each is computed fresh on every rebuild.

The builder

The whole assembler is one pure function. Take the slot inputs, return the string. Nothing more. 

interface PromptOptions {
  tools: ToolDecl[];                              // currently active
  toolSnippets: Record<string, string>;          // one-line "what is this"
  toolGuidelines: Record<string, string[]>;      // per-tool bullets
  projectContextFiles: { path: string; content: string }[];
  userAppend?: string;
  cwd: string;
}

function buildSystemPrompt(opts: PromptOptions): string {
  const lines: string[] = [];

  lines.push("You are an expert coding assistant. You help users by reading " +
             "files, executing commands, editing code, and writing new files.");

  lines.push("", "Available tools:");
  for (const t of opts.tools) {
    const snippet = opts.toolSnippets[t.name] ?? t.description;
    lines.push(`- ${t.name}: ${snippet}`);
  }

  lines.push("", "Guidelines:");
  for (const t of opts.tools) {
    for (const g of opts.toolGuidelines[t.name] ?? []) lines.push(`- ${g}`);
  }
  // always-on guidelines:
  lines.push("- Be concise in your responses.");
  lines.push("- Show file paths clearly when working with files.");

  if (opts.userAppend) lines.push("", opts.userAppend);

  if (opts.projectContextFiles.length) {
    lines.push("", "<project_context>");
    for (const f of opts.projectContextFiles) {
      lines.push(`<project_instructions path="${f.path}">`);
      lines.push(f.content);
      lines.push(`</project_instructions>`);
    }
    lines.push("</project_context>");
  }

  lines.push("", `Current date: ${new Date().toISOString().slice(0, 10)}`);
  lines.push(`Current working directory: ${opts.cwd}`);

  return lines.join("\n");
}

Tools carry their own guidelines

The most underrated detail in that builder is the toolGuidelines input. Bullets like "Use write only for new files" or "Use read instead of cat or sed" are not global knowledge — they belong to the tool that needs them. So attach them to the tool definition itself: 

const write = {
  name: "write",
  description: "Create a new file or completely overwrite an existing one.",
  promptSnippet: "Create or overwrite files",
  promptGuidelines: ["Use write only for new files or complete rewrites."],
  parameters: { /* ... */ },
};

When the harness assembles the prompt, it collects snippets and guidelines from whichever tools are active. Add a new tool? Its guidelines come along for free. Remove a tool? Its guidelines disappear — you do not have a stale "use git_log when ..." bullet sitting in the prompt for a tool that was disabled.

Project context: walking the tree

Almost every modern coding harness honours an AGENTS.md-style file: a markdown document the user puts in their repo with project-specific instructions ("use pnpm, never npm"; "tests live in tests/"; "don't touch the generated files").

Discovering them is a tree walk from the cwd toward the root, plus a global one in the user's home: 

async function loadContextFiles(cwd: string): Promise<{ path: string; content: string }[]> {
  const names = ["AGENTS.md", "CLAUDE.md"];
  const found: { path: string; content: string }[] = [];

  for (const dir of walkUp(cwd)) {            // cwd, cwd/.., cwd/../.., ...
    for (const name of names) {
      const p = join(dir, name);
      if (await exists(p)) found.push({ path: p, content: await fs.readFile(p, "utf8") });
    }
  }
  // and one global location:
  const global = join(os.homedir(), ".pi", "AGENTS.md");
  if (await exists(global)) found.push({ path: global, content: await fs.readFile(global, "utf8") });

  return found;
}

Wrap each file in <project_instructions path="...">...</project_instructions> XML tags inside the prompt. The model is good at respecting that structure; it treats each file as a labeled directive set rather than a wall of text.

When to rebuild

Do not rebuild on every turn. The prompt is large; recomputing it (and paying the cache miss with your provider) is wasteful. Rebuild only when one of its inputs changes:

  • Session start.
  • Tools change (extension loaded, user toggled a tool, mode switched).
  • Resources change (a new AGENTS.md appeared mid-session).
  • The user explicitly reloads.

Cache the result on your Session object and reuse it across turns. Provider-side prompt caching will reward you for keeping the prefix stable.

A few sharp edges

  • Date and cwd go last. They are short. Keeping them at the bottom means the long, stable prefix above stays identical across runs, which is exactly what prompt caches want.
  • Deduplicate guidelines. If two tools both contribute "Be careful with destructive commands", normalize and de-dupe before emitting. Repetition does not reinforce the rule; it dilutes the others.
  • Keep it short. A 4,000-token system prompt is a smell. If yours gets that long, you are probably encoding rules that should be in tool descriptions instead.
  • Document escape hatches. Allow users to replace the base prompt (not just append to it) for unusual workflows. Pi calls this the customPrompt option.
In pi's code

Pi's builder is packages/coding-agent/src/core/system-prompt.ts:buildSystemPrompt(). It is structurally identical to the one above with a few additions: a pointer to pi's own documentation (so the agent can introspect itself), a skills section (Chapter 9), and the ability to fully replace the base prompt with a user-supplied one. The session calls it from agent-session.ts:_rebuildSystemPrompt() exactly at the moments listed in When to rebuild.

What you have now

A harness that adapts to its environment. Run it in a TypeScript project and the model picks up the project's conventions from AGENTS.md. Disable a tool and the model stops trying to use it. Add a tool and the guidelines explaining how to use it come along automatically. Everything that follows in this book either changes which inputs feed the prompt (sessions, extensions, skills) or how the rest of the harness sits around it (UI, persistence).
