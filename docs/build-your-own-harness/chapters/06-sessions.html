Sessions: save and resume

Coding tasks rarely fit into one sitting. You start something, get interrupted, come back the next morning, and want to pick up where you were. This chapter is about adding the persistence layer that makes --continue work — and why JSONL is almost always the right format for it.

Why an append-only log

Your harness already has the source of truth: the in-memory messages array. The naive way to persist it is to dump the whole array to disk after each turn. That works, scales badly, and corrupts loudly on a crash mid-write.

A better shape: append-only. Every message that gets pushed onto the array also gets a line written to a file. The file is the array's history. To resume, you read the file line by line and replay each row into a fresh array. JSON lines (JSONL) is the format: one JSON object per line, newline separated.

The on-disk file mirrors the in-memory array. To resume, replay the lines.

Why JSONL specifically

JSONL has four properties that make it almost unreasonably good for this:

  1. Append is one syscall. No re-encode of prior content.
  2. Lines are independent. If the process dies mid-write, the last (incomplete) line is the only one corrupted; everything before it is fine.
  3. It is human-readable. When something weird happened in a session, you can cat the file and read it.
  4. Tooling already exists. jq, grep, and a hundred other utilities operate on JSONL out of the box.

Where to store sessions

A conventional layout, separate from the project itself: 

~/.pi/agent/sessions/
  <project-hash>/
    01HX0K9T-summarize-the-readme.jsonl
    01HX0M2N-refactor-auth-middleware.jsonl
    ...

Hashing the project root (or its absolute path) into a directory name lets you list this project's sessions without scanning every session you have ever had. The session filename includes a ULID-style sortable prefix (so ls sorts chronologically) and a short title derived from the first user message.

The writer

Open the file once when the session starts, append on every message, close when the harness exits. That is it. 

class SessionWriter {
  constructor(private fh: fs.FileHandle) {}

  static async open(path: string) {
    await fs.mkdir(dirname(path), { recursive: true });
    return new SessionWriter(await fs.open(path, "a"));
  }

  async append(msg: Message & { id?: string }) {
    const row = { id: msg.id ?? ulid(), timestamp: Date.now(), ...msg };
    await this.fh.write(JSON.stringify(row) + "\n");
  }

  async close() { await this.fh.close(); }
}

Wire it to the event stream from Chapter 3. Every time the agent emits a message event, write a line. Nothing else in the harness needs to know the writer exists. 

agent.on("message", (msg) => writer.append(msg));

The reader (and resume)

Resuming is the inverse. Read the file, parse each line, push into a fresh messages array, hand it to the agent. 

async function loadSession(path: string): Promise<Message[]> {
  const text = await fs.readFile(path, "utf8");
  const messages: Message[] = [];
  for (const line of text.split("\n")) {
    if (!line) continue;
    const { id, timestamp, ...msg } = JSON.parse(line);
    messages.push(msg);
  }
  return messages;
}

const messages = await loadSession("~/.pi/sessions/.../foo.jsonl");
await runAgent(messages, tools);

Now wire up the CLI flags users expect:

FlagBehaviour
--continue (or -c) Resume the most recent session for the current project. ls -t the project's session directory; grab index 0.
--resume <id> Resume a specific session by its ULID prefix.
--resume (no arg) Show a picker: list of sessions with timestamps and first-line titles.
(no flag) Start a fresh session. Generate an id, mint a filename, open the writer.

Session metadata

You will eventually want more on disk than just messages. The model used. The thinking budget. Which tools were active. The cwd. Skills loaded. Anything else you need to rebuild the system prompt identically on resume.

Two reasonable approaches, both used in the wild:

Sidecar file

Write a session.json alongside the JSONL with the metadata. Read both on resume. Simple, but two files to keep in sync.

First-line header

Make the first line of the JSONL a special "session_start" row containing the metadata. Compose nicely with the append-only model: just another row. This is what pi does.

Either way, treat metadata as data: every field a different version of your harness might want, even ones you do not use yet. Versioning the file format (a version field on the header) is cheap and saves grief later.

Branching: the bonus feature you get for free

Append-only logs have a quiet superpower. If each message carries an id and a parent_id pointing to the message it responded to, the log becomes a tree, not a list. Now you can rewind to a previous turn, take a different path, and the original branch is still there if you want to come back.

Each row carries a parent_id. Resuming chooses a leaf; the path back to the root is the conversation.

This is more machinery than most harnesses need on day one. But the file format does not preclude it — you just add id and parent_id from the start. If you ever want branching, you can build it without rewriting the storage layer.

Three small bookkeeping things

  • Use fsync sparingly. A coding session produces 50–500 messages. fsync on every line is slow and rarely needed; OS buffer + close-on-exit is usually enough.
  • Atomic appends. On POSIX, an O_APPEND write is atomic for writes under PIPE_BUF. Your JSONL lines fit. Even on a power loss, you get whole-line writes or a torn final line you can detect and discard on read.
  • Never edit old rows. The whole point of append-only is that history is immutable. If you need to "delete" a message, append a tombstone row instead and have the reader skip it. You will never need this for a coding harness, but the discipline is good.
In pi's code

Pi's session layer is packages/agent/src/harness/session/. The JSONL repo is at jsonl-repo.ts, the in-memory one (for tests) at memory-repo.ts, both behind a SessionRepo interface. Pi treats sessions as a tree from the start: each row has id and parentId, and the user can branch via /branch. The header-as-first-row pattern lives in session.ts, with metadata describing model, tools, skills, and compaction state.

What you have now

A harness that survives shutdown. Start a task, quit, come back tomorrow, pi --continue, you are right where you left off — same messages, same context, same model. If you want to look at what happened yesterday, the file is readable text on disk. The transcript is also the storage; nothing is hidden.
