Chapter 4 · Part II

A real coding toolkit

A read-only agent is half an agent. To make changes — to actually do the thing the user asked — the model needs to write files, edit them, and run commands. In this chapter we add the three tools that matter, and confront the design questions each one forces you to answer.

Tool design is product design

By now the mechanics of adding a tool are routine: name, description, schema, executor. The interesting decisions are about shape:

  • What inputs does the tool accept? Few and explicit, or many and lenient?
  • What does success look like? Silence? A confirmation? Some output?
  • What does failure look like? An error string, structured details, both?
  • What is the worst thing this tool can do? Are you OK with the model doing it?

These are not abstract. The choices ripple straight back to model behaviour. A bad bash tool teaches the model to babysit it; a good one fades into the background.

Three tools, three risk profiles, three different jobs. Reach for the smallest one that does the job.

bash — the dangerous one

The instinct is to make bash a thin pass-through: command goes in, all output comes out. That fails in three ways:

  1. It runs forever. A model that runs npm install or a long test suite needs to be cut off if it gets stuck. Always parameterize a timeout (and use a sensible default like 120 seconds).
  2. It produces too much output. A command that dumps a 50,000-line log will blow your context window on a single tool call. Cap the output and tell the model you truncated:
  3. It is unaware of the working directory. If the harness spawns a new shell for each call, every command runs in a fresh cwd. cd in one call does not persist into the next. Pick a model: either run each command from the project root and accept that cd is broken, or maintain a virtual cwd that the harness applies to every spawn.

A reasonable implementation:

const bash: ToolDecl = {
  name: "bash",
  description: "Run a shell command. Returns combined stdout/stderr, truncated to ~1000 lines.",
  parameters: {
    type: "object",
    properties: {
      command: { type: "string" },
      timeout_seconds: { type: "number", description: "Default 120, max 600." },
    },
    required: ["command"],
  },
};

async function runBash({ command, timeout_seconds = 120 }) {
  const proc = spawn("bash", ["-c", command], { cwd, env: process.env });
  const chunks: Buffer[] = [];
  let bytes = 0;
  const MAX = 200_000;
  proc.stdout.on("data", b => { if (bytes < MAX) { chunks.push(b); bytes += b.length; } });
  proc.stderr.on("data", b => { if (bytes < MAX) { chunks.push(b); bytes += b.length; } });

  const timer = setTimeout(() => proc.kill("SIGTERM"), timeout_seconds * 1000);
  const code = await new Promise<number>(r => proc.on("exit", c => r(c ?? -1)));
  clearTimeout(timer);

  let out = Buffer.concat(chunks).toString("utf8");
  if (bytes >= MAX) out += "\n\n[output truncated]";
  return `exit ${code}\n${out}`;
}
Stop and think about this. A coding agent with a bash tool can rm -rf $HOME, exfiltrate your credentials, install backdoors, or spend money. Pi runs without sandboxing by default and relies on the user's review of each step. That is a real trade-off. If your harness is going to ship to anyone but yourself, design the safety story before you ship: an allowlist, a confirmation prompt for destructive commands, a container boundary, or simply no bash at all.

write — the simple one

write is the easiest tool to get right and the easiest to get subtly wrong. Right: 

const write: ToolDecl = {
  name: "write",
  description: "Create a new file or completely overwrite an existing one. " +
               "Use only for new files or complete rewrites. For surgical changes, use edit.",
  parameters: {
    type: "object",
    properties: {
      path: { type: "string" },
      content: { type: "string" },
    },
    required: ["path", "content"],
  },
};

async function runWrite({ path, content }) {
  await fs.mkdir(dirname(path), { recursive: true });
  await fs.writeFile(path, content, "utf8");
  return `wrote ${content.length} bytes to ${path}`;
}

The description is doing real work there. Without the second sentence, the model will use write to make a one-line change to a 5,000-line file, re-emitting all 5,000 lines. That is slow, expensive, and bad for the user's diff history. Spell out the boundary; the model will respect it.

edit — the precise one

edit is where harnesses differ most. Two reasonable shapes:

Diff-based

Send a unified diff. The harness applies it with patch semantics. Pro: familiar format, supports moves. Con: line-number drift; the model has to count lines accurately, which it is bad at.

Text-anchor based

Send { oldText, newText } pairs. The harness finds oldText in the file and replaces it. Pro: the model just quotes existing text. No line numbers. Con: ambiguous matches must be rejected; the model must include enough surrounding context to disambiguate.

Text-anchor is what most modern harnesses (including pi) settle on. It matches how the model thinks — the model can quote text it just read — and the failure modes are easy to surface: "oldText matched zero times" or "oldText matched three times; be more specific." 

const edit: ToolDecl = {
  name: "edit",
  description: "Make precise edits to a file. Each edit replaces an exact " +
               "occurrence of oldText with newText. oldText must appear " +
               "exactly once in the file (use enough context to disambiguate).",
  parameters: {
    type: "object",
    properties: {
      path: { type: "string" },
      edits: {
        type: "array",
        items: {
          type: "object",
          properties: {
            oldText: { type: "string" },
            newText: { type: "string" },
          },
          required: ["oldText", "newText"],
        },
      },
    },
    required: ["path", "edits"],
  },
};

async function runEdit({ path, edits }) {
  let text = await fs.readFile(path, "utf8");
  for (const [i, { oldText, newText }] of edits.entries()) {
    const occurrences = text.split(oldText).length - 1;
    if (occurrences === 0) throw new Error(`edit ${i}: oldText not found`);
    if (occurrences > 1)  throw new Error(`edit ${i}: oldText matched ${occurrences} times`);
    text = text.replace(oldText, newText);
  }
  await fs.writeFile(path, text, "utf8");
  return `applied ${edits.length} edit(s) to ${path}`;
}

Two protective details there:

  • All-or-nothing. If any edit fails, none are applied. The error message tells the model what went wrong so it can retry.
  • Edits apply sequentially to the buffer. The first edit may produce text that the second edit then references. This is convenient for the model; just document it so it knows.

The shape of an error

Tool errors are tool results, not exceptions (we said this in Chapter 2 and it bears repeating). What an error contains matters as much as how it is signaled:

Bad errorGood error
EACCES cannot write to /etc/hosts: permission denied. Run as root or pick a different path.
edit failed edit 2: oldText "import foo from './bar'" not found in src/main.ts. The current import is "import foo from '../bar'".
timeout command killed after 120s. Last 50 lines of output were: ...

The model is trying to recover. Give it what it needs to recover.

A note on confirmation

Some harnesses prompt the user to approve every bash or write call. Some only prompt for destructive commands. Some never prompt. There is no right answer; there is a trade-off between safety and flow. Pick a default for your harness, but build the plumbing so users can choose. Confirmation is just another event listener: when a tool_start event fires for a flagged tool, block the loop on a user response, then either continue or report a synthetic "user cancelled" error back to the model.

In pi's code

Pi's three tools live at packages/coding-agent/src/core/tools/bash.ts, write.ts, and edit.ts. Notable extras: bash truncates by line count and bytes (whichever hits first), saves full output to a temp file when truncated; edit refuses overlapping oldText matches and rejects edits that look like multi-line diffs the model should have batched. The promptGuidelines field on each tool definition is what teaches the model the "use write for new files, edit for surgical changes" rule.

What you have now

A coding agent that can read, write, edit, and run commands. Ask it to add a new field to a config and update the parser; it will read the config, read the parser, edit both, and run the test suite. This is the full functional shape of a coding harness — everything from here on is making it pleasant, safe, and durable.
