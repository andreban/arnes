A live terminal UI

Plain stdout has carried you this far. It will not carry you further. The user wants to see the model's reply stream in and have a cursor in an input box ready for the next prompt — at the same time. That requires giving up on writing-and-forgetting and learning to paint the terminal as if it were a small, character-grid display.

The terminal as a tiny display

A terminal is a grid of cells: rows tall, cols wide. You write a stream of bytes; most are characters that go in cells; some are ANSI escape sequences that move the cursor, change colours, or clear regions. Building a TUI is fundamentally about choosing, on each redraw, what bytes to emit so that the visible cells match the state you want them to.

The core concepts you cannot avoid:

  • Raw mode. By default the terminal cooks input (echoes characters, buffers until newline, handles backspace). For a TUI you want every keystroke, immediately, in raw form. You ask the OS for raw mode at start and restore cooked mode at exit.
  • Alternate screen buffer. An ANSI sequence that gives you a clean scrollback-less canvas to draw into; when you exit, the user's prior terminal contents come back. Optional, but it makes your UI feel like an "app".
  • Cursor control. \x1b[H goes to top-left, \x1b[3;5H goes to row 3 column 5, \x1b[K clears to end of line. With a small vocabulary you can redraw anything.
  • Synchronized output. Without it, fast redraws flicker as you erase before drawing. Wrap a frame in \x1b[?2026h ... \x1b[?2026l and the terminal buffers the whole sequence and applies it atomically.

Full redraw is the wrong default

The instinct is: on every event, clear the screen, redraw everything. It works for a single static screen. It flickers on streaming, scrolls badly, and burns CPU on long transcripts.

The right default is differential rendering. You keep two arrays of lines: the lines currently on screen, and the lines you want on screen. You walk both arrays in lockstep; only emit ANSI sequences for the rows that changed.

Full redraw repaints every cell on every frame. Differential repaints only what changed.

A component is just render(width)

Resist the urge to import a React-clone for the terminal. The abstraction you need is much smaller: 

interface Component {
  render(width: number): string[];   // one array entry per visible line
  handleInput?(data: string): void;  // optional
}

A component is anything that, given a width, can produce a fixed list of string lines and optionally react to keystrokes. That is enough to build text, lists, inputs, modals — everything.

A container is a component that holds children and concatenates their output: 

class Container implements Component {
  children: Component[] = [];
  render(width: number): string[] {
    return this.children.flatMap(c => c.render(width));
  }
  handleInput(data: string) {
    this.focused?.handleInput?.(data);
  }
}

The render loop

One render loop coordinates everything. It owns the previous-frame array, the terminal handle, and the focused component. On any event — a keypress, a streaming token from the agent, a window resize — it schedules a redraw: 

class TUI {
  private prevLines: string[] = [];

  scheduleRender = debounce(() => this.render(), 16);  // ~60 fps cap

  render() {
    const width = process.stdout.columns;
    const newLines = this.root.render(width);
    const frame: string[] = [];

    // begin synchronized output
    frame.push("\x1b[?2026h");

    // emit only changed lines
    const max = Math.max(this.prevLines.length, newLines.length);
    for (let i = 0; i < max; i++) {
      if (this.prevLines[i] === newLines[i]) continue;
      frame.push(`\x1b[${i + 1};1H`);  // move to row i+1 col 1
      frame.push("\x1b[K");             // clear to end of line
      frame.push(newLines[i] ?? "");
    }

    frame.push("\x1b[?2026l");          // end synchronized output
    process.stdout.write(frame.join(""));
    this.prevLines = newLines;
  }
}

Three subtleties hiding in that snippet:

  • Width matters. Each component must produce lines that fit inside the given width. Overflow is the most common TUI bug. Provide helpers for "truncate this string to n visible characters" that understand ANSI escapes (they take no visual width) and combining characters/CJK (which can be wide).
  • The cursor lands where the focused component wants it. After rendering, position the hardware cursor to wherever the input box's cursor sits. Most components emit a tiny marker (a zero-width escape) at the cursor location, the TUI strips it out, and positions the real cursor where the marker was. This is also what makes IME candidate windows show up in the right spot.
  • Resize is just another event. process.stdout emits resize; the loop's response is to invalidate prevLines (force a full redraw next frame) and re-render.

Reading input

In raw mode, every keystroke arrives as one or more bytes on stdin. Plain printable characters are themselves; special keys arrive as ANSI escape sequences: 

\r         -> Enter
\x7f       -> Backspace
\x1b[A     -> Up
\x1b[B     -> Down
\x1b       -> Escape (or the start of a longer sequence)
\x03       -> Ctrl-C
\x04       -> Ctrl-D

Write a tiny parser that takes the raw bytes and emits a typed key: 

type Key =
  | { type: "char"; char: string }
  | { type: "enter" } | { type: "backspace" } | { type: "escape" }
  | { type: "up" } | { type: "down" } | { type: "left" } | { type: "right" }
  | { type: "ctrl"; char: string };

function parseKey(data: string): Key { /* ... */ }

Components can then ignore the byte layer entirely. Modern terminals also support the Kitty keyboard protocol, which encodes every key unambiguously (including shift state, repeat, and release). If you target it, opt in by sending an escape at startup; fall back to the legacy encoding for terminals that do not respond.

A layout sketch for a coding agent

A typical coding-agent TUI: scrolling transcript on top, status row, input at the bottom.

As a layout, this is just three stacked components: a scrolling transcript view, a status row, an input. The transcript subscribes to the agent's event stream and grows a new "message" component every time a message_start arrives. The input owns the cursor; on Enter it dispatches the text to the agent. Streaming text_delta events update the current message in place, which the TUI sees as a one-line diff and repaints just that line.

Windows in passing

Windows console support has historically been the hard part of cross-platform TUIs. The good news: Windows 10+ supports ANSI sequences out of the box, provided you enable ENABLE_VIRTUAL_TERMINAL_INPUT on the console. That is a single Win32 call. Wrap it in a tiny native add-on (or a JS spawn-and-exit dance) and you are good. Use conpty under the hood and most of the rest just works.

In pi's code

Pi's TUI is its own package: packages/tui/. The render loop and Container/Component model live in src/tui.ts; the key parser (both legacy and Kitty protocol) in src/keys.ts; the big components in src/components/. The differential renderer in tui.ts uses three strategies depending on the situation: first-render (no clear, preserves scrollback), full redraw (on width change), and incremental (the common case). Native modifier probing on macOS and the Win32 virtual-terminal toggle are tiny C add-ons under packages/tui/native/.

What you have now

A real interactive harness. Stream tokens land in a scrollable transcript; a persistent input box sits at the bottom; tool calls appear as their own little cards; Ctrl-C aborts cleanly. The agent feels like a program, not a script. From here on out everything is about making the harness open — pluggable, extensible, capable of growing without you in the loop.
