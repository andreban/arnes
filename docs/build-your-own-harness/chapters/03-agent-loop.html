The agent loop

Chapter 2 gave you a model that can call one tool, then answer. Real tasks need more than that. The agent loop is the small piece of control flow that turns a one-shot tool call into open-ended problem solving: "Keep going until you have a real answer."

Why a loop?

Consider this prompt: "Find the file that defines our database connection and tell me how it is configured."

No single tool call answers that. The model needs to list the project, read a few candidates, follow imports, then summarize. It will issue several tool calls, each one informed by the results of the previous ones. Your harness has to be willing to keep running them until the model says it is finished.

That is the loop. It has exactly two states.

Two states, one decision. The whole loop fits in your head.

The loop, in twelve lines

async function runAgent(messages: Message[], tools: ToolDecl[]) {
  while (true) {
    const assistant = await streamAssistantReply(messages, tools);
    messages.push(assistant);

    const toolCalls = assistant.content.filter(c => c.type === "tool_use");
    if (toolCalls.length === 0) return; // model gave a final answer

    const results = await Promise.all(toolCalls.map(executeOne));
    messages.push({ role: "user", content: results });
  }
}

That is the whole thing. Two states (talk, run), one branch (any tool calls this turn?). Everything you will add for the rest of this book sits around that twelve-line core; the core itself almost never changes.

Knowing when the model is done

In Chapter 1 we read individual stream events; we also need to look at the terminator. Most providers send a final event carrying a stop_reason. The values you care about:

Stop reasonWhat it meansWhat you do
end_turn The model is done speaking. If there are tool calls, run them. If not, exit the loop.
tool_use The model paused specifically to wait for tool results. Run the tools, send results, continue.
max_tokens You hit the output token limit mid-reply. Surface this to the user. The reply is truncated and likely useless.
stop_sequence A stop sequence you configured fired. Treat like end_turn.

In practice the simple "any tool calls?" check from the snippet above does the right thing in almost every case. The stop reason is for diagnostics and for catching the broken cases.

Parallel tool calls

A single assistant turn can contain multiple tool_use blocks. When that happens, do not run them one at a time. Run them concurrently. Modern models specifically batch independent calls (three file reads, two greps) precisely because the harness is supposed to fan them out. 

const results = await Promise.all(
  toolCalls.map(async (call) => {
    try {
      const output = await executors[call.name](call.input);
      return { type: "tool_result", toolCallId: call.id, content: output };
    } catch (err) {
      return { type: "tool_result", toolCallId: call.id, content: String(err), isError: true };
    }
  })
);

But: order in the response matters. The tool_result blocks must appear in the same order as the tool_use blocks the model emitted. Promise.all preserves index order, which is exactly what you want. If you ever switch to a queue-based model, sort by index before sending.

Some tools should never run in parallel — anything that mutates shared state (a tool that changes the working directory, a tool that pops dialogs). Mark those tools executionMode: "sequential" and degrade to serial when any sequential tool is present in the batch.

Three things you must guard against

An unbounded loop driven by a probabilistic system is a recipe for runaway behaviour. Three guards keep it tame:

  1. A turn cap. Bail out after, say, 50 turns of pure tool use with no final answer. The model is stuck or the task is impossible; either way, hand control back to the user.
  2. An abort signal. Pipe an AbortSignal through the loop and into your tool executors so the user can press Ctrl-C and have everything stop cleanly — the in-flight HTTP request, the bash process, the file write. Without this, the user is a hostage to the model.
  3. Visible progress. Print which tool is being called and a short preview of its input. A silent loop that hangs for thirty seconds is indistinguishable from a crash. The model is doing things; show that.

Emitting events

As your harness grows, more parts of it will care about what is happening inside the loop: the UI wants to draw tool-call cards, the session log wants to record each message, an extension might want to veto a tool. Push that curiosity out of the loop itself by emitting events instead of calling those systems directly: 

type AgentEvent =
  | { type: "turn_start" }
  | { type: "message"; message: Message }
  | { type: "tool_start"; call: ToolUseBlock }
  | { type: "tool_end"; result: ToolResultBlock }
  | { type: "turn_end" };

The loop emits; subscribers react. In Chapter 7 your TUI subscribes to redraw on each event. In Chapter 6 your session writer subscribes to append every message to disk. In Chapter 8 your extension runtime subscribes to every event and forwards them to extensions. One emitter; many independent consumers.

In pi's code

Pi's loop lives in packages/agent/src/agent-loop.ts — a few hundred lines of TypeScript, but if you squint you can see the same twelve-line skeleton in there. The richer parts are the event vocabulary (turn_start, message_update, tool_execution_start, …), the sequential/parallel mode logic, and a "steering"/"follow-up" mechanism that lets the user inject messages mid-flight. The Agent class in packages/agent/src/agent.ts wraps the loop with mutable state, subscribers, and lifecycle methods.

What you have now

A genuine research agent. Give it a single file path and ask for an explanation of the surrounding module; it will read, follow imports, read more, and produce a synthesis. With just read_file in its toolbox, that is already useful. The next chapter is about giving it enough tools to change things, not just describe them.
