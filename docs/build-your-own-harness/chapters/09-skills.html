Skills

A skill is what you reach for when something is too big for the system prompt and too small for an extension. A markdown file that the agent knows exists but only reads when the task at hand needs it. The trick is that "knows exists" costs almost nothing — and "reads" only happens when it pays off.

The problem with cramming everything in

Imagine your harness should know:

  • How to write database migrations for your particular Postgres setup.
  • How to add a new feature flag in your specific feature-flagging system.
  • How to release a new version of your library: the bump, the changelog, the npm publish, the GitHub release notes.
  • How to interpret crash reports from your monitoring tool.
  • Twenty other specific things, each a page or two of detail.

You could put all of this in the system prompt. It would work. It would also send 8,000 tokens of unrelated instructions on every request, dilute the model's attention, and make every conversation more expensive and slower. Most of those instructions are not relevant to most tasks.

Skills solve this with one observation: the model is good at deciding when to ask for more information. So you do not load the migration playbook into the prompt. You load a one-line signpost: "There is a skill called postgres-migrations that explains how to write database migrations for this project; load it when needed." The model reads the signpost; if the task is about migrations, it calls read_file on the skill's location and gets the full content. Otherwise it ignores it.

The skill's content lives on disk. The prompt carries only the signpost.

The skill format

A skill is a markdown file with YAML frontmatter. The frontmatter carries the metadata the harness needs to advertise it; the body is the instructions for the model. 

---
name: postgres-migrations
description: |
  Write a new database migration for the project's Postgres schema. Use
  when the user wants to add/alter/drop tables, columns, indices, or
  constraints. Includes the naming convention, the directory layout, and
  how to handle backfills for NOT NULL columns on large tables.
---

# Postgres migrations

This project uses [name-your-tool] migrations. Every migration is two files:

1. `migrations/{ulid}_short_name.up.sql`
2. `migrations/{ulid}_short_name.down.sql`

## Steps

1. Generate a new ULID for the migration prefix.
2. Write the up SQL.
3. Write the down SQL (must reverse the up).
4. ... [the rest of the playbook]

Two fields matter, and only two:

  • name — a short, dash-separated identifier. The model uses it to refer to the skill. Keep it under ~50 characters; treat it like a filename.
  • description — the only thing the model sees by default. Write it like a docstring for the entire skill: when to use, what it covers, what edge cases it handles. This is the selector.

Discovery

Same discovery pattern as extensions, applied to SKILL.md files: 

const SKILL_DIRS = [
  join(os.homedir(), ".pi", "skills"),     // global
  join(process.cwd(), ".pi", "skills"),    // project-local
];

async function loadSkills(): Promise<Skill[]> {
  const skills: Skill[] = [];
  for (const root of SKILL_DIRS) {
    for (const dir of await listDirs(root)) {
      const skillPath = join(dir, "SKILL.md");
      if (!await exists(skillPath)) continue;
      const text = await fs.readFile(skillPath, "utf8");
      const { frontmatter, body } = parseFrontmatter(text);
      skills.push({
        name: frontmatter.name,
        description: frontmatter.description,
        filePath: skillPath,
      });
    }
  }
  return skills;
}

Notice we do not read the body. The body lives on disk; the model fetches it when needed.

Surfacing skills to the model

Inject a section at the bottom of the system prompt listing each skill's name, description, and absolute location. An XML block makes the structure unambiguous: 

function formatSkillsSection(skills: Skill[]): string {
  if (skills.length === 0) return "";

  const lines = [
    "",
    "The following skills provide specialized instructions for specific tasks.",
    "Use the read_file tool to load a skill's file when the task matches its description.",
    "",
    "<available_skills>",
  ];

  for (const s of skills) {
    lines.push("  <skill>");
    lines.push(`    <name>${s.name}</name>`);
    lines.push(`    <description>${s.description}</description>`);
    lines.push(`    <location>${s.filePath}</location>`);
    lines.push("  </skill>");
  }
  lines.push("</available_skills>");
  return lines.join("\n");
}

The instruction above the block is critical. Without it, the model is trained to chat with you about the skills instead of using them. Spell out the action: read the file with your read tool.

Skills depend on read

A skill is useless without a tool that can read it. The harness should refuse to advertise skills if the read tool is not active in the current session — otherwise the model will see the signposts, try to follow one, fail, and apologize. Detect this and just skip the whole skills section in that case.

Anatomy of a good skill

Three habits separate skills that work from skills that get ignored:

  1. Write the description like a function signature. "When you should use this. What it covers. What it does not cover." Each clause helps the model decide whether to read the body. Skills with vague descriptions ("information about the database") never get loaded.
  2. Make the body procedural. The model is going to follow the steps mechanically. Numbered steps; concrete code examples; explicit "do this then that" instead of "consider doing X." Save the rationale for a brief preamble, but the bulk should read like a runbook.
  3. Put supporting files next to the SKILL.md. Example code, templates, large reference tables — drop them in the skill's directory and link relatively. The model can read them with the same read tool. This keeps the SKILL.md scannable.

Letting users invoke skills directly

Sometimes the user knows exactly which skill applies. Letting them say /skill:postgres-migrations in the input box (and having the harness inject the skill's body as a system note before the next turn) is a nice escape hatch: the user gets to lead the model rather than hope it picks the right signpost.

In your harness this is a CLI command, not a model-facing tool. The command handler reads the SKILL.md body and pushes it as a synthetic message with role user and content something like: "The following are instructions for the postgres-migrations skill the user explicitly requested. Follow them."

When not to use a skill

Skills are not the answer to everything:

  • If something applies to every task, put it in the system prompt. Skills are for the conditional body of knowledge.
  • If something needs to do things, write an extension. Skills are instructions; extensions are code.
  • If something is small enough to fit in a tool's description, put it there. Tools are even cheaper than skills.

The mental hierarchy is: always-relevant rules → system prompt. Always-relevant capabilities → tools. Sometimes- relevant instructions → skills. Sometimes-relevant capabilities → extensions.

In pi's code

Pi's skills loader is packages/coding-agent/src/core/skills.ts. The format follows the open Agent Skills standard: a directory containing a SKILL.md with YAML frontmatter (name, description, optional disable-model-invocation). The XML block injected into the prompt is built by formatSkillsForPrompt(); the section is only emitted when the read tool is active. Skills can also be contributed by extensions (Chapter 8) via host.contributeSkill().

What you have now

A harness whose effective knowledge grows without growing its prompt. Drop a new SKILL.md in a directory; the next session it is available; the model loads it only when relevant; the rest of the time it is just twenty tokens of metadata. The harness has gone from "smart on a fixed set of tasks" to "as smart as the skills the user bothers to write."
