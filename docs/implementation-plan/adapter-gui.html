Adapter

arnes-gui

The fourth face. Intentionally specified as "another adapter," not as "this technology stack." The whole point of the architecture is that the GUI choice is local and reversible — the core does not care which window system or rendering toolkit you pick.

Three viable paths

All three implement the same Frontend trait against the same arnes-core::Session. They differ only in how they render and where they live.

Tauri

One Rust binary; web UI inside a system webview. arnes-core runs in-process; the webview talks to it via Tauri's command bridge. UI work in HTML/CSS/TS; native distribution.

pro: small binary, web UI flexibility · con: webview baggage

egui / iced (native)

Pure Rust GUI. Single binary, no webview, immediate-mode (egui) or Elm-style (iced). arnes-core lives in the same process; UI state owns the events directly.

pro: no JS, no webview, fast · con: UI features in Rust

Web app + HTTP/WS

The GUI is a separate browser app talking to arnes-serve over the HTTP+WS adapter. No new crate at all — the GUI is just a client of the existing adapter.

pro: zero new Rust code · con: needs a running server

A leaning, not a decision

If we had to pick today, the web app on top of arnes-http is the cheapest option: it requires zero new Rust crates. The browser is a pre-existing, well-understood GUI runtime, and we already need the HTTP/WS adapter for other reasons. A purpose-built native GUI gives a nicer single-binary distribution but doubles the surface area to maintain.

This decision is deferred until we have a concrete user need that distinguishes the options. Until then, the plan treats the GUI as optional, and the architecture is built so that none of the three paths require changes to arnes-core.

What the adapter looks like, whichever stack we pick

Same shape as TUI and HTTP. A GuiFrontend implements Frontend; an input handler calls session.prompt(text) on user submission; a permission UI handles request_permission. The Host is LocalHost for the desktop GUI options, or LocalHost on the server side for the web+HTTP option. 

// arnes-gui/src/frontend.rs (sketch — identical shape regardless of stack)

pub struct GuiFrontend {
    state: Arc<Mutex<GuiState>>,
    redraw: Arc<dyn Fn() + Send + Sync>,   // tauri::App::trigger_global or egui ctx.request_repaint
}

#[async_trait]
impl Frontend for GuiFrontend {
    async fn on_event(&self, ev: SessionEvent) {
        self.state.lock().await.apply(ev);
        (self.redraw)();
    }
    async fn request_permission(&self, req: PermissionRequest) -> Permission {
        // open a modal, await user click via oneshot channel, return decision
    }
}

Capabilities a GUI gets to use

The FrontendCapabilities a GUI advertises (via the trait's capabilities() method) opens up content types the TUI cannot comfortably handle:

  • Inline images. Tools that produce images (screenshots, plots) can render them directly.
  • Rich diffs. The edit tool can emit a structured diff event the GUI renders side-by-side instead of as text.
  • Embedded resources. Same content-block types ACP supports; GUI displays them inline.

The system prompt builder reads these capabilities and adjusts what it tells the model is available, so a tool that produces an image can know whether the current frontend will actually show it.

Permission UX, GUI flavour

A modal dialog or a sidebar notification, with three buttons (allow, always-allow-this-tool, deny). Same trait method, native widget instead of a curses box or a JSON-RPC round-trip.

What we are explicitly not committing to

  • A specific UI toolkit. See Three viable paths.
  • A specific look. Theming and visual identity wait until we pick a stack.
  • Mobile. Out of scope. If a phone use-case appears, treat it as a separate adapter or a browser PWA against arnes-http.
  • Pixel-perfect parity with the TUI. The GUI gets to be different where different is better — richer media, side panels, drag-and-drop file attachments.

The adapter is done when

You launch a desktop app (or a browser tab pointed at arnes-serve), you see your existing JSONL sessions in a sidebar, you open one, you prompt, you watch a streamed reply with nicely-rendered tool calls and diffs, and a modal asks you to approve a destructive bash. Same harness, more pixels.
