Adapter

arnes-acp

The adapter that turns arnes into an Agent Client Protocol server: JSON-RPC over stdio, designed so any ACP-compatible editor (Zed today, others as the ecosystem grows) can drive an arnes session. This adapter is the reason the Host trait exists.

Built in lockstep with the TUI

arnes-acp is not built in one go after the TUI is finished. It grows alongside the TUI — both adapters land each capability at the same milestone (see the roadmap). The full method surface documented further down is where we end up; the table below shows when each piece arrives.

MilestoneWhat the ACP adapter gains
M1initialize, session/new, session/prompt, session/cancel, outbound session/update (text deltas only). Every outbound notification includes _meta.agent_id from M1 onward — V1 always emits "root"; reserved for sub-agent attribution post-V1.
M2tool_call variants on session/update + outbound fs/read_text_file
M3outbound session/request_permission, fs/write_text_file, terminal/*
M4–M5(no protocol-surface change — AGENTS.md and skills are internal to the system prompt)
M6session/load
M7(custom _meta on session/update for compaction notices — informative only)
M8same router mounted behind WebSocket once upstream ACP spec ships transport

The benefit of growing both adapters together: the Frontend trait stays honest. If a method only makes sense for the TUI, the ACP impl will struggle to implement it — that is the signal to rework the trait. With a single consumer, you cannot tell the difference between a generally-useful method and one that happens to suit the consumer you have.

The role reversal

In the TUI adapter, arnes owns the filesystem and the terminal — tools call tokio::fs directly via LocalHost. In ACP mode, the editor is the trusted party with the file buffers and the integrated terminal. arnes is a guest in someone else's house. Reads and writes round-trip back to the editor:

Bidirectional JSON-RPC. The editor calls into arnes; arnes calls back into the editor for any side effect.

Transport

V1: JSON-RPC 2.0 over stdio. The editor spawns arnes as a child process and exchanges newline-delimited JSON over stdin/stdout (the ACP convention). V2 (when the ACP spec lands HTTP/WS transport): we expose the same handler behind arnes-http with a small routing shim. Same handler code; different framing. 

// arnes-acp/src/transport/stdio.rs
pub async fn run_stdio(session: Session<AcpFrontend, AcpHost>) -> io::Result<()> {
    let stdin  = tokio::io::stdin();
    let stdout = tokio::io::stdout();
    let mut server = JsonRpcServer::new(stdin, stdout);
    server.handle_requests(make_router(session)).await
}

Bidirectionality matters. ACP is not request/response one way. The editor calls session/prompt and waits; meanwhile arnes calls back with fs/read_text_file requests over the same connection. The JSON-RPC library must support being both server and client on the same channel — this is why we picked jsonrpsee (with hand-rolled framing as the documented fallback) at M1.

Capability negotiation

During initialize the editor declares what it can do (file ops, terminal). arnes records these on the AcpHost. If a tool asks the host to do something the editor doesn't support, the host returns an error the tool surfaces as a tool-result error — same path as Chapter 4's "tool errors are tool results, not exceptions." 

pub struct AcpHost {
    client_caps: ClientCapabilities,
    rpc: Arc<BidirectionalRpc>,
}

#[async_trait]
impl Host for AcpHost {
    async fn read_text_file(&self, path: &Path) -> io::Result<String> {
        if !self.client_caps.fs.read_text_file {
            return Err(io::Error::new(io::ErrorKind::Unsupported,
                "client does not support fs/read_text_file"));
        }
        let resp: ReadTextFileResponse = self.rpc.call("fs/read_text_file", &ReadTextFileRequest {
            path: path.to_path_buf(),
            line: None, limit: None,
        }).await?;
        Ok(resp.content)
    }
    /* ... terminal_create, terminal_output, etc. ... */
}

Permission flow

Sensitive tools (the same set the TUI gates) hit Frontend::request_permission. In ACP mode, that issues a session/request_permission request to the editor and awaits the answer. The editor renders the prompt however it likes.

The flow is symmetric with the TUI's modal dialog — same trait, different rendering.

Content blocks: aligning vocabularies

arnes' internal content block enum should be a near-superset of ACP's. When we emit, we map our types to ACP's; when we receive a prompt, we map ACP's back to ours. The intersection is large:

Non-goals for the ACP adapter

  • No MCP bridging in V1. ACP allows clients to advertise MCP servers; bridging them through to our tool registry is a separate feature. Out of scope for first cut.
  • No custom protocol extensions. ACP supports underscore-prefixed custom methods. Don't use them — commit to the standard surface so any compatible editor works.
  • No editor-specific behaviour. If we need editor-specific polish, do it through the standard protocol surface or push for a capability addition upstream. No if (client == "zed").

The adapter is done when

Launching arnes-acp as a child of an ACP-compatible editor gives you a working coding agent: prompts flow in via session/prompt; the editor sees streaming session/updates; tool calls show up in the editor's UI; file writes land in the editor's buffers; bash commands run in the editor's terminal; the user approves sensitive actions through the editor's permission UI. The same arnes-core drives both this and the TUI — only the adapter wiring is different.
