Plan

Roadmap

Nine milestones, each one leaves you with something you can try. The organising principle: two frontends from day one — the TUI and the ACP adapter grow together so the harness has two independent consumers at every stage. Extensions and a few other niceties are explicitly deferred.

Two clients from day one

The temptation when bootstrapping is to build one frontend, make it nice, then bolt on a second later. We are not doing that. Every milestone after M1 lands a capability and surfaces it in both the TUI and the ACP adapter at the same time.

The reason is purely architectural hygiene. A single consumer of an abstraction always pulls the abstraction toward itself: you cannot tell the difference between a generally-useful method on the Frontend trait and a method that happens to suit the only caller you have. With two consumers — one rendering to a terminal, one speaking JSON-RPC to an editor — that signal stays loud. If a change is awkward for ACP, the trait is wrong.

The minimum-viable ACP surface at M1 is tiny: four methods plus one notification. Real method weight (fs/*, terminal/*, session/request_permission) lands exactly when the tools that need them land, which keeps M1 small enough to actually finish.

Phasing at a glance

Single milestone track. Each milestone lands a harness capability and surfaces it in both the TUI and ACP frontends.

M1 — agent-rig + minimal TUI + minimal ACP

Goal. Stand up the workspace and prove the two-frontend architecture works.

Scope. Cargo workspace. arnes-core with Frontend and Host trait definitions. A LocalHost impl. A Session wrapper around agent_rig::AgentRunner. Two adapters wired up:

arnes-tui at M1
  • ratatui + crossterm
  • An input box and a scrolling output pane — nothing else
  • Streams text deltas to the pane
arnes-acp at M1
  • JSON-RPC 2.0 over stdio
  • initialize, session/new, session/prompt, session/cancel
  • Outbound session/update with text chunks only
M1 JSON-RPC choice: ACP needs bidirectional dispatch on stdio — arnes must be able to send server-initiated requests back to the client (fs/*, terminal/*) over the same channel it serves on. We start with jsonrpsee; if its outbound-call ergonomics, cancellation integration, or _meta propagation become a fight during M1, we fall back to a hand-rolled ~350-line framer on tokio_util::codec::LinesCodec. Roll-your-own is the fallback, not the default. See M1 § JSON-RPC library for the fallback triggers.

End state

arnes streams a Gemini reply into a ratatui pane. Spawning arnes-acp as a child and piping JSON-RPC at it produces the same reply as session/update notifications. Same harness; two faces.

M2 — First tool (read)

Goal. Prove tool-calling end-to-end through both adapters.

Scope. The Tool trait, ToolRegistry, and the first built-in tool (read) all in arnes-core::tools, taking &dyn Host. Sequential execution.

arnes-tui at M2
  • Tool-call card appears in the transcript
  • Card updates: pending → running → done
  • Uses LocalHost (reads files locally)
arnes-acp at M2
  • session/update tool_call variants emitted
  • Outbound fs/read_text_file callback to the client
  • Uses AcpHost (reads files via the editor's buffers)

End state

In the TUI, "what's in my Cargo.toml?" results in a tool-call card and a typed reply. In the ACP harness, the client receives a tool_call update and a corresponding fs/read_text_file request — same agent loop, same model, two different Host impls.

M3 — Coding toolkit + permissions

Goal. Move from read-only to a real coding agent.

Scope. Three more built-in tools: write, edit (anchor-text), bash. Per-tool permission policies. The request_permission path on the Frontend trait wired through.

arnes-tui at M3
  • Modal dialog: allow / always-allow / deny
  • Esc cancels mid-tool
  • Bash output truncated and shown inline
arnes-acp at M3
  • Outbound session/request_permission
  • Outbound fs/write_text_file
  • Outbound terminal/create, output, wait_for_exit, kill, release

End state

Either frontend can drive a "rename foo to bar everywhere and run tests" task. The TUI shows modals; the ACP client receives session/request_permission requests. From here on, the protocol surface is stable enough that further milestones rarely add new ACP methods.

M4 — System prompt assembly

Goal. Stop hard-coding the prompt; assemble it from inputs.

Scope. SystemPromptBuilder. Tool snippets + per-tool guidelines slot. AGENTS.md tree walk. Cwd + date footer. Cache by input hash; rebuild only when inputs change. Frontend capabilities propagated.

This milestone is server-internal — no new ACP methods. Both adapters benefit equally; the proof is that the same prompt assembly produces useful behaviour in both the TUI and the ACP client.

End state

Run arnes in a Rust project and the prompt reflects the project's conventions from AGENTS.md. Run it in a Python project and the prompt rebuilds. Same in TUI and ACP modes.

M5 — Skills

Goal. Conditional knowledge without prompt bloat.

Scope. arnes-core::skills. SKILL.md discovery from global and project directories. YAML frontmatter parse. <available_skills> XML block in the system prompt. Skills only advertised when read is active.

TUI gets a /skill:<name> slash command for explicit invocation. ACP needs no new methods — skills surface through the system prompt and load themselves via the existing fs/read_text_file callback.

End state

Drop a SKILL.md in ~/.arnes/skills/<name>/. The agent advertises it on every turn for ~20 tokens; loads it via read only when a task matches. Works identically in both frontends.

M6 — Sessions on disk

Goal. Survive a restart.

Scope. arnes-core::persist. JSONL writer with header row + message rows + compaction rows. UUID v7 session ids. Project-scoped session directories under ~/.arnes/sessions/{project-hash}/. --continue, --resume <id>, --resume (picker) CLI flags.

arnes-tui at M6
  • arnes -c picks up most recent
  • Picker UI for --resume
arnes-acp at M6
  • session/load handler implemented
  • Resume returns the full content blocks to rehydrate the client's view

End state

Quit mid-task in either frontend, restart, resume the same session. The JSONL log is readable text on disk; you can cat it.

M7 — Compaction

Goal. Long sessions survive context exhaustion.

Scope. arnes-core::compact. Token estimation. Threshold trigger at the top of Session::prompt (only between turns). Structured-summary prompt. History rewrite preserving last K turns. JSONL Compaction row recorded; raw history retained.

TUI surfaces a one-line "compacted" notice and exposes a /compact command. ACP carries the same information via a custom _meta field on session/update — informative only; the client can render it however it likes.

End state

A multi-day session no longer hits a context wall. With M6 + M7, arnes is genuinely usable as a daily-driver agent through either frontend.

M8 — HTTP / WebSockets adapter

Goal. Make arnes networked.

Scope. arnes-http crate. axum server. /v1 REST routes (sessions CRUD, prompt, cancel, compact). /v1/sessions/{id}/ws streaming socket with arnes-native frame vocabulary. Bearer-token auth. CORS allow-list. SessionRegistry with per-session locking.

Once upstream ACP ships its HTTP/WS transport spec, we mount the same router that arnes-acp uses for stdio behind a WebSocket route. The handler code is transport-agnostic by design; only the framing changes.

End state

arnes-serve --bind 127.0.0.1:7878 --token $T stays up. A browser page or a script can drive a session over REST + WS. Multiple concurrent sessions per server. Foundation in place for ACP-over-WS.

M9 — GUI

Goal. The fourth face.

Scope. Pick one of the three paths from the GUI adapter page (Tauri, native, or web-on-HTTP). arnes-gui crate (or a separate frontend project with no new Rust if we pick web-on-HTTP). GuiFrontend with permission modal, transcript widget, input box. Rich diffs and inline images via FrontendCapabilities.

End state

A desktop or browser app you can use as your primary coding-agent UI. Same harness, more pixels.

Parallel workstream: testing infrastructure

The two-clients-from-day-one approach gives you interactive testing for free (any milestone is something you can do). Automated testing is a separate but cheap workstream:

PieceLandsPurpose
RecordingFrontend during M2 Mock Frontend impl in arnes-core/tests/ that captures every event for assertions.
InMemoryEnv during M2 Mock Host with a fake filesystem and a fake terminal — no real processes.
Scripted LLM during M3 An LlmModel impl for agent-rig that replays canned responses; deterministic loop testing without an API key.
ACP test client during M3 A tiny Rust integration test that spawns arnes-acp, drives the JSON-RPC dance, asserts on outbound requests. Replaces "a real editor" for ACP CI.

With this set in place, every subsequent milestone gets regression coverage on both adapters automatically.

Deferred

Things explicitly out of the V1 plan. The architecture accommodates them; we just don't build them now.

Designed for, not built. For sub-agents in particular, the V1 type system is sub-agent-aware (AgentId, per-(agent, model) usage, principal-aware permissions) so that landing the implementation post-V1 is mostly arnes-side configuration plus agent-rig AgentTool registration — not a protocol-surface refactor. See core.html § Future-compatibility: sub-agents for the design contract.
CapabilityWhy deferred
Sub-agents as first-class tools agent-rig already supports the mechanics (a Tool whose execute() runs a nested agent loop). What V1 doesn't ship: nested event propagation, per-agent permission scoping beyond Principal::Any, sub-agent rows in JSONL, GUI rendering of nested activity. The trait surface is sub-agent-ready from M1 — the implementation is the work-item, not the design.
Extensions The delivery mechanism in Rust (cdylib, sub-process IPC, embedded scripting) is a sub-design effort, and we have no concrete user need yet. The extensions module spec stays in the architecture for when we revisit.
MCP bridging in ACP ACP allows clients to advertise MCP servers; bridging them into our tool registry is its own feature. Add after the core ACP surface is stable in production.
Multi-tenant HTTP isolation V1 HTTP server assumes single trust boundary. Sandboxing or remote workers come up only when there is a multi-tenant deployment to design against.
Inline images in the TUI Useful but a big native-protocol yak (Kitty/iTerm2). The GUI gets images for free at M9.
Branching sessions The JSONL format carries id and parent_id from M6 so this can land later without a format break, but we don't expose branching UX in V1.

What success looks like, day by day

  • Morning. arnes -c picks up yesterday's session. You spend two hours; arnes does most of the typing.
  • Midday. You switch to your editor. The editor talks to arnes-acp running as a child; same session, same model, same skills, same JSONL log.
  • Afternoon. You push the morning's branch to CI. A GitHub action posts to arnes-serve over HTTP: "summarize the changes in this PR." arnes reads the diff, returns a paragraph.
  • Evening. Same browser tab pointed at the same arnes-serve — a GUI session from the couch. The harness has no idea which mouth is speaking, and that is the entire point of the architecture.
