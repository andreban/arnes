Milestone 3 · Coding toolkit

write, edit, bash + permissions

The transition from "agent that can read your code" to "agent that can change it." Three new tools, a permission model that goes through the Frontend trait, and the full set of ACP outbound callbacks (fs/write_text_file, terminal/*, session/request_permission).

Why these three, why now

The toolkit chosen mirrors the book (Chapter 4) and pi's defaults. These three together give the model enough leverage to do real work: write for new files and complete rewrites, edit for surgical changes, bash for everything else. After M3 the ACP protocol surface is essentially complete; subsequent milestones rarely add methods.

Permission model

Permission decisions cannot be coarse. Approving "write" once for a session approves writes to anything — too much trust. Approving "bash" on the binary alone means cargo test and cargo publish get the same blanket approval — worse. The right unit is a tool-defined scope pattern: a path glob for filesystem tools, a command pattern for bash. The tool builds a menu of candidate patterns the user can pick; the session remembers the picks for future calls that match.

Tool trait additions

pub trait Tool: Send + Sync {
    // ... M2 methods ...

    /// False for read-only tools (read, ls, grep): they never hit the modal.
    fn permission_required(&self) -> bool { false }

    /// For each call that requires permission, build a summary and a menu
    /// of scope options the user can pick to "always allow" similar calls.
    fn build_permission_request(&self, input: &Value) -> PermissionRequest;

    /// For a previously-approved scope, decide whether THIS call falls
    /// within it. Only called when the allowlist has an entry for this tool.
    fn matches_scope(&self, scope: &Scope, input: &Value) -> bool;

    /// The widest persistence scope an "always allow" decision for this
    /// tool can be trusted at. Observation-only tools can permit Global;
    /// mutating tools cap at Workspace. The frontend uses this to hide
    /// persistence options the tool doesn't endorse.
    fn max_persistence(&self) -> Persistence { Persistence::Session }
}

Types

pub struct PermissionRequest {
    pub summary: String,           // "Run: cargo test --lib"
    pub input:   Value,            // raw arguments (for UI redisplay)
    pub scopes:  Vec<ScopeOption>, // ordered narrowest-first
}

pub struct ScopeOption {
    pub label: String,             // shown in the modal: "any cargo command"
    pub scope: Scope,              // opaque to the UI; tool-defined
}

pub enum Scope {
    JustThis,                                              // allow once, no entry
    PathGlob       { glob: String },                       // write / edit
    Command        { command: String },                    // bash exact match
    CommandPattern { pattern: String },                    // bash glob
    Custom         { tool_data: serde_json::Value },       // future tools
}

pub enum Persistence {
    Session,    // in-memory only; resets when the session ends
    Workspace,  // ~/.arnes/permissions/{project-hash}.toml
    Global,     // ~/.arnes/permissions/global.toml (read-only tools only)
}

pub enum Permission {
    AllowOnce,
    AllowAlways { scope: Scope, persistence: Persistence }, // append to the matching store
    Deny,
}

Allowlist and persistence

The allowlist holds AllowEntry structs (not bare tuples) partitioned by persistence level. Each entry carries a principal field reserved for future per-agent scoping — V1 only ever stores Principal::Any, but the field exists so post-V1 sub-agents can be approved separately without a breaking change to the allowlist. 

pub struct AllowEntry {
    pub tool_name: String,
    pub scope:     Scope,
    pub principal: Principal,    // V1: always Any
}

pub enum Principal {
    Any,                         // V1 default: applies to whatever agent calls the tool
    Root,                        // root agent only (post-V1)
    SubAgent { spec: String },   // a named sub-agent kind (post-V1)
}

pub struct PermissionAllowlist {
    // Loaded at session start: global + workspace. The session layer
    // appends Session entries in-memory only.
    session:   Vec<AllowEntry>,
    workspace: Vec<AllowEntry>,
    global:    Vec<AllowEntry>,
}

impl PermissionAllowlist {
    pub fn allows(&self, tool: &dyn Tool, agent: &AgentId, input: &Value) -> bool {
        self.iter_all().any(|e|
            e.tool_name == tool.name()
            && e.principal.matches(agent)              // V1: Any matches everything
            && tool.matches_scope(&e.scope, input))
    }
    pub fn add(&mut self, entry: AllowEntry, level: Persistence) {
        match level {
            Persistence::Session   => self.session.push(entry),
            Persistence::Workspace => self.workspace.push(entry),    // V2: also writes to disk
            Persistence::Global    => self.global.push(entry),       // V3: also writes to disk
        }
    }
}

The agent argument to allows() is the AgentId of the caller. V1 always passes AgentId::Root; Principal::Any matches anything; no observable behavior change. Post-V1 the same code path handles per-agent scoping by introducing other Principal variants — no refactor of the call sites.

Toolmax_persistence()Rationale

Rollout

PhaseWhat lands
V1 (M3) Session persistence only. Persistence::Workspace and Global are valid enum variants and the trait method exists; PermissionAllowlist::add for those levels is in-memory and a no-op on shutdown. Frontends show only the "session" persistence option.
V2 (post-M3) Workspace persistence. ~/.arnes/permissions/{project-hash}.toml — the same project-hash used by sessions in M6, so loading is mechanical at Session construction. Frontends gain the "workspace" option.
V3 (small follow-up) Global persistence. ~/.arnes/permissions/global.toml. Frontends gain the "global" option, but only when tool.max_persistence() == Global. Mutating tools never offer it.

What each gated tool builds

write — call: {path: "src/main.rs", content: "..."}

impl Tool for WriteTool {
    fn permission_required(&self) -> bool { true }
    fn max_persistence(&self) -> Persistence { Persistence::Workspace }

    fn build_permission_request(&self, input: &Value) -> PermissionRequest {
        let path = input["path"].as_str().unwrap_or("<invalid>").to_string();
        let parent = parent_dir(&path);                 // "src"
        let ext    = extension(&path);                  // "rs"
        PermissionRequest {
            summary: format!("Write {path}"),
            input:   input.clone(),
            scopes: vec![
                ScopeOption { label: "this file".into(),
                              scope: Scope::PathGlob { glob: path.clone() } },
                ScopeOption { label: format!("anything in {parent}/"),
                              scope: Scope::PathGlob { glob: format!("{parent}/**") } },
                ScopeOption { label: format!("any *.{ext} file"),
                              scope: Scope::PathGlob { glob: format!("**/*.{ext}") } },
            ],
        }
    }

    fn matches_scope(&self, scope: &Scope, input: &Value) -> bool {
        let path = input["path"].as_str().unwrap_or("");
        match scope {
            Scope::PathGlob { glob } => glob_matches(glob, path),
            _ => false,
        }
    }
}

edit uses the same scope shape as write — the operation is path-scoped; the individual edit ops don't carry separate permission semantics.

bash — call: {command: "cargo test --lib"}

impl Tool for BashTool {
    fn permission_required(&self) -> bool { true }
    fn max_persistence(&self) -> Persistence { Persistence::Workspace }

    fn build_permission_request(&self, input: &Value) -> PermissionRequest {
        let cmd: String = input["command"].as_str().unwrap_or("").to_string();
        let parts: Vec<&str> = cmd.split_whitespace().collect();
        let mut scopes = vec![
            ScopeOption { label: "this exact command".into(),
                          scope: Scope::Command { command: cmd.clone() } },
        ];
        // Propose patterns at each prefix depth: "cargo test *", "cargo *", ...
        for depth in (1..=parts.len().min(3)).rev() {
            let prefix = parts[..depth].join(" ");
            scopes.push(ScopeOption {
                label: format!("any '{prefix} ...'"),
                scope: Scope::CommandPattern { pattern: format!("{prefix} *") },
            });
        }
        PermissionRequest { summary: format!("Run: {cmd}"), input: input.clone(), scopes }
    }

    fn matches_scope(&self, scope: &Scope, input: &Value) -> bool {
        let cmd = input["command"].as_str().unwrap_or("");
        match scope {
            Scope::Command { command }        => command == cmd,
            Scope::CommandPattern { pattern } => cmd_glob_matches(pattern, cmd),
            _ => false,
        }
    }
}

read, future ls, future grep: permission_required() returns false. They never reach the modal.

Matchers. Use globset for path globs; write a tiny custom matcher for bash command patterns (~30 lines: split on whitespace, treat * as "match the rest"). Two different matchers because the syntax expectations are different — reusing a path-glob engine for command lines confuses users who expect shell-style semantics.

The three tools

write

#[derive(serde::Deserialize, schemars::JsonSchema)]
struct WriteInput {
    path: String,
    content: String,
}

#[async_trait]
impl Tool for WriteTool {
    fn name(&self) -> &str { "write" }
    fn description(&self) -> &str {
        "Create a new file or completely overwrite an existing one. \
         Use only for new files or complete rewrites. For surgical \
         changes to existing files, use the edit tool instead."
    }
    // permission_required + build_permission_request + matches_scope
    // are shown in the Permission model section above.

    async fn execute(&self, input: serde_json::Value, cx: &ToolContext) -> ToolResult {
        let WriteInput { path, content } = serde_json::from_value(input)?;
        match cx.host.write_text_file(Path::new(&path), &content).await {
            Ok(()) => ToolResult::ok(format!("wrote {} bytes to {}", content.len(), path)),
            Err(e) => ToolResult::error(format!("write failed: {e}")),
        }
    }
}

edit

Anchor-text edits. The model supplies {oldText, newText} pairs; the harness applies them only when oldText matches exactly once in the file. All-or-nothing semantics: any edit failing rolls back the lot. 

#[derive(serde::Deserialize, schemars::JsonSchema)]
struct EditInput {
    path: String,
    edits: Vec<EditOp>,
}

#[derive(serde::Deserialize, schemars::JsonSchema)]
struct EditOp { old_text: String, new_text: String }

async fn execute(&self, input: serde_json::Value, cx: &ToolContext) -> ToolResult {
    let EditInput { path, edits } = serde_json::from_value(input)?;
    let mut text = match cx.host.read_text_file(Path::new(&path)).await {
        Ok(t) => t, Err(e) => return ToolResult::error(e.to_string()),
    };
    for (i, EditOp { old_text, new_text }) in edits.iter().enumerate() {
        let count = text.matches(old_text.as_str()).count();
        if count == 0 { return ToolResult::error(format!("edit {i}: oldText not found")); }
        if count > 1  { return ToolResult::error(format!("edit {i}: oldText matched {count} times; be more specific")); }
        text = text.replacen(old_text, new_text, 1);
    }
    match cx.host.write_text_file(Path::new(&path), &text).await {
        Ok(()) => ToolResult::ok(format!("applied {} edit(s) to {path}", edits.len())),
        Err(e) => ToolResult::error(e.to_string()),
    }
}

bash

Runs a command through the Host's terminal interface. Capped output, hard timeout, exit code reported. In ACP mode this goes through the editor's integrated terminal; in TUI mode it spawns locally. 

#[derive(serde::Deserialize, schemars::JsonSchema)]
struct BashInput {
    command: String,
    #[serde(default = "default_timeout")]
    timeout_seconds: u32,
}
fn default_timeout() -> u32 { 120 }

async fn execute(&self, input: serde_json::Value, cx: &ToolContext) -> ToolResult {
    let BashInput { command, timeout_seconds } = serde_json::from_value(input)?;
    let handle = cx.host.terminal_create(TerminalSpec::shell(&command)).await?;
    let _ = tokio::time::timeout(
        Duration::from_secs(timeout_seconds as u64),
        cx.host.terminal_wait(&handle),
    ).await;
    let snap = cx.host.terminal_output(&handle).await?;
    cx.host.terminal_release(handle).await.ok();
    let body = truncate(snap.combined_output, 1000_lines_or_200kb);
    ToolResult::ok(format!("exit {}\n{body}", snap.exit_code.unwrap_or(-1)))
}

Host, fully implemented

LocalHost
  • write_text_file: tokio::fs::write after create_dir_all on parent.
  • terminal_create: spawn bash -c via tokio::process::Command; keep handle in HashMap<TerminalHandle, Child>.
  • terminal_output: read accumulated stdout+stderr from background tasks.
  • terminal_wait: child.wait().await.
  • terminal_kill: child.kill().await.
AcpHost
  • write_text_file: outbound fs/write_text_file; editor lands changes in its buffer/diff view.
  • terminal_create: outbound terminal/create; receive a handle.
  • terminal_output, terminal_wait, terminal_kill, terminal_release: thin RPC pass-throughs.
  • Each method short-circuits with Unsupported if the client didn't advertise the capability.

What the frontends do

TUI at M3
  • Permission modal — floating box showing the tool summary, the raw input preview, and a menu of choices: Allow once, then one row per ScopeOption (e.g. "Always: this file", "Always: anything in src/", "Always: any *.rs file"), each row carrying a persistence selector limited by tool.max_persistence() (V1: only session; V2 adds workspace; V3 adds global for read-only tools). Final row is Deny. Arrow keys + Enter to pick; Tab cycles persistence on a highlighted row.
  • Esc cancels mid-tool: harness aborts the agent run, the child process (or in-flight RPC) gets a cancel signal.
  • Tool-call cards expand to show output preview on success; full error on failure.
  • Slash command: /tools lists active tools and their policies.
  • Status line shows cumulative token usage and context-window position: 12.3k tokens · 12.3k/200k. Narrow terminals collapse to 12.3k/200k. Cost calculation is out of scope for V1 — whoever cares about money multiplies tokens by their own rate table.
ACP at M3
  • Outbound session/request_permission issued before each gated tool. Map our (ScopeOption × allowed persistence levels) matrix to ACP's RequestPermissionOptions: one option per (scope, persistence) pair, plus Allow once and Deny. The editor surfaces these as its own UI; the selected optionId tells us whether to allow once, allow always with which (scope, persistence), or deny. tool.max_persistence() bounds which pairs we emit.
  • Outbound fs/write_text_file for write and indirectly via edit.
  • Outbound terminal/create, terminal/output, terminal/wait_for_exit, terminal/kill, terminal/release for bash.
  • If the client's capabilities did not advertise terminal, bash is not even registered as a tool for this session — the system prompt won't mention it.

Cancellation, end to end

Cancellation now matters because tools may take seconds or minutes. Session holds a CancellationToken; cancelling it:

  1. Causes the agent-rig stream to terminate at the next yield point.
  2. Triggers each in-flight tool's execute future to be dropped (Rust async drop cleans up the spawned child, the in-flight RPC, etc.).
  3. For bash, host.terminal_kill(handle) on cancel ensures the OS process actually dies.
  4. Emits a SessionEvent::Error { message: "cancelled" } for the frontends to render appropriately.

Implementation tasks

  1. Extend Tool with permission_required(), build_permission_request(), matches_scope(), and max_persistence(). Define PermissionRequest, ScopeOption, Scope, Persistence, Permission in arnes-core::frontend.
  2. Add PermissionAllowlist on Session with three lanes (session/workspace/global); consult all three in Session::prompt before each gated tool call; append to the session lane on AllowAlways for V1. Workspace/global add disk reads/writes in V2/V3.
  3. Add a tiny cmd_glob_matches helper (whitespace tokens, * wildcard) and a glob_matches wrapper over globset::Glob.
  4. Implement write_text_file, terminal_* on both LocalHost and AcpHost.
  5. Add three tools to arnes-core::tools: write, edit, bash.
  6. Update Session::prompt: consult policy & cache; emit SessionEvent::ToolCall*; pump cancellation through.
  7. TUI: permission modal component; Esc cancellation; tool-card output preview; /tools slash command.
  8. ACP: outbound session/request_permission; map outcome to Permission enum.
  9. ACP capability gating: omit unsupported tools from the registry at session start.

Testing checklist

  • Unit: each tool against InMemoryEnv. Bash needs an InMemoryEnv extension that records spawned commands and returns canned exit codes/output.
  • Edit: zero-match, multi-match, multi-edit, edits-that-reference-prior-edit-output. All-or-nothing rollback verified.
  • Permission flow: scripted LLM emits a bash tool_use; RecordingFrontend returns Deny; verify the harness emits a synthetic ToolResult::error("user denied") instead of executing.
  • Scope matching: the user approves AllowAlways(CommandPattern "cargo *") for the first cargo test. The next call (cargo build) skips the modal. A subsequent npm install still prompts.
  • Glob correctness: PathGlob "src/**" matches src/main.rs and src/a/b.rs but not tests/main.rs. Exhaustive table of cases covered.
  • Cancellation: kick off a long-running bash via scripted LLM; cancel mid-flight; assert child process dies and a cancelled event surfaces.
  • ACP golden: a scenario where the client serves fs/write_text_file, denies a permission, approves the next. Assert outbound message sequence.

Risks specific to M3

  • Process leaks on cancel. If the bash tool is dropped before terminal_release, the child may persist. Use a guard struct on the handle to enforce release-on-drop.
  • Permission UX in ACP without an editor. Hand-written ACP test clients may not implement request_permission. Provide a CLI flag --auto-allow-once for headless testing (every prompt resolves to AllowOnce; nothing is added to the allowlist); document loudly that production must not use it.
  • Scope-option overload. A bash call like cargo test --workspace --all-features -- --nocapture could generate eight prefix scopes. Cap at three (exact + two prefix depths) and pick depths by token usefulness, not raw count.
  • Glob expressiveness vs surprise. A user picking "any *.rs file" from a write call in src/ probably doesn't realize they just approved writes to tests/foo.rs and vendor/leftpad.rs. Label scopes literally ("any *.rs file" not "Rust files"); document this in user-facing docs when those exist.
  • Edit ambiguity. Models will sometimes send oldText that legitimately appears multiple times in repetitive code. The "matched N times" error guides them to widen context; verify the error message is good.
  • Output truncation correctness. Truncating mid-UTF-8 sequence corrupts output. Truncate on grapheme boundaries; tested by a Unicode-heavy fixture.

End state of M3

"Rename foo to bar everywhere and run the tests" works in both adapters. TUI users see permission modals; ACP clients see session/request_permission requests. Bash commands run locally for TUI, in the editor's integrated terminal for ACP. With M1–M3 done, arnes is functionally a coding agent — M4 onward is about making it pleasant, durable, and aware of its context.
