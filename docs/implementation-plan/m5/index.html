Milestone 5 · Conditional knowledge

Skills

On-demand instruction packs. Markdown files the model knows exist via a short signpost in the system prompt; loads the full body only when the task at hand matches. Small, self-contained — the right next milestone after the prompt builder lands.

Why M5, why now

Skills only make sense once the system prompt is composable (M4) and the read tool is wired (M2). With both in place, M5 is mostly filesystem-walking and YAML parsing. No ACP surface change, no new SessionEvent variant — the model loads skills using the same read tool we already shipped.

arnes-core::skills

// arnes-core/src/skills.rs

pub struct Skill {
    pub name: String,
    pub description: String,
    pub file_path: PathBuf,
    pub disable_model_invocation: bool,   // user opted out of auto-load
}

pub struct SkillsCatalog {
    pub skills: Vec<Skill>,
    pub diagnostics: Vec<SkillDiagnostic>,
}

impl SkillsCatalog {
    pub async fn discover(host: &dyn Host, roots: &[PathBuf]) -> Self;
    pub fn format_for_prompt(&self) -> String;   // the <available_skills> block
    pub fn find(&self, name: &str) -> Option<&Skill>;
}

Skill file format

A directory containing a SKILL.md file. The frontmatter is YAML; the body is markdown the model will follow once loaded. 

~/.arnes/skills/postgres-migrations/
├── SKILL.md
├── template.up.sql
└── template.down.sql

# SKILL.md:
---
name: postgres-migrations
description: |
  Write a new database migration for the project's Postgres schema. Use
  when the user wants to add/alter/drop tables, columns, indices, or
  constraints. Covers naming, the directory layout, and backfills for
  NOT NULL columns on large tables.
disable-model-invocation: false   # optional; default false
---

# Postgres migrations

This project uses [tool] migrations. Every migration is two files:

1. `migrations/{uuid}_short_name.up.sql`
2. `migrations/{uuid}_short_name.down.sql`

Discovery

Scan known roots; for each directory under each root, check for SKILL.md; parse frontmatter; collect. Roots are:

RootSource
~/.arnes/skills/global
.arnes/skills/project-local (relative to cwd)
Contributed pathsextensions (deferred — nothing contributes at M5)

Same as AGENTS.md discovery (M4), the harness uses the Host for filesystem access — so in ACP mode the editor sees the read traffic too. 

pub async fn discover(host: &dyn Host, roots: &[PathBuf]) -> SkillsCatalog {
    let mut skills = Vec::new();
    let mut diagnostics = Vec::new();

    for root in roots {
        for dir in host.list_dir(root).await.unwrap_or_default() {
            if !dir.is_dir { continue; }
            let path = dir.path.join("SKILL.md");
            match host.read_text_file(&path).await {
                Ok(text) => match parse_frontmatter(&text) {
                    Ok((meta, _body)) => skills.push(Skill {
                        name: clamp(&meta.name, 64),
                        description: clamp(&meta.description, 1024),
                        file_path: path,
                        disable_model_invocation: meta.disable_model_invocation,
                    }),
                    Err(e) => diagnostics.push(SkillDiagnostic::parse(path, e)),
                },
                Err(_) => {} // no SKILL.md, not a skill directory
            }
        }
    }

    SkillsCatalog { skills, diagnostics }
}

list_dir is a new Host method added at M5. Both impls are short: LocalHost uses tokio::fs::read_dir; AcpHost needs a tiny custom helper since ACP does not currently have a fs/list_dir method — in the meantime we fall back to a host-side enumeration using the actual local filesystem (ACP servers run with full OS access to their own home directory; only the project filesystem is delegated).

Edge case worth knowing. ACP's fs/* methods are about the project's working tree, where the editor owns the source of truth. The user's global skill directory at ~/.arnes/skills/ is the harness's own filesystem — we read it locally even in ACP mode. Project-local skills under .arnes/skills/ in the editor's project are a grey area; for V1, prefer local read with a warning, and revisit once ACP gains fs/list_dir.

The prompt section

Skills surface to the model as an XML block at the end of the system prompt, after <project_context> but before the date/cwd footer: 

The following skills provide specialized instructions for specific tasks.
Use the read tool to load a skill's file when the task matches its description.
When a skill file references a relative path, resolve it against the skill's
directory and use that absolute path in tool commands.

<available_skills>
  <skill>
    <name>postgres-migrations</name>
    <description>Write a new database migration...</description>
    <location>/home/me/.arnes/skills/postgres-migrations/SKILL.md</location>
  </skill>
  ...
</available_skills>

SystemPromptBuilder::build() gains an optional skills argument. Skills only surface when the read tool is active — otherwise the signposts point at something the model cannot follow. disable_model_invocation-tagged skills are filtered out of the auto-advertised list and can only be invoked manually.

/skill slash command (TUI)

User-driven skill invocation. The TUI parses /skill:<name> as an input prefix; on submit it:

  1. Looks up the named skill in the catalog.
  2. Reads the SKILL.md body via the Host.
  3. Injects a synthetic user message before the actual user input: "The following are instructions for the <name> skill the user explicitly invoked. Follow them when carrying out the next request."
  4. Sends the rest of the user input as the actual prompt.

ACP equivalent for editors that want it: a session/set_mode call where the mode name is skill:<name>. The harness treats the same way — loads the body, injects the synthetic message at the start of the next turn. This is a no-protocol-change way to surface the feature.

Frontmatter parsing

FieldTypeRequiredNotes
namestringyesclamped to 64 chars
descriptionstringyesclamped to 1024 chars; normalized whitespace
disable-model-invocationboolnodefault false
license, tags, etc.anynoignored at V1; preserved for future

Use the serde_yaml crate. Frontmatter delimited by --- at start and end; reject files where the first line is not ---.

Implementation tasks

  1. Add list_dir to Host trait + both impls. LocalHost: tokio::fs::read_dir. AcpHost: stub (panic) for now and call the global-only host-side helper directly from SkillsCatalog::discover.
  2. Create arnes-core::skills with Skill, SkillsCatalog, SkillDiagnostic.
  3. Write the frontmatter parser; reject malformed input with friendly error messages.
  4. Extend SystemPromptBuilder::build to take a skills argument and emit the <available_skills> block when (a) skills present and (b) read tool active.
  5. Wire Session::new to discover skills at session start and store in SkillsCatalog on the session.
  6. TUI: parse /skill:<name> prefix; inject synthetic message. Add /skills command to list loaded skills.
  7. ACP: map session/set_mode with skill:* names to the same injection path.
  8. /reload command (M4) now re-runs skills discovery too.

Testing checklist

  • Frontmatter parser: happy path, missing required field, malformed YAML, body without frontmatter, frontmatter without body.
  • Discovery: InMemoryEnv populated with several skill dirs (one valid, one missing description, one not a directory); assert the valid ones land in the catalog and the rest become diagnostics.
  • Prompt section: snapshot test of the <available_skills> block; assert no section emitted when read tool is inactive.
  • Slash command: scripted LLM that asserts the synthetic message arrives at position 1 in the turn's history.
  • ACP smoke: set_mode with a skill name; verify same injection happens.

Risks specific to M5

  • Skill discoverability vs prompt bloat. Twenty 200-character descriptions is ~4000 characters of prompt overhead before any work happens. Cap the catalog size or let users disable skills they don't want. Add a --skill CLI flag to enable a specific subset.
  • ACP gap on directory listing. The host-side workaround for global skills is fine; for project-local skills, document the limitation and revisit when upstream adds the method.
  • Skill quality drives behaviour. A vague description means the model never loads the skill. Document this prominently in the user-facing docs (out of scope for the V1 plan but should appear in the documentation workstream).

End state of M5

Drop a SKILL.md in ~/.arnes/skills/<name>/; next session it appears in the catalog. Ask a task that matches the description; the model calls read on the skill's location and follows it. Type /skill:<name> in the TUI (or session/set_mode skill:<name> in ACP) to force load. Same behaviour in both frontends; no ACP protocol surface change.
