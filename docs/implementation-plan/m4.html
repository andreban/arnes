Milestone 4 · Context

System prompt assembly + AGENTS.md

Stop hard-coding the system prompt. Build it from slots: tool snippets, per-tool guidelines, project context files, working directory, date. Same harness behaves like a focused coding assistant in any project, in either frontend, without code changes.

Why this milestone now

Through M1–M3 we've been getting away with a one-line system prompt. It works in toy scenarios; it falls apart the moment a project has any conventions of its own. M4 is what turns the harness from a chat application that runs tools into an agent that belongs in your project.

M4 is server-internal: no new SessionEvent variants, no new ACP methods. The proof is behavioural — same assembly produces context-appropriate behaviour in both adapters.

Tool trait extensions

pub trait Tool: Send + Sync {
    // ... M2/M3 methods ...

    /// One-line entry for "Available tools" section.
    fn prompt_snippet(&self) -> Cow<'_, str> {
        // default: first line of description()
        first_line(self.description()).into()
    }

    /// Per-tool guideline bullets injected into the "Guidelines" section.
    /// Each bullet must name the tool explicitly (avoid "this tool ...").
    fn prompt_guidelines(&self) -> &[String] { &[] }
}

Update the three M3 tools to carry their own guidelines:

  • read: "Use read to examine files instead of cat or sed."
  • write: "Use write only for new files or complete rewrites."
  • edit: "Use edit for precise changes (oldText must match exactly).", "Each oldText is matched against the original file, not after earlier edits are applied. Merge nearby edits."
  • bash: "Use bash to run shell commands; do not chain destructive commands without intent."

AGENTS.md discovery

Walk from cwd upward toward the root, plus a global location. Read any file named AGENTS.md or CLAUDE.md. Wrap each in <project_instructions path="..."> tags inside the assembled prompt. 

pub async fn discover_context_files(cwd: &Path) -> Vec<ContextFile> {
    const NAMES: &[&str] = &["AGENTS.md", "CLAUDE.md"];
    let mut out = Vec::new();

    // 1. Walk up from cwd to root (or to a .git ancestor, whichever first).
    let mut dir = cwd.to_path_buf();
    loop {
        for name in NAMES {
            let p = dir.join(name);
            if let Ok(content) = tokio::fs::read_to_string(&p).await {
                out.push(ContextFile { path: p, content });
            }
        }
        if !dir.pop() { break; }
    }

    // 2. Global.
    if let Some(home) = dirs::home_dir() {
        let p = home.join(".arnes").join("AGENTS.md");
        if let Ok(content) = tokio::fs::read_to_string(&p).await {
            out.push(ContextFile { path: p, content });
        }
    }

    out.reverse();   // global first, then root-ward project, then cwd-local
    out
}

AGENTS.md in ACP mode

In ACP mode, the harness still reads AGENTS.md via the Host — not directly. That means AcpHost::read_text_file issues fs/read_text_file callbacks for each candidate path during context discovery. Editors get to see the agent looking up its context just like any other read.

Discovery in ACP mode also happens at session start, before the first user prompt — not lazily. This means the initial prompt the editor observes already has the project context in it.

Caching the assembled prompt

Provider-side prompt caching rewards stable prefixes; we should not rebuild the prompt on every turn. The cache key is the structural hash of the inputs: 

fn cache_key(tools: &[Arc<dyn Tool>], context_files: &[ContextFile], cwd: &Path) -> u64 {
    let mut h = DefaultHasher::new();
    for t in tools { t.name().hash(&mut h); t.prompt_snippet().hash(&mut h); /* etc */ }
    for f in context_files { f.path.hash(&mut h); f.content.hash(&mut h); }
    cwd.hash(&mut h);
    h.finish()
}

Session holds the last (cache_key, prompt); rebuilds only on miss. Triggers for invalidation: tool registry mutated (rare in V1; common once extensions land), context files changed (manual via /reload slash command), explicit SystemPromptBuilder setter changed.

Reload mechanism

Add a /reload slash command (TUI) and an internal Session::reload_resources() method (called via session/set_mode with a known mode in ACP, or via the future HTTP POST .../reload endpoint). Reload:

  1. Re-discovers context files.
  2. Re-reads the tool registry (no-op in V1; meaningful once extensions land).
  3. Invalidates the prompt cache key.
  4. Emits a SessionEvent the frontend can render as "context refreshed."

Implementation tasks

  1. Create arnes-core::prompt with SystemPromptBuilder, ContextFile, and the cache key function.
  2. Extend Tool with prompt_snippet() and prompt_guidelines(); update the four existing tools.
  3. Implement discover_context_files using the Host (not direct fs).
  4. Wire Session::new to take an optional SystemPromptBuilder; otherwise use a sensible default builder.
  5. In Session::prompt, rebuild the system prompt if the cache key changed; pass it to AgentRunner via agent-rig's Agent::builder().instructions(...).
  6. Implement Session::reload_resources(); add /reload TUI command; map ACP mode change appropriately.
  7. Surface FrontendCapabilities::markdown hint and have the TUI start rendering basic markdown (bold, code, lists) — full renderer can wait.

Testing checklist

  • Golden prompt: a deterministic fixture (fixed tools, fixed context files, fixed cwd, frozen date) produces a known string. Snapshot the output; diff on changes.
  • Cache: assert the prompt is rebuilt only when an input changes; identical inputs return the cached string.
  • Discovery: InMemoryEnv populated with AGENTS.md at three nesting levels; assert all three appear in the assembled prompt with correct path tags.
  • Behavioural smoke (TUI): run two sessions in two real projects with different AGENTS.md; verify the model's first-turn behaviour reflects each.
  • Behavioural smoke (ACP): same, via a hand-written ACP test client that stubs fs/read_text_file with fake AGENTS.md content.

Risks specific to M4

  • Prompt bloat. Some projects have long AGENTS.md files. The full assembled prompt may grow past a few thousand tokens; that hurts cost and may degrade attention. No mitigation in V1 — M5 (skills) and M7 (compaction) address it from different angles.
  • Tree-walk performance in deep projects. Negligible in practice (file system stat is cheap), but a project mounted on a network filesystem could surprise us. Cap the walk depth at 50 to be safe.
  • ACP read storms. Discovery may issue many fs/read_text_file calls in quick succession. Editors are designed for this; still, batch where the protocol allows once the spec adds a multi-read.

End state of M4

Run arnes in two different projects without changing any flags or config; the model picks up each project's conventions from its AGENTS.md. The same behaviour appears whether you are driving through the TUI or through an ACP client. From M4 forward, the harness has a context-appropriate posture in every session it joins.
