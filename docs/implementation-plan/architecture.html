Architecture

Modular design

Hexagonal architecture, two key traits, a Cargo workspace of small crates. The point of the design is to make adding a new frontend feel like adding a fifth side to the hexagon, not like rewriting the harness.

Two traits do most of the work

Every architectural decision in arnes flows from two abstractions. The first lets multiple frontends drive the same harness; the second lets the same tools work whether they run on the local OS or inside an editor's sandbox.

Frontend

What a "client" of arnes implements. Receives streaming SessionEvents; provides user input; handles permission prompts. The TUI implements it. ACP implements it. HTTP/WS implements it. GUI implements it. arnes-core never knows which.

Host

What tools call instead of touching the OS directly. Reads files, writes files, runs commands. LocalHost calls tokio::fs / tokio::process; AcpHost proxies through the ACP client. Tools never know which.

The Frontend trait

Driving the harness from a frontend is, at heart, a stream consumer plus an occasional callback. We model it as: 

// arnes-core/src/frontend.rs

pub trait Frontend: Send + Sync {
    /// Forward an event from the agent loop to the UI.
    /// Implementations: paint a TUI line, send an ACP session/update,
    /// push a WS frame, etc.
    async fn on_event(&self, event: SessionEvent);

    /// Ask the user to approve a sensitive action (destructive bash,
    /// arbitrary write, etc.). Block until they answer.
    async fn request_permission(&self, req: PermissionRequest) -> Permission;

    /// Optional capabilities the frontend advertises (e.g. "I can render
    /// markdown", "I can show images"). The system prompt builder consults
    /// these.
    fn capabilities(&self) -> FrontendCapabilities {
        FrontendCapabilities::default()
    }
}

Notice what is not on this trait. There is no render(state); the frontend is push-driven by events, not pull-driven by a snapshot. There is no read_user_input(); user input arrives as a method call into the session (session.prompt(text)), not pulled from the frontend. This inversion is what makes the same core drive a synchronous TUI loop and a JSON-RPC stdio handler with no glue code.

The Host trait

ACP's design forces the issue, but the abstraction pays off everywhere: testable tools, sandboxed tools, remote tools. Same surface area as the ACP fs/* and terminal/* methods: 

// arnes-core/src/host.rs

pub trait Host: Send + Sync {
    async fn read_text_file(&self, path: &Path) -> io::Result<String>;
    async fn write_text_file(&self, path: &Path, content: &str) -> io::Result<()>;
    async fn list_dir(&self, path: &Path) -> io::Result<Vec<DirEntry>>;

    async fn terminal_create(&self, cmd: TerminalSpec) -> io::Result<TerminalHandle>;
    async fn terminal_output(&self, h: &TerminalHandle) -> io::Result<TerminalSnapshot>;
    async fn terminal_wait(&self, h: &TerminalHandle) -> io::Result<ExitStatus>;
    async fn terminal_kill(&self, h: &TerminalHandle) -> io::Result<()>;
}

The shape is deliberately close to ACP's method surface. AcpHost becomes a near-mechanical translation: each method serializes its arguments, dispatches as an outbound JSON-RPC call, awaits the response. LocalHost is just thin wrappers around tokio::fs and tokio::process.

Why this trait, not std::fs? Because every tool must work in ACP mode where filesystem operations are not local — they round-trip through JSON-RPC. Coding the tools against std::fs would mean ACP mode requires a fork of every tool. Trait dispatch costs us one virtual call per syscall; nothing measurable.

Ports and adapters, viewed differently

Frontend is the inbound port; Host is the outbound port. Core depends on neither concretely.

The Cargo workspace

One workspace, many small crates. Each adapter is its own binary — not a subcommand of a larger router. The TUI binary is named arnes (the daily driver); ACP and HTTP each get their own named binary that editors and operators spawn directly. Conventional Rust layout, conventional install story (one binary per use case), and cargo handles "only build what you need" via crate selection rather than feature gymnastics. 

arnes/
├─ Cargo.toml                  # workspace root
├─ crates/
│  ├─ arnes-core/              # the coding-harness library:
│  │                           #   traits, Session, prompt, persistence,
│  │                           #   compaction, skills, LocalHost, and the
│  │                           #   built-in tools (read, write, edit, bash)
│  │
│  ├─ arnes-tui/               # binary `arnes`       (TUI daily driver)
│  ├─ arnes-acp/               # binary `arnes-acp`   (ACP server; AcpHost lives here)
│  ├─ arnes-http/              # binary `arnes-serve` (HTTP/WS server)
│  └─ arnes-gui/               # binary `arnes-gui`   (or web app on arnes-serve, M9)
└─ docs/                       # this plan + the book

Why one library crate, not two. arnes is a coding harness — not a general-purpose agent framework. The "general agent runtime" role belongs to agent-rig directly below us. So arnes-core's scope is specifically coding-harness machinery, and the built-in coding toolkit (read, write, edit, bash) belongs inside that crate — there is no realistic non-coding consumer to factor it out for.

Two notes on where the Host impls live:

  • LocalHost — the tokio::fs + tokio::process impl — lives in arnes-core::host, next to the trait it implements. It is ~200 lines and uses no dependencies beyond what arnes-core already has, so a separate crate buys nothing.
  • AcpHost lives inside arnes-acp as arnes-acp::host. It is tightly coupled to the adapter's JSON-RPC client (every method issues outbound RPC), so splitting it out would create a circular-feeling dependency for no architectural win.

Each binary is a thin main.rs: parse flags, construct the right Frontend and Host, hand them to a Session, run the event loop. Three short, independent entry points instead of one router: 

// crates/arnes-tui/src/main.rs           // produces `arnes`
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let opts = TuiOpts::parse();
    arnes_tui::run(opts).await
}

// crates/arnes-acp/src/main.rs           // produces `arnes-acp`
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let opts = AcpOpts::parse();
    arnes_acp::run_stdio(opts).await
}

// crates/arnes-http/src/main.rs          // produces `arnes-serve`
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let opts = ServeOpts::parse();
    arnes_http::run(opts).await
}

Common flags (--model, --cwd, --session, …) live in arnes-core::cli as a reusable CommonOpts struct that each binary's own options struct flattens in via clap's #[command(flatten)].

Each adapter knows how to assemble its own Frontend, its own Host, and its own user-input loop, then hand them to a Session from arnes-core.

Crate dependency graph

Four binary crates depend on one library crate. arnes-core holds everything coding-harness specific; the general-agent layer sits below it as agent-rig.

What a Session looks like

The single entry point a frontend talks to. Holds the message history, the tool registry, the system prompt, the agent-rig AgentRunner, and the configured Host. Exposes a tiny surface: 

// arnes-core/src/session.rs

pub struct Session<F: Frontend, E: Host> {
    frontend: Arc<F>,
    host: Arc<E>,
    runner: AgentRunner,        // from agent-rig
    tools: ToolRegistry,
    history: Vec<Message>,
    prompt_builder: SystemPromptBuilder,
    writer: Option<SessionWriter>,
    extensions: ExtensionHost,
}

impl<F, E> Session<F, E> where F: Frontend, E: Host {
    pub async fn prompt(&mut self, input: UserInput) -> Result<()>;
    pub async fn cancel(&self);
    pub async fn compact(&mut self) -> Result<()>;
    pub fn set_mode(&mut self, mode: SessionMode);
    pub fn snapshot(&self) -> SessionSnapshot;
}

Session::prompt runs the agent loop, fans events out through frontend.on_event(...), and pauses for frontend.request_permission(...) whenever a sensitive tool is about to fire. Everything else is plumbing.

SessionEvent: the lingua franca

Every adapter speaks the same event vocabulary. Most variants map almost 1:1 to ACP's session/update payloads, which is not a coincidence — ACP got this right and there is no reason to invent something different. 

pub enum SessionEvent {
    AgentMessageDelta { text: String },
    AgentThoughtDelta { text: String },
    ToolCallStart   { id: String, name: String, input: serde_json::Value },
    ToolCallUpdate  { id: String, partial: serde_json::Value },
    ToolCallEnd     { id: String, result: ToolResult },
    TurnStart,
    TurnEnd         { stop_reason: StopReason },
    ModeChanged     { mode: SessionMode },
    Compacted       { tokens_freed: u64 },
    Error           { message: String },
}

The TUI turns these into screen updates. The ACP adapter wraps them in session/update notifications. The HTTP/WS adapter pushes them over a channel. The GUI translates them into UI state updates. None of them edit the vocabulary — only consume it.

Two things this design deliberately does not try

  • No erased trait objects in hot paths. Session is generic over F: Frontend and E: Host. We pay nothing for dispatch in the inner loop. Each binary monomorphises one Session at startup; everything after that is static dispatch.
  • No process-per-adapter. All four adapters run in the same process; a future arnes-serve can host the same Session behind multiple transports concurrently. We keep the option open without committing to it.

What this gets us

A core that does not know what year it is. Add a fifth frontend (an e-mail bot, a Slack adapter, a CI integration) and you write a Frontend impl, a tiny entry point, and you are done. Add a new sandboxing strategy (containerised filesystems, a remote dev box) and you write a fourth Host impl and pass it to the same Session constructor. Neither change touches the harness logic or the tools.
