feat/recording-frontend

A test-only Frontend impl that captures every event into a shared Vec<SessionEvent> for assertions. First PR to land anything under crates/arnes-core/tests/support/ — creates the shared test-support module skeleton phase 2 deferred.

Goal

Ship RecordingFrontend: implements Frontend, pushes each SessionEvent received via on_event onto an internal vec, exposes events() returning a snapshot for the test to assert against. Permission requests are denied by default.

Files touched

  • new: crates/arnes-core/tests/support/mod.rs — the support-module skeleton: pub mod recording_frontend; + (placeholder comment for the modules added by PRs #5 and #6).
  • new: crates/arnes-core/tests/support/recording_frontend.rs — the helper itself + its unit test.

No new deps. std::sync::Mutex is in std; we don't need tokio::sync::Mutex because the helper never holds the lock across an .await (see point 2 below).

Discussion

1. Where the support module lives. crates/arnes-core/tests/support/, not crates/arnes-core/src/test_support/. Two reasons:

  • It's only for integration tests, not unit tests. Unit tests inside src/ use inline fixtures (per the existing metering/ pattern). The support module exists so multiple tests/*.rs files can share helpers.
  • It doesn't ship in the published crate. Anything under src/ would be reachable from downstream crates and visible in cargo doc; living under tests/ keeps it firmly test-only. (arnes-core is publish = false anyway, but the principle holds.)

Each integration-test file that wants the helpers adds mod support; at the top — Cargo's tests/ convention makes tests/support/mod.rs reachable from any sibling test file.

2. std::sync::Mutex, not tokio::sync::Mutex. The lock is held only across pure-data ops (push to vec, clone the vec out). No .await while holding the lock. The std mutex is cheaper and doesn't require RecordingFrontend to be used inside a tokio runtime context. (The frontend itself runs inside one because on_event is async, but the lock's critical section is sync.)

3. Snapshot via events() rather than handing out the lock. Two patterns considered:

  • fn events(&self) -> Vec<SessionEvent> (chosen): clones the vec under the lock; returns owned data. Cheap because SessionEvent is Clone and the vec is small (one test's worth of events — usually < 20).
  • fn events(&self) -> MutexGuard<'_, Vec<SessionEvent>>: hands out the lock. Lets the caller iterate without copying. But couples the test to mutex semantics; if a panic in the test poisons the lock, every subsequent assertion fails opaquely.

The clone-out variant trades a tiny perf cost (irrelevant in tests) for test-failure ergonomics.

4. Permission: deny by default. RecordingFrontend::request_permission returns Permission::Deny always. The permission flow doesn't exist yet (M3 work), but the trait method needs an impl. Denying rather than allowing matches the spirit of "Unknown is never silently zero" from phase 3: a test that accidentally triggers a permission prompt should get a visible denied state in its assertions, not silent acceptance. Tests that do want a permission flow will land alongside M3 with a richer test helper.

5. Public API surface. Three methods: 

impl RecordingFrontend {
    pub fn new() -> Self;
    pub fn events(&self) -> Vec<SessionEvent>;
    pub fn clear(&self);   // for multi-prompt tests that want fresh state
}

clear() is added now because PR #7's two-turn test wants to assert per-turn event slices without summing across both turns. Could equally be done by snapshot-diffing in the test; the method is cheaper to read.

6. No Arc wrapping inside the helper. Session takes Arc<F>, so the test constructs the helper as Arc::new(RecordingFrontend::new()) and passes the same Arc to both Session::new and the test's assertion sites (via arc.events()). The helper itself doesn't bake an Arc in — that's the caller's responsibility.

The helper (tests/support/recording_frontend.rs):

use std::sync::Mutex;

use async_trait::async_trait;

use arnes_core::{Frontend, Permission, PermissionRequest, SessionEvent};

#[derive(Default)]
pub struct RecordingFrontend {
    events: Mutex<Vec<SessionEvent>>,
}

impl RecordingFrontend {
    pub fn new() -> Self { Self::default() }

    pub fn events(&self) -> Vec<SessionEvent> {
        self.events.lock().expect("recording-frontend mutex poisoned").clone()
    }

    pub fn clear(&self) {
        self.events.lock().expect("recording-frontend mutex poisoned").clear();
    }
}

#[async_trait]
impl Frontend for RecordingFrontend {
    async fn on_event(&self, event: SessionEvent) {
        self.events
            .lock()
            .expect("recording-frontend mutex poisoned")
            .push(event);
    }

    async fn request_permission(&self, _req: PermissionRequest) -> Permission {
        Permission::Deny
    }
}

Tests

One self-contained unit test in the same file (or in a sibling test file under tests/ that uses mod support;):

  • Round trip: construct the helper, manually call on_event twice with two distinct events, assert events() returns them in order; call clear(), assert events() is empty.
  • Permission denied default: call request_permission; assert the return is Permission::Deny.

These are the test-helper's own correctness tests — not tests of Session. They live wherever the tests/support/ convention places test files; the conventional path is one tiny tests/support_smoke.rs file that pulls mod support; and exercises each helper as it lands. (PR #5 and PR #6 extend the same smoke file.)
