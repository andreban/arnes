M1 · Phase 4

Session + test scaffolding

The agent-rig wrapper plus the mocks every later PR will reuse for testing. First phase that ships runtime behaviour — previous phases shipped type vocabularies (phase 2) and pure arithmetic (phase 3). The acid test: a deterministic two-turn round-trip integration test that runs without any API key.

Order matters. PR #1 is a dep-only chore that everything else compiles against; PR #2 lays down the struct shape so PR #3's translator has a body to live in; PR #4 creates the tests/support/ skeleton that PRs #5 and #6 each drop a submodule into (so #5 and #6 can swap order, but #4 is first of the three); PR #7 needs every prior PR to assemble the integration test.

What "chore" means here. PR #1 is a pure dependency / workspace-config change — no new Rust source files in arnes-core/src/, no behavioural change. It's still its own PR because the dep choice itself is an architectural decision (which features to enable, which source to track — main branch, pinned rev, or crates.io — whether to add it as a workspace dep) and folding it into a behavioural PR would bundle that discussion away.

Cross-cutting decisions (settled)

Four choices apply to multiple PRs in this phase. Captured here so each PR doc can reference them rather than re-litigate.

1. Generic monomorphisation over F: Frontend, H: Host. Session<F, H> is generic; no dyn Frontend or dyn Host in the hot path. Each binary monomorphises one Session at startup — the TUI binary instantiates Session<TuiFrontend, LocalHost>; the ACP binary instantiates Session<AcpFrontend, AcpHost>; tests instantiate Session<RecordingFrontend, InMemoryHost>. This is restated from the architecture doc; phase 2's async-trait decision for Host (because ToolContext holds Arc<dyn Host>) does not apply at the Session boundary — Session holds Arc<H>, not Arc<dyn Host>, so the static-dispatch promise survives.

2. Shared tests/support/ module lands here. Phase 2 deferred this; phase 4 needs it because three of its PRs (recording-frontend, in-memory-host, scripted-llm) all ship test-only helpers reused across later integration tests. The first PR to add anything under tests/support/ (PR #4, recording-frontend) creates the module skeleton (mod.rs with the relevant pub mod declarations); subsequent PRs each add one submodule. Modules under tests/support/ are pub(crate)-as-far-as-tests-go — reachable from every integration-test file in the same tests/ directory via mod support; at the top.

3. Cancellation via tokio_util::CancellationToken. Already in tree from phase 2 (in ToolContext). Session owns a CancellationToken field; Session::cancel() calls token.cancel(); agent-rig's AgentRunner accepts the same token and stops pulling from the provider when it fires. At M1 the cancel surface is cooperative — we do not race a select! against the token in the translator yet, because the translator's awaits are on agent-rig's stream, and agent-rig is what reads the token. M2+ may add a direct select! when tools (which run inside the translator's await tree) need to be interruptible mid-execution.

4. agent-rig consumed with no opt-in features. At M1 we only need the runtime core: the LlmModel trait, the AgentRunner driver, and the typed-delta stream vocabulary — all of which are unconditional in agent-rig (the crate's default = [] means providers are explicit opt-ins, never defaults). Provider features (gemini, ollama) are deliberately not enabled here — the scripted LLM exercises the same trait without any HTTP, and the real Gemini wire-up is phase 7's job. This keeps phase 4's CI fast and dependency-light, and keeps arnes-core's unit tests runnable on machines without network access. Source choice and the rationale for landing this as its own chore PR live in PR #1.

Discussion sections in each PR doc

Same pattern as phases 2 and 3: every per-PR doc has a Discussion section surfacing the architectural choices, even when they look obvious. The point is to make every choice reviewable individually rather than bundling them away. Examples of what gets discussed:

  • agent-rig-dep: source (main-branch tracking vs pinned rev vs crates.io); features at M1 vs phase 7 (none vs provider opt-ins); workspace dep vs per-crate; the rationale for sequestering this in its own chore PR.
  • session-skeleton: type-parameter naming (F, H vs F, E); Arc<F> vs owned F; what new() takes; whether cancel() consumes or borrows; where CumulativeUsage lives (field vs computed); the history: Vec<Message> internal-vs-public question deferred to the snapshot API in M6/M8.
  • session-prompt: the translator pattern (single fork between event emission and content-block accumulation); how each agent-rig delta maps to an EventKind; when TurnEnd fires; TurnUsage construction (where pricing lookup happens — or doesn't, yet); error mapping to EventKind::Error vs the Result return.
  • recording-frontend: Mutex<Vec<SessionEvent>> vs tokio::sync::Mutex; whether the helper owns the events or hands them out as a snapshot; permission default for tests; the deny-by-default rationale.
  • in-memory-host: which methods to implement vs leave on the trait default; backing storage shape (HashMap<PathBuf, String>); terminal methods stay Unsupported (deferred to M3); whether to seed initial files via constructor.
  • scripted-llm: canned-deltas data shape (Vec<Script> per turn); explicit token counts on the script; whether to support thinking blocks at M1; ordering / pacing (no artificial delays); how to signal turn boundaries.
  • session-roundtrip-test: what exactly is asserted (event sequence, history shape, cumulative usage after two turns); deterministic ordering guarantees; why two turns rather than one; how this test grows in M2 once tool calls land.

Test strategy for the phase

This phase's tests are both the deliverable and the infrastructure: PRs #4–#6 ship test helpers that are themselves exercised by their own per-PR unit tests, and PR #7 is the integration test that ties them together. Concretely:

  • PR #2 (session-skeleton): unit tests for new()'s wiring + cancel() flipping the token + cumulative_usage() returning the default at construction. No agent-rig calls.
  • PR #3 (session-prompt): ships with a tiny inline test-double LLM (a few-line fixture local to PR #3's unit tests) that emits a fixed sequence of typed deltas. This keeps the PR self-contained — we don't reorder phase 4 to land scripted-llm first, because scripted-llm's value is as a reusable helper for richer scenarios (PR #7), not as the only way to exercise the translator. PR #3's tests assert: text deltas produce TextDelta events; the final assembled Message matches the concatenation; TurnEnd fires once with the right TurnUsage.
  • PR #4 (recording-frontend): unit test that pushing an event into the helper makes it readable in the recorded vec.
  • PR #5 (in-memory-host): unit tests for read_text_file / write_text_file / list_directory against an in-memory map; assertion that terminal methods still return Unsupported.
  • PR #6 (scripted-llm): unit test that the canned script replays in order and reports the configured token counts.
  • PR #7 (session-roundtrip-test): the integration test — crates/arnes-core/tests/session_roundtrip.rs — constructs a Session with all three test doubles, runs two turns, and asserts on the event sequence, history, and cumulative usage.
