M1 · Phase 4 · PR 1 of 7

chore/agent-rig-dep

Add agent-rig to arnes-core's dependency list. No new Rust source files; no behavioural change. The whole PR is the Cargo manifest edits plus a one-test smoke check that the crate's surface types are importable.

Goal

Make use agent_rig::{LlmModel, AgentRunner, /* ... */}; compile from inside arnes-core. Nothing in this PR uses those imports yet — PRs #2 and #3 do — but landing the dep as its own PR isolates the dependency-choice discussion from any behavioural change.

Files touched

  • modify: Cargo.toml — one new entry under [workspace.dependencies].
  • modify: crates/arnes-core/Cargo.toml — one new entry under [dependencies] that picks up the workspace dep.
  • modify: Cargo.lock — the resolved set of transitive deps; reviewed but not hand-edited.

No new modules, no new source files, no new pub use lines in lib.rs.

Discussion

1. Source: track agent-rig's main branch. 

agent-rig = { git = "https://github.com/andreban/agent-rig", branch = "main", default-features = false, features = ["<core feature name>"] }

arnes and agent-rig share a maintainer, so the usual reason to pin a specific rev — insulate against an upstream we don't control — doesn't apply here. We pull from main and rely on the committed Cargo.lock to keep day-to-day builds reproducible. A breakage that surfaces after a cargo update -p agent-rig is something the maintainer caused, sees, and fixes on the same loop — not an external instability event to defend against.

Alternatives considered and rejected:

  • Pinned rev = "<sha>": the right call when the upstream is external; not necessary here. Adds a manual bump step every time the agent-rig side moves, for no benefit we'd otherwise miss.
  • Published crates.io version: not yet applicable — agent-rig hasn't picked a release cadence. When it does, the dep-source change is a one-line follow-up PR.

2. Features: none at M1. agent-rig's feature layout is the convenient case: the base API (LlmModel, AgentRunner, typed deltas) is unconditional, and each provider (gemini, ollama, …) is its own opt-in feature with default = []. So arnes-core takes the dep with no features list and no default-features = false — nothing to enable, nothing to disable. Providers are phase 7's call and will be enabled on the per-crate dep in the adapter that needs them (arnes-tui / arnes-acp), not on the workspace entry.

3. Workspace dep vs per-crate dep. Phase 1's deferred decisions said "no pre-declared [workspace.dependencies]"; but the convention since has been "each PR adds the deps its own code introduces, in the workspace table." Continuing that pattern: agent-rig goes in [workspace.dependencies] with its git URL + branch, and arnes-core/Cargo.toml picks it up with { workspace = true }. Later adapter crates (arnes-tui, arnes-acp) that need to construct concrete provider LlmModels in phase 7 will pick up the same workspace entry and add features = ["gemini"] (or similar) at the per-crate level — without re-litigating the source choice.

4. Why a separate PR instead of folding into PR #2? Three reasons:

  • Dependency choices are architectural. Source (git branch vs pinned rev vs crates.io), feature set, workspace vs per-crate — each has tradeoffs worth a Discussion section, and bundling them into a behavioural PR buries them.
  • The blast radius is the whole workspace. A bad pin breaks every downstream PR; isolating it lets a revert be one-commit-clean.
  • Reviewability. The diff is small, the build log is the meaningful artifact (no warnings? cargo check --workspace still clean? Cargo.lock changes look sane?). A reviewer can confirm those in seconds without context-switching into Rust source.

5. No smoke test in src/. One temptation is to add a #[allow(unused_imports)] use agent_rig::LlmModel; somewhere as a "the dep resolves" canary. We don't — cargo check --workspace in CI already confirms the dep resolves. Adding a dead-import canary is noise that the next PR has to delete anyway.
