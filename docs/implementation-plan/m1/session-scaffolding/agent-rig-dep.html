M1 · Phase 4 · PR 1 of 7

chore/agent-rig-dep

Add agent-rig to arnes-core's dependency list. No new Rust source files; no behavioural change. The whole PR is the Cargo manifest edits plus a one-test smoke check that the crate's surface types are importable.

Goal

Make use agent_rig::{LlmModel, AgentRunner, /* ... */}; compile from inside arnes-core. Nothing in this PR uses those imports yet — PRs #2 and #3 do — but landing the dep as its own PR isolates the dependency-choice discussion from any behavioural change.

Files touched

  • modify: Cargo.toml — one new entry under [workspace.dependencies].
  • modify: crates/arnes-core/Cargo.toml — one new entry under [dependencies] that picks up the workspace dep.
  • modify: Cargo.lock — the resolved set of transitive deps; reviewed but not hand-edited.

No new modules, no new source files, no new pub use lines in lib.rs.

Discussion

1. Source: git rev vs published crate. Two options:

  • Published crates.io version: agent-rig = "X.Y". Pros: standard, cacheable, no submodule-style fragility. Cons: only available if agent-rig has actually published a version we want, and pinning floats inside the SemVer range unless we also commit a precise Cargo.lock (we already commit one).
  • Git revision: agent-rig = { git = "https://github.com/andreban/agent-rig", rev = "<sha>" }. Pros: lets us live on a specific main-branch commit before agent-rig stabilises a release cadence. Cons: no docs.rs autoindex; cargo doc still works locally but link-checked rustdoc is weaker.

Recommendation: git revision with an explicit rev (not branch = "main" — that would make builds non-reproducible across cargo update). Switch to a crates.io version when agent-rig publishes one we want; the dep-source change is then itself a one-line PR.

2. Features. Pin default-features = false and explicitly opt into only what arnes-core needs at M1. Concretely: whatever feature exposes LlmModel, AgentRunner, and the typed-delta stream. No provider features (gemini, anthropic, ollama, …) — those are phase 7's call, and adding them here would silently pull in reqwest / rustls / TLS-backend bikeshedding into a chore PR.

3. Workspace dep vs per-crate dep. Phase 1's deferred decisions said "no pre-declared [workspace.dependencies]"; but the convention since has been "each PR adds the deps its own code introduces, in the workspace table." Continuing that pattern: agent-rig goes in [workspace.dependencies] with its version + rev + features, and arnes-core/Cargo.toml picks it up with { workspace = true }. Later adapter crates (arnes-tui, arnes-acp) that need to construct concrete provider LlmModels in phase 7 will then pick up the same workspace entry — without re-litigating the rev/version.

4. Why a separate PR instead of folding into PR #2? Three reasons:

  • Dependency choices are architectural. Source (git vs crates.io), rev pin, feature set, workspace vs per-crate — each has tradeoffs worth a Discussion section, and bundling them into a behavioural PR buries them.
  • The blast radius is the whole workspace. A bad pin breaks every downstream PR; isolating it lets a revert be one-commit-clean.
  • Reviewability. The diff is small, the build log is the meaningful artifact (no warnings? cargo check --workspace still clean? Cargo.lock changes look sane?). A reviewer can confirm those in seconds without context-switching into Rust source.

5. No smoke test in src/. One temptation is to add a #[allow(unused_imports)] use agent_rig::LlmModel; somewhere as a "the dep resolves" canary. We don't — cargo check --workspace in CI already confirms the dep resolves. Adding a dead-import canary is noise that the next PR has to delete anyway.

Manifest edits

Workspace root Cargo.toml:

[workspace.dependencies]
# … existing entries …
agent-rig = { git = "https://github.com/andreban/agent-rig", rev = "<sha>", default-features = false, features = ["<core feature name>"] }

crates/arnes-core/Cargo.toml:

[dependencies]
# … existing entries …
agent-rig = { workspace = true }

Tests

None new in this PR. The workspace-wide cargo check and cargo build jobs in CI are what assert the dep resolves.

Acceptance

  • cargo check --workspace clean.
  • cargo build --workspace succeeds on all three OSes (Linux/macOS/Windows).
  • cargo clippy --workspace --all-targets -- -D warnings clean.
  • cargo test -p arnes-core green (existing tests unchanged).
  • RUSTDOCFLAGS="-D warnings" cargo doc --no-deps -p arnes-core clean.
  • Cargo.lock change is committed and the transitive set looks sane (no surprise heavy deps pulled by the chosen feature flags).
