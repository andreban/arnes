Cross-cutting decisions (settled)

Two choices apply to multiple PRs in this phase. Captured here so each PR doc can reference them rather than re-litigate.

1. Integer micros for money. All amounts in arnes-core are Micros(i64) — millionths of a dollar (six decimal places). Reasons:

  • No float drift. Summing thousands of small per-token costs in f64 accumulates rounding error; integer math is exact.
  • Range is enormous. i64 max ~ 9.2×1018 micros ~ 9.2×1012 dollars. Saturates well above any plausible session cost.
  • Lighter than Decimal. The rust_decimal crate is the alternative, but its 128-bit reps and per-op machinery are overkill for "track costs in dollars with six decimal places."
  • Six decimals is enough. Provider pricing is published to that precision (e.g. $0.075 per 1M tokens = 75 micros/Mtok). Truncating below that loses fractions of a fraction of a cent.

Display formatting (turning Micros into $0.0001 or $1,234.56) is a frontend concern; arnes-core never produces formatted strings for end users.

2. Unknown pricing is never silently zero. The three-state pricing enum (Priced / Free / Unknown) is load-bearing: it lets us report "we don't know what this turn cost" honestly rather than aggregating it into a fake $0.00. CumulativeUsage tracks turns_with_unknown_cost as a separate count from known_cost; flatten-style projections preserve the same distinction.

Discussion sections in each PR doc

Same pattern as phase 2: every per-PR doc has a Discussion section surfacing the architectural choices, even when they look obvious. Examples of what gets discussed:

  • money-types: why integer micros (vs Decimal, vs f64); per-token-kind Cost breakdown rationale; whether to store or compute total.
  • pricing-types: three-state vs Option<ModelPricing>; whether optional cache/thinking pricing fields belong on every ModelPricing.
  • usage-record: when Cost is computed (eager at Usage construction); why Option<Cost> on Usage; shape of ModelUsage as the aggregated row.
  • cumulative-usage: indexing by (AgentId, ModelKey); record() semantics; separating known_cost from turns_with_unknown_cost.
  • pricing-registry: wildcard matching shape; override precedence; the Unknown fallback.
  • pricing-toml-loader: TOML schema shape; bundling via include_str! vs runtime file; where the user-override file lives.
  • cumulative-usage-projections: borrowed vs owned view returns; projection consistency invariant; whether to expose iterators instead.
  • turnend-usage-wiring: minimal — one-field addition; consumer sweep.

Test strategy for the phase

Each PR ships tests for its own surface. The phase as a whole earns these integration-style assertions (across the relevant PRs):

  • Three-state pricing behaves correctly (PRs #2, #5): Priced / Free / Unknown each produce the expected Option<Cost> from compute_cost.
  • User override wins over bundled (PR #5): override entry for a model is used instead of the bundled entry.
  • Wildcard pattern matches (PR #5): the Ollama provider = "ollama", pattern = "*" rule matches any model_id.
  • Cumulative sums are consistent (PR #4 + #7): the sum of by_model() totals equals the sum of by_agent() totals equals the registry's total_known_cost(); unknown-cost turns count consistently.
  • Per-(agent, model) bucketing (PR #4): two synthetic Usage values with different ModelKeys produce two entries in CumulativeUsage.
