M1 work plan

Foundation, by phase

M1 is organized into phases; each phase contains one or more PRs sized so the user can fully review every architectural choice before it lands. For the design rationale that motivates the work, see the M1 milestone page.

Sizing rule. Each PR is small enough to discuss end-to-end: usually one Rust file (or one logical type), the deps it needs, the tests it earns, and one acceptance gate. Six similar files is six PRs — not one. The architectural choices each PR represents must be surfaced in its plan doc for explicit discussion before implementation.

Detailing strategy. Phases are detailed (full plan docs per PR, with discussion sections) just-in-time — before starting work on the phase, not all up front. This keeps the planning cost in sync with how much we actually know, and lets earlier phases' decisions inform later phases' details. Right now only phase 2 is fully detailed; the others have scope-level entries below that get expanded before they're started.

Critical path. 0 → 1 → 2 → 3 → 4 → 7 → 8/9. Phase 5 starts in parallel with phase 2 (different crate, no shared types yet); phase 6 unblocks the ACP path independently of TUI work.

Phase 0 — Repo bootstrap (done)

Stand up the repo with planning docs, meta files, and a clean first commit on main. No Rust. Direct-to-main per design (the bootstrap window predates the feature-branch workflow). See the commit history on main: README, AGENTS, CONTRIBUTING, LICENSE, .gitignore, .gitattributes.

Phase 1 — Workspace + CI (done, PR #2 on GitHub)

Goal. cargo check --workspace passing in CI before any real code lands. Pure workspace Cargo.toml with three empty member crates (arnes-core, arnes-tui, arnes-acp); GitHub Actions matrix on Linux/macOS/Windows running fmt, clippy -D warnings, and test.

Deliberately deferred at phase 1 (rationale matters because future PRs will be tempted to add these):

  • No rust-version MSRV pin. Pays off for crates.io publishing or external support policies; neither applies yet.
  • No rust-toolchain.toml. Pinning channel = "stable" only auto-installs stable for rustup users who don't already have it — tiny convenience, no reproducibility.
  • No rustfmt.toml / clippy.toml. Only useful for overriding defaults. Empty stubs invite bikeshedding.
  • No pre-declared [workspace.dependencies]. Each later PR adds the deps its own code introduces, in the same commit.

Phase 2 — Core types (planned in detail)

Define the vocabulary the rest of the workspace depends on: Frontend and Host traits, Message and ContentBlock, the agent-identity types, the error type, the tool-context bundle. Each lands as its own PR so every architectural choice gets discussed individually.

See the Core types phase plan for the six per-PR docs, the settled cross-cutting decisions (async-trait, no thiserror), and the discussion items each PR must surface before implementation.

Phase 3 — Usage + pricing (planned in detail)

Goal. Token/cost types with three-state pricing (Priced / Free / Unknown), per-(agent, model) aggregation, and a tested registry loaded from bundled TOML with user overrides. First phase that ships runtime arithmetic; previous phases shipped type vocabularies only.

See the Usage + pricing phase plan for the eight per-PR docs, the cross-cutting decisions (integer-micros for money; Unknown is never silently zero), and the discussion items each PR must surface before implementation.

Phase 4 — Session + test scaffolding (scope only)

Goal. The agent-rig wrapper plus the mocks every later PR will reuse for testing. The acid test: a deterministic two-turn round-trip test that runs without any API key.

Anticipated PRs (to be detailed before phase starts):

  • chore/agent-rig-dep — add agent-rig to workspace deps (no provider features yet).
  • feat/session-struct — Session<F, H> with new, prompt, cancel, cumulative_usage; event-stream translation.
  • feat/recording-frontend — test helper that captures every event for assertions.
  • feat/in-memory-host — fake host (real fs/process impls land in M3).
  • feat/scripted-llm — LlmModel impl that replays canned responses with known token counts.
  • feat/session-roundtrip-test — the two-turn integration test pulling everything together.

Phase 5 — ACP transport spike (single PR)

Goal. Bidirectional JSON-RPC over stdio works; the library decision is made and recorded as an ADR.

jsonrpsee server on stdin/stdout; outbound-call helper to validate server-initiated request path; integration test for malformed frames and unknown methods. ADR docs/adr/0001-jsonrpc-library.md records the decision and any fallback triggers that almost fired.

Acceptance gate: if any M1 fallback trigger fires (outbound boilerplate >10 lines per method, cancellation interference, _meta friction), this PR is replaced with the hand-rolled framer alternative.

Phase 6 — ACP minimal protocol (scope only)

Goal. Four inbound methods + one outbound notification, end-to-end through a real Session.

Anticipated PRs (to be detailed before phase starts):

  • feat/acp-initialize — protocol version negotiation; capability advertisement.
  • feat/acp-session-new-and-prompt — construct Session<AcpFrontend, AcpHost>; mint a UUID v7; push user message; return stop reason.
  • feat/acp-session-cancel — notification routing into the session's cancellation token.
  • feat/acp-frontend-and-update — AcpFrontend; translates SessionEvent::AgentMessageDelta into session/update notifications. Includes the golden test.

Phase 7 — Wire Gemini provider + real usage (single PR)

Goal. A real LLM call produces a real reply, real token counts, and a real cost.

Enable agent-rig's gemini feature; construct GeminiModel in both binaries from GEMINI_API_KEY; verify usage extraction. Smoke tests gated on the env var via #[ignore]; CI runs them in a job with the secret available.

Phase 8 — Minimal TUI (scope only)

Goal. arnes binary drops you into a ratatui session that streams a Gemini reply, with clean shutdown on any exit path (terminal raw mode restored even on panic).

Anticipated PRs (to be detailed before phase starts):

  • feat/tui-skeleton — clap CLI; crossterm raw-mode setup with RAII guard; empty render loop.
  • feat/tui-input-task — key event reader; submit on Enter; Ctrl-C exit; Esc cancel.
  • feat/tui-render-task — transcript region; input box; ratatui layout.
  • feat/tui-agent-task-wiring — TuiFrontend; bridges Session events into the render task's command channel.

Phase 9 — M1 end-state: smoke tests + docs (single PR)

Goal. Tie everything off; M1 is mergeable to main as "done."

Top-level README with five-line examples for both binaries; per-crate READMEs; a "Hello, arnes" walkthrough doc. CI smoke job verifies cargo install --path crates/arnes-tui and crates/arnes-acp succeed on all three OSes.

What is deliberately not in M1

  • Tool calling end-to-end. Lands in M2. arnes-core::tools::register_defaults() doesn't exist yet; the registry from phase 2 is empty at session start.
  • Real permission flow. The trait surface is in place from phase 2; the modal, session/request_permission outbound call, and matches_scope logic are M3.
  • Persistence. No JSONL write/read in M1. Sessions are ephemeral.
  • Multi-provider support. Gemini only at M1. Adding Anthropic/OpenAI is the parallel "Additional providers" workstream.
