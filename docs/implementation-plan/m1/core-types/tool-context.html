feat/tool-context

The bundle every Tool::execute receives: a host handle, a progress sink, a cancellation token, and the invoking agent's ID. The Tool trait itself lives in M2; the context lives here so phase 4's test scaffolding can build one and M2 lands tools against an already-frozen shape.

Goal

Ship ToolContext, ProgressSink, and ProgressUpdate. Last PR in phase 2; closes out the core type vocabulary so phase 3 (usage) can build on it.

Files touched

  • new: crates/arnes-core/src/tool_context.rs
  • modify: crates/arnes-core/src/lib.rs
  • modify: root + arnes-core Cargo.toml — add tokio-util.

Discussion

1. Why bundle into a context struct at all? agent-rig (and many tool-calling APIs) pass a few values to tool execution. Bundling them into one struct means adding a new capability (timing budget, log tap, trace ID, …) is a struct field change, not a trait signature change. Tool::execute stays async fn execute(&self, input: Value, cx: &ToolContext) -> ToolResult forever; the cx grows.

2. The early arrival of tokio in arnes-core. ToolContext.cancellation: CancellationToken comes from tokio_util::sync::CancellationToken, which pulls tokio into arnes-core's dep tree starting with this PR. That's earlier than phase 4 (where Session actually runs anything on a runtime), but unavoidable if ToolContext lives here.

Alternatives considered:

  • Defer ToolContext to M2's first PR: cleaner sequencing, but means M2 has to design the type while also writing the first tool. Splitting now lets phase 2 settle the shape.
  • Use futures::future::AbortHandle instead: runtime-agnostic, but agent-rig and both adapters use tokio anyway; abstracting over runtime is ceremony for nothing.
  • Use a callback for cancellation: more flexible but harder to compose; tokio's cancellation token is the idiomatic choice in tokio code.

Decision: keep ToolContext in phase 2; accept the early-tokio cost.

3. ProgressSink as trait, not a channel. Tools emit progress; Session turns those into events on its own stream. The trait-based shape means the session can implement it on its event-translation side without exposing channel types here. ProgressUpdate has both Text (the default) and Structured (reserved for tools that emit richer payloads later).

4. No SubAgentSpawner or spawn_subagent field. An earlier draft of this plan had ToolContext carry an Arc<dyn SubAgentSpawner> so post-V1 sub-agent-aware tools could compile against the M1 trait surface unchanged. Checking agent-rig's src/tools/agent_tool/mod.rs shows this is the wrong abstraction.

agent-rig already has AgentTool: a wrapper that registers a child Agent + its own AgentRunner as a tool in the parent's ToolRegistry. The parent invokes it like any other tool; agent-rig's runner serialises args into a user message, runs the child, and forwards every child AgentEvent back through the parent's stream (tagged with parent_run_id so Session can map it to AgentId::SubAgent(...)).

So sub-agents in arnes aren't a separate "spawn from inside a tool" mechanism — sub-agents are tools, dispatched through the same registry as everything else. The post-V1 enablement flow is:

  1. Session config declares which sub-agents are available (name, system prompt, allowed tools, …).
  2. On Session construction, arnes builds an agent_rig::AgentTool for each declared sub-agent and registers them via ToolRegistry::register_agent.
  3. The parent model invokes them like any other tool. No new arnes runtime machinery.
  4. Child events flow back through the same stream Session already consumes; the run-id-tagged events become SessionEvents with AgentId::SubAgent(uuid) and depth > 0.

Nothing in ToolContext needs to change for this. Tools never explicitly spawn sub-agents — they don't even know sub-agents exist as a category. The SubAgentSpawner trait, the SubAgentSpec stub, the SubAgentHandle stub, and the spawn_subagent field on ToolContext all drop from the design (not just deferred from M1).

5. Arc<dyn ...> on host and progress. host: Arc<dyn Host> and progress: Arc<dyn ProgressSink>. Reasons:

  • Tools are dyn Tool in ToolRegistry; their execute takes &ToolContext, not &ToolContext<F, H, ...>.
  • ToolContext needs to be constructible without the caller knowing the concrete Host impl.
  • Arc is the right shared-ownership primitive for possibly-concurrent tool execution.

The dyn requirement on Host is what justified the async-trait choice from the cross-cutting decisions.

//! Per-invocation context passed to every tool's `execute`.

use std::sync::Arc;

use serde_json::Value;
use tokio_util::sync::CancellationToken;

use crate::{AgentId, Host};

/// Everything a tool body needs from the harness, bundled so capability
/// additions don't change `Tool::execute`'s signature.
pub struct ToolContext {
    pub host: Arc<dyn Host>,
    pub progress: Arc<dyn ProgressSink>,
    pub cancellation: CancellationToken,
    pub agent_id: AgentId,
}

/// One progress payload from a running tool.
#[derive(Clone, Debug)]
pub enum ProgressUpdate {
    Text(String),
    /// Structured payload, tool-defined. Reserved for future use.
    Structured(Value),
}

/// Sink for `ProgressUpdate`s.
pub trait ProgressSink: Send + Sync {
    fn send(&self, update: ProgressUpdate);
}

lib.rs additions

mod tool_context;

pub use tool_context::{ProgressSink, ProgressUpdate, ToolContext};
