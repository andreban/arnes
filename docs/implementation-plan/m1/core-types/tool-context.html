feat/tool-context

The bundle every Tool::execute receives: a host handle, a progress sink, a cancellation token, the invoking agent's ID, and a sub-agent spawn handle. The Tool trait itself lives in M2; the context lives here so phase 4's test scaffolding can build one and M2 lands tools against an already-frozen shape.

Goal

Ship ToolContext, ProgressSink, ProgressUpdate, and the SubAgentSpawner stub. Last PR in phase 2; closes out the core type vocabulary so phase 3 (usage) can build on it.

Files touched

  • new: crates/arnes-core/src/tool_context.rs
  • modify: crates/arnes-core/src/lib.rs
  • modify: root + arnes-core Cargo.toml — add tokio-util with the rt feature.

Discussion

1. Why bundle into a context struct at all? agent-rig (and many tool-calling APIs) pass a few values to tool execution. Bundling them into one struct means adding a new capability (timing budget, log tap, trace ID, …) is a struct field change, not a trait signature change. Tool::execute stays async fn execute(&self, input: Value, cx: &ToolContext) -> ToolResult forever; the cx grows.

2. The early arrival of tokio in arnes-core. ToolContext.cancellation: CancellationToken comes from tokio_util::sync::CancellationToken, which pulls tokio into arnes-core's dep tree starting with this PR. That's earlier than phase 4 (where Session actually runs anything on a runtime), but unavoidable if ToolContext lives here.

Alternatives considered:

  • Defer ToolContext to M2's first PR: cleaner sequencing, but means M2 has to design the type while also writing the first tool. Splitting now lets phase 2 settle the shape.
  • Use futures::future::AbortHandle instead: runtime-agnostic, but agent-rig and both adapters use tokio anyway; abstracting over runtime is ceremony for nothing.
  • Use a callback for cancellation: more flexible but harder to compose; tokio's cancellation token is the idiomatic choice in tokio code.

Decision: keep ToolContext in phase 2; accept the early-tokio cost.

3. ProgressSink as trait, not a channel. Tools emit progress; Session turns those into EventKind::ToolCallUpdate events (M2). The trait-based shape means the session can implement it on its event-translation side without exposing channel types here. ProgressUpdate has both Text (V1 default) and Structured (post-V1 sub-agent tools emitting nested events).

4. SubAgentSpawner stub. Sub-agents are post-V1 (see future-compat table). The trait exists so the field type is stable; the V1 implementation either:

  • Returns Err(CoreError::Session("sub-agents are post-V1".into())) — recoverable, callers can branch.
  • Panics with unimplemented!() — explicit "you should not be calling this at V1," loud if anyone does.

Recommendation: unimplemented!() for the V1 impl. M1 has no caller, so the panic is never reached. Post-V1, the body gets filled in; the test against the panic catches an accidental partial enable.

Where does the actual impl SubAgentSpawner live at M1? Phase 4's Session constructs the ToolContext for its tools (when they exist in M2); for M1 there are no tools, so no ToolContext ever gets built outside tests. Phase 4 test scaffolding ships a NullSubAgentSpawner for in_memory_host setups.

5. Arc<dyn ...> everywhere? host: Arc<dyn Host>, progress: Arc<dyn ProgressSink>, spawn_subagent: Arc<dyn SubAgentSpawner>. Reasons:

  • Tools are dyn Tool in ToolRegistry; their execute takes &ToolContext not &ToolContext<F, H, ...>.
  • ToolContext needs to be constructible without the caller knowing the concrete Host impl.
  • Arc is the right shared-ownership primitive for multi-tool, possibly-concurrent execution.

The dyn requirement is what justifies the async-trait choice from the cross-cutting decisions.

//! Per-invocation context that every tool's `execute` receives.
//!
//! The `Tool` trait itself lands in M2; this PR ships the context type
//! so M2 can land tools against an already-frozen shape, and phase 4's
//! test scaffolding can construct one without churn.

use std::sync::Arc;

use async_trait::async_trait;
use serde_json::Value;
use tokio_util::sync::CancellationToken;

use crate::{AgentId, Host, Result};

/// Everything a tool body needs from the harness, bundled into one
/// struct so capability additions never change the `Tool::execute`
/// trait signature.
pub struct ToolContext {
    /// OS-resource access. Tools route every filesystem / process call
    /// through this.
    pub host: Arc<dyn Host>,

    /// Progress / partial-result emitter. The session translates each
    /// update into a `SessionEvent`.
    pub progress: Arc<dyn ProgressSink>,

    /// Cooperative cancellation. Tools poll this between work units
    /// and bail out cleanly when set.
    pub cancellation: CancellationToken,

    /// Which agent invoked this tool. V1 always `AgentId::Root`;
    /// post-V1 sub-agent tools pass their own ID through.
    pub agent_id: AgentId,

    /// Sub-agent spawn handle. V1 impls panic on call; the field
    /// exists so future sub-agent-aware tools compile against the M1
    /// trait surface unchanged.
    pub spawn_subagent: Arc<dyn SubAgentSpawner>,
}

/// One progress payload from a running tool.
#[derive(Clone, Debug)]
#[non_exhaustive]
pub enum ProgressUpdate {
    /// Plain text progress. V1's default.
    Text(String),
    /// Structured payload — tool-defined.
    /// Reserved for post-V1 sub-agent tools emitting nested events
    /// the session translates into child `SessionEvent`s.
    Structured(Value),
}

/// Sink for `ProgressUpdate`s. Adapter-side: the session implements
/// this to fold updates into its own event stream.
pub trait ProgressSink: Send + Sync {
    fn send(&self, update: ProgressUpdate);
}

/// Sub-agent spawner. V1 implementations either return an error or
/// panic; the trait exists so `ToolContext.spawn_subagent`'s type is
/// stable.
#[async_trait]
pub trait SubAgentSpawner: Send + Sync {
    async fn spawn(&self, spec: SubAgentSpec) -> Result<SubAgentHandle>;
}

/// Sub-agent specification. Body lands post-V1; opaque at M1.
#[derive(Clone, Debug, Default)]
pub struct SubAgentSpec;

/// Handle returned by a successful sub-agent spawn. Body lands post-V1;
/// opaque at M1.
#[derive(Clone, Debug, Default)]
pub struct SubAgentHandle;
