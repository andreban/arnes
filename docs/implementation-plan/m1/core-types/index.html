M1 · Phase 2

Core types

Define the vocabulary the rest of the workspace depends on. Six PRs, each one file (plus the deps that file needs), each with its own discussion of the architectural choices it represents. The type shapes also encode the design's sub-agent commitments from M1 onward.

PRs in this phase

OrderPROne-line goal
1 feat/error-type The crate's error enum (small at M1; grows with each milestone).
2 feat/agent-identity AgentId and ModelKey — the identity vocabulary.
3 feat/message-types Message + ContentBlock. Includes the thinking-blocks discussion.
4 feat/frontend-trait Frontend trait, SessionEvent, EventKind, M3 permission stubs.
5 feat/host-trait Host trait, terminal/dir types, LocalHost default-Unsupported impl.
6 feat/tool-context ToolContext, ProgressSink, SubAgentSpawner stub.

Order matters: each PR's code references types from earlier PRs in this phase. Specifically: agent-identity is referenced by message types (none directly at M1) and by frontend (SessionEvent carries an AgentId); host references its own types only; tool-context bundles host + agent-identity + the not-yet-existing progress sink. Building bottom-up keeps the compiler green between PRs.

The lib.rs re-exports are extended in each PR — whoever adds a new pub type also adds the pub use line. No separate re-exports PR.

Cross-cutting decisions (settled)

Three choices apply to multiple PRs in this phase. Captured here so each PR doc can reference them rather than re-litigate.

1. async-trait for dyn-compatible async traits. Frontend is generic in Session<F: Frontend, H: Host> (no dyn required), but Host is held as Arc<dyn Host> in ToolContext — so Host must be dyn-compatible. Native async fn in traits (stable since Rust 1.75) does not produce dyn-compatible traits by default. We use async-trait — macro that boxes the returned future; small per-call alloc overhead, ecosystem-standard. Applied to Frontend, Host, SubAgentSpawner, and later Tool in M2. Alternatives considered and rejected: trait_variant::make (more macro magic), hand-rolled Pin<Box<dyn Future>> returns (same overhead, more verbose).

2. No thiserror yet. The M1 enum is small (3–5 variants); hand-written Display and Error impls are ~20 lines and don't pull in a proc-macro build-time dep. Revisit when the enum grows past ~8 variants or the From conversions start to multiply.

3. No #[non_exhaustive] on internal enums. The attribute exists to keep external consumers' match arms compiling across a SemVer minor bump. arnes-core sets publish = false; all consumers are in-tree adapter crates, and we sweep every match site in the same PR that adds a new variant. Marking enums #[non_exhaustive] would silently let a missed match site fall through to a wildcard arm and swallow the new variant; the compile error is the cognition-positive default. Revisit if/when any of arnes-core's types ship on crates.io. (The reasoning matches the AgentId-specific call in the feat/agent-identity doc; this generalizes it.)

Discussion sections in each PR doc

Every per-PR doc in this phase has a Discussion section surfacing the architectural choices the PR represents — even if they look obvious. The point is to make every choice reviewable individually rather than bundling them away. Examples of what gets discussed:

  • error-type: variant naming; growth path; whether to expose From conversions or keep the enum closed.
  • agent-identity: ModelKey versioning question; whether AgentId uses a tagged enum or a more compact representation.
  • message-types: thinking blocks (Claude extended thinking, Gemini 2.5 reasoning); ContentBlock variant set; serde tagging shape (load-bearing for M6 persistence); whether Message::System should be content-blocks too.
  • frontend-trait: StopReason variant set; EventKind exhaustiveness; whether FrontendCapabilities should be a struct or bitflags.
  • host-trait: the conservative ACP-aligned method set; whether to ship list_directory vs delay.
  • tool-context: the early arrival of tokio in arnes-core; SubAgentSpawner stub shape.

Test strategy for the phase

Two integration test files land in crates/arnes-core/tests/ during this phase:

  • local_host_unsupported.rs (lands with feat/host-trait) — one #[tokio::test] per Host method, each calling the default impl on LocalHost and asserting err.kind() == io::ErrorKind::Unsupported.
  • serde_roundtrip.rs (lands with feat/message-types) — round-trip Message through serde_json; pin the on-the-wire JSON shape with a literal-string assertion so a future #[serde(tag = ...)] change has to deliberately update the test.

No shared tests/support/ module yet — that lands in phase 4 with the session scaffolding. Each integration-test file in this phase is self-contained.

Phase acceptance

  • All six PRs merged.
  • cargo check --workspace clean (CI green throughout).
  • cargo test -p arnes-core green; the two integration tests pass.
  • RUSTDOCFLAGS="-D warnings" cargo doc --no-deps -p arnes-core clean — every public item documented.
  • No code in arnes-core spawns a tokio runtime or calls tokio::spawn; the runtime dep is there for the CancellationToken type and for the #[tokio::test] harness only.
