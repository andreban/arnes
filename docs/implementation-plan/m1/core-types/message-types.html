feat/message-types

Message and ContentBlock — the content vocabulary that flows in and out of the LLM, gets persisted to disk in M6, and crosses the wire in ACP and HTTP/WS frames. The serde shape pinned in this PR is load-bearing for years.

Goal

Land a Message enum (per-role) holding Vec<ContentBlock>, with the ContentBlock variants M1 needs plus the variants M2 needs as stubs (so M2 doesn't churn the enum). Pin the JSON wire shape via a round-trip test against a literal string so any future change is deliberate.

What this PR is not

ContentBlock represents complete, post-streaming content — the durable form that lands in conversation history, in M6's JSONL persistence, and in ACP / HTTP message frames. It is not the live stream the frontend renders.

The two-layer model:

  • Storage layer (this PR): Message / ContentBlock. Always complete.
  • Streaming layer (next PR, feat/frontend-trait): SessionEvent / EventKind. Carries deltas (AgentMessageDelta today; ThinkingDelta / block-aware variants under discussion).

Session is the translator: it consumes provider stream events, emits delta events to the frontend for live rendering, and assembles the complete Message with its ContentBlocks when the turn ends. The "how do thinking blocks stream?" question lands in the feat/frontend-trait discussion, not here.

Discussion

This is the PR with the most genuine design weight in the phase. Every choice here is hard to revisit later (persistence file format, ACP payload shape, frontend rendering assumptions all build on it).

1. Thinking blocks (the previously-missed concern)

Modern LLMs emit a content type that isn't the model's response text: the model's reasoning / thinking. arnes must represent this as a first-class ContentBlock from M1, not bolt it on later.

ProviderWhat's emittedWire shape
Anthropic (Claude with extended thinking) Plain-text thinking + occasionally encrypted thinking {type: "thinking", thinking: "..."}; {type: "redacted_thinking", data: "encrypted-blob"}
Google (Gemini 2.5 Flash/Pro thinking mode) Reasoning text marked with a thought: true flag on the part part with thought: true
OpenAI (o-series, gpt-5) Reasoning tokens, mostly opaque to caller Reasoning summary or hidden; token counts in usage

Why arnes cares from M1:

  • Persistence (M6) needs to record it — an honest replay should include what the model was thinking, not just what it said. If we don't ship the variant now, M6's JSONL gets a breaking-shape change when we do.
  • Frontends choose what to do with it — TUI may render in dim color or hide behind a key; ACP forwards to the editor; HTTP streams it for inspector tools. The harness shouldn't pre-decide.
  • Cost accounting attributes it — TurnUsage.tokens.thinking already exists in the design (see metering module spec). Without a thinking content block, the token count is unattributable to any visible artifact.
  • M1's Gemini integration will emit them if the model is configured for thinking mode. Skipping this variant means M1 silently drops content that the API returned.

Decision: M1 ships a ContentBlock::Thinking { text: String } variant. We skip RedactedThinking for now since we're Gemini-only at M1 and Gemini doesn't produce encrypted blobs; adding the variant later (when we wire Anthropic) will require a sweep of match sites, which is what we want — see the phase cross-cutting decisions for why we skip #[non_exhaustive]. signature field (Anthropic's signed-thinking attestation) is also deferred until Anthropic lands.

2. ContentBlock variant set at M1

After the thinking discussion, the M1 set is:

  • Text { text: String } — M1 constructs and renders.
  • Thinking { text: String } — M1 constructs (from Gemini); frontends choose to render.
  • ToolUse { id: String, name: String, input: serde_json::Value } — declared so M2 doesn't churn the enum; M1 never constructs.
  • ToolResult { tool_use_id: String, content: serde_json::Value, is_error: bool } — same M1 rationale.

Deliberately deferred variants (add when there's a real consumer):

  • RedactedThinking { data: String } — Anthropic-specific; add when we wire Anthropic.
  • Image { source: ImageSource } — multimodal; M4 is when prompt-building lands, image input is plausibly M5+.
  • Document { source: DocSource } — PDF / file upload; same timing.
  • Citation { ... } — Claude RAG-specific; defer.

3. Serde tagging shape (load-bearing)

Three options for representing ContentBlock variants in JSON:

  • Internally tagged (#[serde(tag = "type")]): {"type": "text", "text": "hi"}. Matches Anthropic's API shape directly. Compact and readable. Recommended.
  • Adjacently tagged (#[serde(tag = "type", content = "data")]): {"type": "text", "data": {"text": "hi"}}. More uniform for tooling; slightly less readable.
  • Externally tagged (default): {"Text": {"text": "hi"}}. Verbose and Rust-flavored; bad fit for JSON.

The persistence format (M6 JSONL) and the ACP wire format will both read whatever shape we ship here. Decision: internally tagged with rename_all = "snake_case", matching the Anthropic-style on-the-wire convention. Pinned by a literal-string assertion in the round-trip test.

4. Message::System: String or Vec<ContentBlock>?

The user/assistant roles need Vec<ContentBlock> for multi-part messages (text + tool use + thinking, etc.). The system role carries just instructions. Two options:

  • System { content: String } (chosen): simpler, matches "one system instruction per turn" idiom, matches most provider APIs at their simplest.
  • System { content: Vec<ContentBlock> } with text-only enforced: more uniform with user/assistant; allows future cache_control annotations per system block (Anthropic prompt caching).

Provider caching matters for cost (huge win on long system prompts) but lands later (post-M1). The decision is "make this simple now; introduce the block-list shape when caching wiring shows up." That shape change requires sweeping every site that constructs or matches on Message::System, which is exactly the kind of cognition the compile-error path gives us.

5. Helper constructors

Add the obvious one (Message::user_text) so tests and the scripted-LLM in phase 4 don't have to spell out the vec![ContentBlock::Text { ... }] ceremony every time. Other constructors (::assistant_text, ::tool_result) earn their place when they have a caller.

Code skeleton

// Copyright 2026 Andre Cipriani Bandarra
// SPDX-License-Identifier: Apache-2.0

//! Message + content-block vocabulary.

use serde::{Deserialize, Serialize};
use serde_json::Value;

/// A message in conversation history.
#[derive(Clone, Debug, Serialize, Deserialize)]
#[serde(tag = "role", rename_all = "snake_case")]
pub enum Message {
    User { content: Vec<ContentBlock> },
    Assistant { content: Vec<ContentBlock> },
    System { content: String },
}

/// One part of a message's content.
#[derive(Clone, Debug, Serialize, Deserialize)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum ContentBlock {
    Text { text: String },
    /// Model reasoning, distinct from response text. Frontends choose
    /// whether to display.
    Thinking { text: String },
    ToolUse {
        id: String,
        name: String,
        input: Value,
    },
    ToolResult {
        tool_use_id: String,
        content: Value,
        is_error: bool,
    },
}

impl Message {
    /// Convenience constructor: a single-text-block user message.
    pub fn user_text(text: impl Into<String>) -> Self {
        Self::User {
            content: vec![ContentBlock::Text { text: text.into() }],
        }
    }
}

// Copyright 2026 Andre Cipriani Bandarra
// SPDX-License-Identifier: Apache-2.0

use arnes_core::{ContentBlock, Message};

#[test]
fn message_user_text_roundtrip() {
    let m = Message::User {
        content: vec![
            ContentBlock::Text { text: "hi".into() },
            ContentBlock::Thinking { text: "let me think".into() },
        ],
    };

    let json = serde_json::to_string(&m).unwrap();
    let back: Message = serde_json::from_str(&json).unwrap();

    // Structural round-trip.
    match back {
        Message::User { content } => {
            assert_eq!(content.len(), 2);
            assert!(matches!(content[0], ContentBlock::Text { .. }));
            assert!(matches!(content[1], ContentBlock::Thinking { .. }));
        }
        _ => panic!("expected User variant"),
    }
}

#[test]
fn message_wire_shape_is_pinned() {
    // Pin the on-the-wire JSON so any future #[serde(tag = ...)] change
    // forces a deliberate test update, not a silent format break.
    let m = Message::User {
        content: vec![ContentBlock::Text { text: "hi".into() }],
    };
    let json = serde_json::to_string(&m).unwrap();
    assert_eq!(
        json,
        r#"{"role":"user","content":[{"type":"text","text":"hi"}]}"#,
    );
}

#[test]
fn system_message_is_plain_string() {
    // System currently carries a String (not Vec<ContentBlock>).
    // Shape change requires a deliberate migration; see message-types
    // PR plan, Discussion section 4.
    let m = Message::System { content: "be helpful".into() };
    let json = serde_json::to_string(&m).unwrap();
    assert_eq!(json, r#"{"role":"system","content":"be helpful"}"#);
}
