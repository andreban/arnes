feat/agent-identity

AgentId and ModelKey — the identity vocabulary used by usage tracking, persistence rows, ACP _meta fields, and every SessionEvent. Small file, large blast radius: every later PR's signatures reference these.

Goal

Ship AgentId (with the post-V1 sub-agent variant in place but never minted at M1) and ModelKey (the provider / model cost-accounting key). The shapes encode the sub-agent commitments — later PRs and milestones depend on these types not changing shape when sub-agents land.

Files touched

  • new: crates/arnes-core/src/identity.rs
  • modify: crates/arnes-core/src/lib.rs — declare module, re-export AgentId + ModelKey.
  • modify: workspace root Cargo.toml — add uuid to [workspace.dependencies].
  • modify: crates/arnes-core/Cargo.toml — add uuid = { workspace = true }.

Discussion

1. Why uuid with v7, not ulid? UUID v7 (RFC 9562, finalized 2024) is the standardized time-sorted 128-bit ID. It has the same properties ULID was designed for (time-sortable, collision-resistant) but is universally recognized by databases, log tools, SDKs, and editors. The uuid crate is one of the most battle-tested in the Rust ecosystem. No realistic reason to pick ULID for new code in 2026.

2. AgentId as enum vs newtype. Choices:

  • Enum (chosen): Root | SubAgent(Uuid). Clear at the call site whether a particular agent is the root or a sub-agent. Pattern matching surfaces the distinction.
  • Newtype: struct AgentId(Uuid) with a magic "all zeros" or similar for root. More compact but loses the type-level distinction.
  • Just Uuid: same downsides as newtype plus no semantic affordance.

The enum costs nothing extra at runtime (SubAgent(Uuid) takes 16 bytes + discriminant; Root is one variant discriminant) and makes the V1-only-creates-Root invariant easy to grep for and lint against. No #[non_exhaustive] — the enum is closed, and the phase-2 cross-cutting decisions skip the attribute across the crate anyway.

3. Where does the sub-agent kind/role live? A real sub-agent system distinguishes sub-agent instances (one specific running agent) from sub-agent kinds (code-reviewer, summarizer, planner, …). Tempting question: should AgentId::SubAgent carry both?

Decision: no. AgentId is the identifier — like a primary key. The kind/role lives at the registration site for the sub-agent: in arnes' design, sub-agents are registered as agent-rig AgentTools, and whatever arnes-side config struct declares those sub-agents carries their kind/role/system-prompt/tool-allowlist. The spawned run gets a UUID at dispatch time that flows into the child's AgentId; the kind is recoverable by looking up the registration, not by inspecting the ID.

Reasons to keep them separated:

  • Different concerns. Identifier vs description-of-what. Mixing them pushes every consumer that just wants identity to also handle "what kind was that?"
  • We don't know the right shape for "kind." Fixed enum (SubAgentKind::CodeReviewer | Summarizer | ...), free-form String (user-defined sub-agents), capability bag (Vec<Capability>), or SKILL-style markdown card? Picking now is picking blind — and it'll be picked by whoever designs the arnes-side sub-agent registration, not by this PR.
  • Migration cost is symmetric. Changing SubAgent(Uuid) to SubAgent { id, kind } is a breaking change to the variant (tuple→struct). The minimal shape is the one we're least likely to need to revise.

4. ModelKey: provider + model_id is enough? Question worth surfacing: model versions like gemini-2.5-flash-001 vs gemini-2.5-flash-latest vs gemini-2.5-flash exist. Cost-wise they're priced the same; behavior-wise they can differ. Options:

  • Treat the version suffix as part of model_id (chosen for M1). ModelKey { provider: "gemini", model_id: "gemini-2.5-flash-001" }. Lets pricing TOML key on whatever granularity each model uses; matches what agent-rig reports back from the wire.
  • Add a separate version field. Cleaner semantically but most pricing data doesn't break down to version; over-engineered for what we're doing now.

Keep it at two fields for M1; revisit if M2/M3 pricing or routing logic actually needs the split.

5. Derives. Clone, Debug, Eq, PartialEq, Hash on both types. Hash is needed because CumulativeUsage indexes by (AgentId, ModelKey) in a HashMap (phase 3). Eq + PartialEq are pure-equality types — trivial here. Clone because these are passed by value through SessionEvent and Usage records. No Serialize/Deserialize yet — persistence (M6) and ACP (phase 6) need them and will add the derive then. The uuid crate's serde feature is opt-in via crate features on uuid itself, so deferring keeps the dep tree smaller for now.

// Copyright 2026 Andre Cipriani Bandarra

//! Identity types for agents and models.

use uuid::Uuid;

/// Identifies an agent within a session.
#[derive(Clone, Debug, Eq, PartialEq, Hash)]
pub enum AgentId {
    Root,
    SubAgent(Uuid),
}

/// Identifies a model for cost accounting and usage attribution.
///
/// The pair `(provider, model_id)` is the natural key; pricing data
/// is indexed by it, and per-model usage breakdowns bucket by it.
#[derive(Clone, Debug, Eq, PartialEq, Hash)]
pub struct ModelKey {
    pub provider: String,
    pub model_id: String,
}

mod identity;
