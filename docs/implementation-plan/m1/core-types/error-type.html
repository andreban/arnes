feat/error-type

Stand up the crate's error type. Tiny enum at M1 with one variant reserved for the session loop; designed so each later PR adds one or two variants without churning the public API.

Goal

arnes_core::Result<T> and arnes_core::CoreError exist and can be returned from trait methods in later PRs of this phase. That's the whole job. No From impls, no rich variants, no catch-all Other.

Files touched

  • new: crates/arnes-core/src/error.rs
  • modify: crates/arnes-core/src/lib.rs — declare module, re-export CoreError + Result.

No Cargo.toml changes — the per-phase decision is no thiserror at this stage (see phase cross-cutting decisions).

Discussion

The architectural choices to settle in this PR's review:

1. What variants does the enum need at M1, given no other code has landed yet? Strictly: zero, because no in-tree code returns it. Pragmatically: at least one placeholder so the type can flow through trait signatures (Frontend::request_permission can return Result<Permission> in a later PR without needing error.rs to be re-touched). Recommendation: a single Session(String) variant earmarked for the session loop.

2. Growth path. What does this enum look like at the end of M1? Plausibly: 

pub enum CoreError {
    Session(String),     // session loop runtime errors
    Pricing(String),     // pricing-registry lookup / TOML parse errors
    Io(io::Error),       // wrapping Host io errors when they cross the boundary
}

At ~5 variants we should re-evaluate the no-thiserror decision; at ~8 variants thiserror probably becomes worth it.

What does not belong here. Adapter-specific errors (ACP protocol / transport, HTTP framing, TUI render errors) live in their own crates. arnes-core is intentionally ignorant of UIs and transports (see arnes-core non-goals); putting an Acp variant in CoreError would invert that dependency. Each adapter crate defines its own error type (arnes_acp::AcpError, etc.) and converts to/from CoreError at its boundary — typically wrapping a CoreError::Session inside the adapter error rather than the other way around.

3. String message vs structured fields. Stringly-typed messages are easy to construct but lossy for callers who want to programmatically match on the cause. M1 has no callers matching on errors (every consumer just propagates), so String messages are fine. Revisit when the first caller wants to branch on the failure mode.

4. From impls. Skip until the first conversion is actually needed. Adding From<io::Error> the moment we have an Io variant is reasonable; adding it pre-emptively isn't.

5. The Result alias. Standard pattern; saves typing across the crate. Defined in the same module as the error type so a single use crate::Result reads as expected.

//! Error type for the crate.
//!
//! Hand-written `Display` and `Error` impls; no `thiserror` at M1
//! (see [Phase 2 cross-cutting decisions]
//! (../../docs/implementation-plan/m1/core-types/index.html#cross-cutting)).

use std::fmt;

/// The crate's unified error type. New variants are added in the PR that
/// first needs them.
#[derive(Debug)]
#[non_exhaustive]
pub enum CoreError {
    /// Runtime failure inside the session loop (e.g. agent-rig stream
    /// terminated unexpectedly). Variant exists so the type can be
    /// threaded through signatures before the session loop lands.
    Session(String),
}

impl fmt::Display for CoreError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            CoreError::Session(msg) => write!(f, "session error: {msg}"),
        }
    }
}

impl std::error::Error for CoreError {}

/// Convenience alias used throughout the crate.
pub type Result<T> = std::result::Result<T, CoreError>;

#[non_exhaustive] on the enum so adding variants in later PRs isn't a breaking change for any (future) external consumer. Debug derived so error chains print usefully in panic! output and test failures.
