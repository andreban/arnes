Adapter

arnes-tui

The terminal frontend: a live, persistent input box at the bottom, a streaming transcript above. Implements the Frontend trait by translating SessionEvents into screen updates. Uses LocalHost — the filesystem is right here, no need to delegate.

Built as the parallel testbed. The TUI is not a single late-stage milestone. A minimal version — just an input box and a streaming output pane — lands at M1 alongside the minimal ACP adapter, and every subsequent milestone surfaces its new capability in both frontends at the same time. The full layout described below is the end state, reached incrementally. See the roadmap for what the TUI looks like at each milestone.

Why not write our own renderer like pi-tui? Because the point of arnes is the harness, not the TUI. ratatui's differential renderer + crossterm's raw mode give us 90% of pi-tui for 0% of the maintenance. If we ever outgrow it, that's a single-crate replacement.

Screen layout

Three ratatui regions: scrolling transcript, status line, input. Matches the Book Chapter 7 layout.

The Frontend impl

All UI mutations funnel through a single channel from the Frontend impl to the render task. The agent loop pushes events; the render task drains the channel and updates ratatui state. 

pub struct TuiFrontend {
    tx: mpsc::UnboundedSender<UiCommand>,
}

#[async_trait]
impl Frontend for TuiFrontend {
    async fn on_event(&self, ev: SessionEvent) {
        let _ = self.tx.send(UiCommand::Event(ev));
    }

    async fn request_permission(&self, req: PermissionRequest) -> Permission {
        let (tx, rx) = oneshot::channel();
        let _ = self.tx.send(UiCommand::Permission(req, tx));
        rx.await.unwrap_or(Permission::Deny)
    }
}

enum UiCommand {
    Event(SessionEvent),
    Permission(PermissionRequest, oneshot::Sender<Permission>),
    UserInput(String),
}

Three tasks, one channel

The TUI binary spawns three tokio tasks; they communicate over the UiCommand channel.

  1. Render task. Owns the ratatui Terminal, drains UiCommand, mutates AppState, calls terminal.draw(...) on each frame. Caps to ~60fps.
  2. Input task. Reads crossterm::event::EventStream, handles editor keybindings locally (cursor movement, backspace, paste), and on Enter sends UiCommand::UserInput(text) to the render task and calls session.prompt(text) to start a turn.
  3. Agent task. Runs session.prompt(); events flow back through TuiFrontend::on_event into the channel. Cancellable via Esc — the input task aborts the JoinHandle.
A single channel keeps the three tasks loosely coupled and the renderer single-threaded.

Permission UX

Sensitive tools (bash, write, edit by default) trigger frontend.request_permission before executing. The TUI pops a modal: 

+--------------------------------------------------------+
| Allow this tool call?                                  |
|                                                        |
|   bash                                                 |
|   rm -rf node_modules && pnpm install                  |
|                                                        |
|   [a] allow once  [A] always for bash  [d] deny  [Esc] |
+--------------------------------------------------------+

"Always for bash" sets a per-session policy in the Session's permission cache so we don't pester the user every time. The cache is in-memory; restarting the session resets it.

Cancellation

Esc at the input box does nothing when no agent task is running. When one is running, Esc calls session.cancel() which aborts the agent-rig stream and propagates an AbortSignal into any in-flight tool. The TUI shows "cancelled" in the transcript and unlocks the input.

Slash commands

TUI-only commands that don't go to the model:

CommandEffect
/clearReset the transcript (history stays in JSONL; new in-memory session)
/compactForce compaction now
/model <name>Switch model mid-session
/toolsShow active tools
/skillsList loaded skills + locations
/skill:<name>Inject a skill body into the next turn (Chapter 9)
/reloadRe-scan extensions, skills, AGENTS.md

What this adapter deliberately does not do

  • No mouse support in V1. Keyboard is enough; mouse adds a pile of edge cases (selection vs. native terminal selection, scroll wheel conflicts) we don't want to debug yet.
  • No inline images. Useful, but a big native-protocol yak (Kitty/iTerm2). Drop it in once the core is stable.
  • No theming. Use ratatui's default style for V1. A theme system can land as an extension contribution later.

The adapter is done when

Running arnes drops you into a live session: streaming output, working input box, permission dialogs for destructive tools, Esc cancellation, slash commands, persistent JSONL log. That is the local-developer story complete.
