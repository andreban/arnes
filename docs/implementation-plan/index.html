Implementation plan

arnes — a modular coding harness in Rust

This is the plan for building arnes (from Portuguese arnês, "harness") — a coding agent harness in Rust, built on top of agent-rig for the LLM runtime, and designed from day one to be exposed through multiple frontends: a TUI, the Agent Client Protocol, HTTP/WebSockets, and eventually a GUI.

What we are building

The same coding harness, behind four different faces:

Hexagonal: a single core, four adapters in front, two interchangeable hosts behind the tools, and agent-rig under the floor.

Grounding in the book

The companion Build Your Own Harness describes the conceptual model in ten chapters. This plan picks up exactly where that book leaves off and turns the concepts into a concrete Rust implementation. The shape stays identical:

Book chapterarnes module / adapter
1. Streaming LLM clientagent-rig (already exists)
2. Your first tool callarnes-core::tools
3. The agent loopagent-rig::AgentRunner + thin Session wrapper
4. A real coding toolkitarnes-core::tools (read, write, edit, bash) using Host

9. Skillsarnes-core::skills
10. Compactionarnes-core::compaction
— (new)arnes-acp, arnes-http, arnes-gui

What this document is and is not

What this is
  • An architectural plan: crate split, interfaces, data flow.
  • A phased roadmap with end-states per milestone.
  • A concrete mapping from book chapters to Rust modules.
  • A method-by-method map for the ACP adapter.
What this is not
  • Code. No .rs files yet — just decisions.
  • A schedule. Milestones are ordered; durations are not estimated.
  • An API freeze. Names and signatures will shift as we implement.
  • A vendor selection (the GUI stack is intentionally left open).

Reading order

  1. Modular design — the ports-and-adapters split, the two key traits (Frontend and Host), and the Cargo workspace layout.
  2. arnes-core — the harness crate that holds everything not specific to a frontend: session, prompt, persistence, compaction, extensions, skills.
  3. The four adapter chapters — each is independently readable: TUI, ACP, HTTP / WebSockets, GUI.
  4. Roadmap — the order we build things and what works at the end of each milestone.

Key decisions, up front

DecisionChoiceWhy
Language Rust agent-rig is Rust; ACP/HTTP servers want async + good ecosystem.
LLM runtime agent-rig Provider-agnostic, streaming, parallel tools, structured output, auth hook. Saves Chapters 1–3 of the book.
Tool host Trait with two impls: LocalHost and AcpHost ACP delegates filesystem and terminal to the client; tools must not hard-code OS calls.
Frontends Implement a small Frontend trait Lets arnes-core drive any of TUI / ACP / HTTP / GUI without conditionals.
Workspace Cargo workspace, many small crates Adapters opt into core; users only build what they use.
Persistence JSONL session logs See Book Chapter 6. Append-only, crash-safe, human-readable.
Providers (Phase 1) Gemini + Ollama (what agent-rig ships) Anthropic/OpenAI added later as agent-rig features or local adapters.

Open questions, intentionally deferred

  • GUI stack. Tauri (share the binary, web UI inside), egui / iced (native), or a web app talking to the HTTP/WS adapter. Pick when we get there; the modular design makes any of them work.
  • Permission UX in non-TUI adapters. ACP has session/request_permission; HTTP/GUI need their own equivalent. Briefly addressed per adapter; design fully when M8 lands.
