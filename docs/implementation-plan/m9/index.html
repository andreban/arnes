Milestone 9 · The fourth face

GUI

The last milestone. The same harness as M7, exposed through a graphical interface. Stack choice is intentionally local — the modular design means the GUI is just another Frontend impl, and none of the work below changes if we switch toolkits later.

Why M9 is last

Two reasons. First, by M8 we have HTTP/WS — which means the simplest GUI option (a browser app talking to arnes-serve) is free the moment that adapter ships. Second, every GUI stack imposes its own asymmetric maintenance burden, and we'd rather absorb that after the harness is genuinely complete than risk derailing core milestones.

First: pick a stack

Three viable paths, described in detail on the adapter page. M9 begins with a one-page ADR documenting the choice and the trade-off accepted. Defaults the plan leans toward, in order of cheapness:

StackCheapest becauseCatches
Web app on arnes-http Zero new Rust. M8 already exists. Use any web framework you like for the front-end. Requires arnes-serve running. Two processes (browser + server). Permission UX in the browser.
Tauri Web UI inside a system webview. arnes-core in-process via Tauri command bridge. Single binary distribution. Webview baggage on each OS. Some UI work in JS/TS.
egui or iced (native) Pure Rust. Single binary. No webview. Fast. All UI work in Rust. Smaller widget library than the web.

The rest of this milestone assumes the web-on-HTTP path. If we pick differently, the implementation tasks shift but the shape of GuiFrontend (the trait impl) and the FrontendCapabilities advertisement do not.

Layout

Sessions sidebar, transcript with rich rendering, input at the bottom. Same shape as the TUI, more pixels and richer media.

GuiFrontend

Identical surface to HttpFrontend and TuiFrontend — the trait does not know it's driving a browser: 

// Web-on-HTTP: GuiFrontend lives on the server side. The browser is a
// WebSocket client. There is no new arnes crate; we just write a web
// project that consumes M8's WS.

// Tauri / native variant: arnes-gui crate.
pub struct GuiFrontend {
    state: Arc<Mutex<GuiState>>,
    redraw: Arc<dyn Fn() + Send + Sync>,
}

#[async_trait]
impl Frontend for GuiFrontend {
    async fn on_event(&self, ev: SessionEvent) {
        self.state.lock().await.apply(ev);
        (self.redraw)();
    }
    async fn request_permission(&self, req: PermissionRequest) -> Permission {
        // Open modal, await user choice via oneshot, return decision.
    }
    fn capabilities(&self) -> FrontendCapabilities {
        FrontendCapabilities {
            markdown: true,
            images: true,
            embedded_resource: true,
            permission_ui: true,
        }
    }
}

Rich rendering enabled by capabilities

The web frontend advertises capabilities the TUI can't — images: true, embedded_resource: true — and the system prompt picks them up. Tools that produce images can emit them as ContentBlock::Image and the GUI will render them inline. The diff display for edit can be a real side-by-side instead of plain text.

Three rendering upgrades the GUI gets that the TUI deliberately skips:

  • Real markdown. Headings, lists, code blocks with syntax highlighting via highlight.js or a Rust port.
  • Structured diffs. edit tool emissions render as a real diff view (line-by-line, additions/removals coloured).
  • Drag-and-drop attachments. Drop a file or image into the input box to attach it as a ContentBlock::Image or ContentBlock::EmbeddedResource in the next user message.
  • Usage panel. A sidebar widget breaks down current session usage: input / output / cache / thinking tokens, known cost (or "— (N turns unpriced)" if any), context-window percentage, per-turn sparkline. Unknown-cost turns surface as a distinct visual state, not collapsed to zero.

Permission UX, GUI flavour

A modal dialog over the transcript with three buttons (Allow, Always for this tool, Deny) and a 60-character preview of the input. Same trait method as the TUI's curses modal; native widget instead of an ASCII box.

Auth in the browser

If the GUI is the browser path: the page asks for the bearer token on first load, stores in localStorage, attaches to every HTTP and WS request. This is V1's "single trust boundary" model: whoever can open the page can drive the harness. Anything more (per-user accounts, OAuth, ...) is post-V1.

Implementation tasks (web-on-HTTP path)

  1. Pick a stack; write the ADR. No new arnes crate if web-on-HTTP.
  2. If web-on-HTTP: set up a small front-end project (any framework you like) under web/ in the repo. Vite + plain TS is plenty.
  3. Connect to arnes-serve via the M8 WebSocket. Render frames into a typed transcript view.
  4. Implement markdown rendering and syntax highlighting in the transcript.
  5. Implement the permission modal as a real dialog component; round-trip via the WS permission_response frame.
  6. Implement the sessions sidebar: fetch GET /v1/sessions; click to load via POST /v1/sessions/.../prompt after attaching the WS.
  7. Implement drag-and-drop file attachments — encode as content blocks in the next outbound prompt frame.
  8. Document the M8 FrontendCapabilities the WS frontend advertises; ensure the system prompt builder consumes them server-side.
  9. Smoke test against a real Gemini-backed arnes-serve; daily-driver use for a week before declaring M9 done.

Implementation tasks (Tauri path, if chosen instead)

  1. Create arnes-gui crate; add Tauri dependency.
  2. Implement GuiFrontend wired to Tauri's event emitter; Session lives in the Rust side.
  3. Front-end work is the same as the web-on-HTTP path; only the transport differs (Tauri commands instead of WS).
  4. Build for macOS, Linux, Windows; document signing requirements per OS.

Testing checklist

  • Smoke: open the GUI; prompt; watch the reply stream.
  • Permission: trigger a destructive bash; modal appears; allow proceeds, deny rolls back to a clean error.
  • Reconnect: kill the WS; verify the GUI shows "disconnected" state and reconnects when the server is back, re-attaching to the same session.
  • Rich rendering: assert markdown, code blocks, diffs, and images all render correctly.
  • Multi-session: open three sessions in three tabs against the same server; verify isolation.

Risks specific to M9

  • Sunk cost on the wrong stack. Mitigation: the choice is reversible because Frontend is the only contract. Switching from web-on-HTTP to Tauri later means a new crate and a port of the front-end; the core doesn't move.
  • Browser security model. Be careful with token storage and CORS. Document threat model: the GUI is for a single trusted user; do not deploy with arbitrary origins allowed.
  • Maintenance burden. A GUI is a long-tail commitment. Be conservative with features; resist the urge to add settings panels and theme editors until users ask.

End state of M9

Open the GUI (browser or desktop); see your sessions in a sidebar; open one; prompt; watch a richly-rendered reply with inline diffs and a working permission modal. Same harness as M1–M7, behind the fourth face. The architecture promise — one core, many consumers — is realized.

After M9

The V1 plan is complete. What lives beyond it — extensions, MCP bridging, multi-tenant HTTP, branching sessions, inline TUI images — is enumerated on the roadmap's Deferred section. Each is its own sub-plan; none of them require rearchitecting what we have built.
