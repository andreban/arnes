Adapter

arnes-http

The networked face of arnes. Same Session, exposed over HTTP and WebSockets so a browser, a remote tool, or a hosted control plane can drive it. Designed to host ACP-over-WS as soon as the upstream spec lands — until then, a small REST + WS surface for plain HTTP clients.

Two surfaces, one binary

HTTP and WebSockets serve different needs and live behind a single axum server:

HTTP (request/response)

For everything that fits a single response: list sessions, get session metadata, list tools, read or update config. No streaming. Plain JSON with normal status codes. Suitable for non-interactive integrations (scripts, CI).

WebSocket (streaming)

One socket per active session. Frames are JSON messages following the same vocabulary as ACP's session/update (so the wire format is portable). Suitable for a browser UI or a hosted client where stdio is not an option.

WebSocket: GET /v1/sessions/{id}/ws

Opening the socket attaches a streaming consumer to the session. Frames are JSON in both directions; the vocabulary aligns with ACP's session/update so the same client code can speak either protocol with a thin adapter.

Client → server frames

{ "type": "prompt", "content": [ { "type": "text", "text": "..." } ] }
{ "type": "cancel" }
{ "type": "set_mode", "mode": "ask" }
{ "type": "permission_response", "id": "...", "decision": "allow" | "deny" }

Server → client frames

Every server-to-client frame carries agent_id (V1 always "root"); attribution is in the protocol from day one so post-V1 sub-agent frames are additive, not breaking. usage payloads additionally carry the ModelKey that produced the turn.

{ "type": "agent_thought_chunk", "agent_id": "root", "text": "..." }
{ "type": "tool_call",  "agent_id": "root", "id": "...", "name": "bash", "input": { ... }, "status": "pending" }

ACP over WebSocket (deferred)

The ACP spec calls out HTTP/WS transport as a work-in-progress. When that lands, the implementation is almost mechanical:

  1. Mount a second route, e.g. GET /acp/ws, that frames upstream's chosen JSON-RPC wire format on the socket.
  2. Hand the framed channel to the same router function that arnes-acp uses for stdio — make_router(session) is transport-agnostic by design.
  3. Done. ACP capability negotiation, methods, bidirectional callbacks all work without changes; AcpHost just talks over a socket instead of a pipe.
One server, multiple route trees, shared core. ACP-over-WS adds without rewriting.

The Frontend impl

HttpFrontend is wired per WebSocket connection. Events go through the socket; permission requests round-trip via a correlated request/response over the same socket. 

pub struct HttpFrontend {
    tx: mpsc::UnboundedSender<ServerFrame>,
    pending_perms: Mutex<HashMap<Uuid, oneshot::Sender<Permission>>>,
}

#[async_trait]
impl Frontend for HttpFrontend {
    async fn on_event(&self, ev: SessionEvent) {
        let _ = self.tx.send(ev.into_server_frame());
    }

    async fn request_permission(&self, req: PermissionRequest) -> Permission {
        let id = Uuid::now_v7();
        let (resp_tx, resp_rx) = oneshot::channel();
        self.pending_perms.lock().await.insert(id, resp_tx);
        let _ = self.tx.send(ServerFrame::PermissionRequest { id, req });
        resp_rx.await.unwrap_or(Permission::Deny)
    }
}

A small dispatcher on the socket's recv side resolves permission_response frames against the pending map.

Host, in this adapter

V1: LocalHost. The server has direct access to the host filesystem — tools read and write there.

This is fine for self-hosted setups where the operator controls who can talk to the server. It is not safe for multi-tenant deployments where untrusted users can submit prompts; an untrusted user with a bash tool would have shell access to the server. Two ways to address that down the road, both deliberately out of scope for V1:

  • A SandboxedEnv impl that runs tools in a container or a chroot with restricted permissions.
  • A RemoteEnv impl where filesystem and terminal calls round-trip to a per-tenant worker (the same trick ACP uses, but with a different transport).

Session lifecycle and state

Sessions live in a process-wide SessionRegistry: a HashMap<SessionId, Arc<Mutex<Session>>>. Created on POST /v1/sessions, deleted on DELETE /v1/sessions/{id}, GC'd if idle for too long. A session can have at most one active prompt at a time; concurrent POST .../prompt requests respond with 409 Conflict.

Authentication

V1: a single bearer token configured at server start. Every request must carry Authorization: Bearer <token>; missing or wrong token returns 401. WS upgrades validate the token in the upgrade request.

V2: pluggable auth provider trait, plus optional per-user scoping (so user A cannot see user B's sessions). Deferred until there is a real multi-user deployment to design against.

CORS, content security, and the browser

If a browser UI talks to the server, CORS must be configured. Default: permissive on /healthz, restrictive on everything else (no *; require an explicit allow-list of origins in the server config).

Non-goals for V1

  • No clustering or sharding. Single process, single host. Scale up before scale out.
  • No multi-tenant isolation. One trust boundary; one token.
  • No metrics surface. Logs only. Prometheus endpoint can come later.
  • No rate limiting. Reverse-proxy handles it if needed.

The adapter is done when

arnes-serve --bind 127.0.0.1:7878 --token $T stays up, accepts POST /v1/sessions + /prompt, streams a browser UI through /ws, and survives a few hours of daily use as your daily-driver remote agent. The ACP-over-WS handler can be slotted in once upstream's spec stabilises.
