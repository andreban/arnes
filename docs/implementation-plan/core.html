Architecture

arnes-core

The crate that everything else depends on. Holds the agent loop wrapper, the tool registry, the system prompt builder, the persistence layer, the extension host, the compactor, and the trait definitions. Knows nothing about UIs, transports, or specific operating systems.

See the type map for a visual reference of what's currently in the crate and how the pieces relate.

How a client uses arnes-core

The shape a client (a TUI, an editor adapter, an HTTP wrapper) sees is small: one entry point (Session), one trait to implement (Frontend), and one method to call in a loop (session.prompt()). Tools, prompt assembly, compaction, persistence, and usage tracking all live behind Session and never appear in the client's call graph.

End-state sketch. Session doesn't exist in the crate yet (it lands in M6). The builder API below is the intended ergonomic shape, not a contract; exact field names may shift once agent-rig's provider config is wired in. 
use arnes_core::{
    EventKind, Frontend, LocalHost, Permission, PermissionRequest,
    Session, SessionEvent, UserInput,
};
use async_trait::async_trait;
use std::sync::Arc;

// 1. Implement Frontend for whatever your UI / transport is.
//    Three methods, two of them with sensible defaults.
struct MyFrontend;

#[async_trait]
impl Frontend for MyFrontend {
    async fn on_event(&self, ev: SessionEvent) {
        match ev.kind {
            EventKind::TextDelta { text }   => print!("{text}"),
            EventKind::ThinkingDelta { .. } => { /* maybe dim, maybe skip */ }
            EventKind::TurnEnd { .. }       => println!(),
            _ => {}
        }
    }

    async fn request_permission(&self, _req: PermissionRequest) -> Permission {
        // Real frontends prompt the user here. AllowOnce makes
        // everything non-interactive.
        Permission::AllowOnce
    }
}

#[tokio::main]
async fn main() -> arnes_core::Result<()> {
    // 2. Wire the session. One builder call assembles frontend + host
    //    + model + tools + (optional) persistence.
    let mut session = Session::builder()
        .frontend(Arc::new(MyFrontend))
        .host(Arc::new(LocalHost))                  // file/terminal I/O
        .model("gemini", "gemini-2.5-flash")
        .with_default_tools()                       // read/write/edit/bash
        .persist_to("~/.arnes/sessions/demo.jsonl")
        .build()
        .await?;

    // 3. Drive turns. Each prompt() call streams events into your
    //    Frontend until the model stops. Compaction, persistence,
    //    system-prompt rebuild, and tool dispatch all happen internally.
    loop {
        let line = read_one_line_from_somewhere();
        if line == "/quit" { break; }
        session.prompt(UserInput::text(line)).await?;
    }

    // 4. Cumulative usage is queryable at any time.
    let usage = session.cumulative_usage();
    println!("total: {:?}", usage.total_known_cost());
    Ok(())
}

Two things worth pinning down on this picture:

  • The client only touches Session and Frontend. Host has a default (LocalHost) you only swap out when you need sandboxing — e.g. running inside an editor that wants to mediate filesystem access. Tools, the system-prompt builder, the compactor, the persistence writer, and the cumulative usage table are all internal to Session.
  • Permission prompts come back through the same trait. When a sensitive tool (bash, write, edit) needs approval, Session calls frontend.request_permission(...) on the same object that receives events. No separate transport, no callback registry.

session — the orchestrator

Session wraps agent_rig::AgentRunner with the pieces agent-rig deliberately leaves out: persistence, system prompt assembly, extension hooks, compaction triggers. prompt() is the single hot path.

Each Session carries an AgentId and an optional parent reference. V1 only ever creates root sessions (parent is None, agent_id is AgentId::Root) — but the fields exist so a future sub-agent built on top of the trait surface doesn't need a breaking change. 

pub enum AgentId {
    Root,
    SubAgent(Uuid),
}

pub struct Session<F: Frontend, H: Host> {
    pub agent_id: AgentId,
    parent:       Option<Weak<Session<F, H>>>,   // V1: always None
    // ... existing fields ...
}

impl<F, H> Session<F, H> {
    pub fn agent_id(&self) -> &AgentId { &self.agent_id }
    pub fn parent_id(&self) -> Option<AgentId> { /* V1: always None */ }

    // No spawn_subagent method. Post-V1 sub-agents are registered as
    // agent-rig AgentTools in the ToolRegistry, not spawned via a
    // separate Session API. See "Future-compatibility: sub-agents".
}
impl<F: Frontend, E: Host> Session<F, E> {
    pub async fn prompt(&mut self, input: UserInput) -> Result<()> {
        // 1. compact if we are nearing context limit
        if self.compactor.should_compact(&self.history) {
            self.compact().await?;
        }

        // 2. rebuild system prompt if any input changed (tools, skills, ...)
        let system = self.prompt_builder.build(&self.cwd);

        // 3. append user message + persist
        let msg = Message::user(input.into_blocks());
        self.history.push(msg.clone());
        self.writer.as_mut().map(|w| w.append(&msg));

        // 4. extension hook: before_agent_start (can mutate prompt/history)
        self.extensions.fire_before_agent_start(&mut system, &mut self.history).await;

        // 5. run agent-rig loop; pump events into the frontend
        let mut stream = self.runner.run_with_system(&system, &self.history, &self.tools);
        while let Some(ev) = stream.next().await {
            let session_event = self.translate(ev);
            self.frontend.on_event(session_event).await;
            self.apply_to_history(&ev);
            if let Some(msg) = self.completed_message(&ev) {
                self.writer.as_mut().map(|w| w.append(&msg));
            }
        }
        Ok(())
    }
}

The whole orchestration fits in one method because every concern it touches is already abstracted. Tools are &dyn Tool from ToolRegistry. Permission gating lives in agent-rig's AuthManager, which we wire to call frontend.request_permission(...). The writer is optional (some adapters may not want persistence).

tools — the registry

agent-rig's Tool trait is concrete enough to use directly. We extend it with the things the book's harness needs but agent-rig doesn't prescribe: 

pub trait Tool: Send + Sync {
    fn name(&self) -> &str;
    fn description(&self) -> &str;
    fn parameters(&self) -> &JsonSchema;

    /// Per-tool guideline bullets injected into the system prompt
    /// (Chapter 5). Empty by default.
    fn prompt_guidelines(&self) -> &[String] { &[] }

    /// Short one-liner for the "Available tools" section. Defaults to
    /// the first line of description().
    fn prompt_snippet(&self) -> &str { /* first_line(self.description()) */ }

    /// Sensitive tools (bash, write, edit) request permission before running.
    /// Default false (read, ls, grep). When true, the session calls
    /// build_permission_request() and matches_scope() — see
    /// M3 § Permission model.
    fn permission_required(&self) -> bool { false }
    fn build_permission_request(&self, input: &Value) -> PermissionRequest { unreachable!() }
    fn matches_scope(&self, scope: &Scope, input: &Value) -> bool { false }

    async fn execute(&self, input: serde_json::Value, cx: &ToolContext) -> ToolResult;
}

/// Everything a tool body needs from the harness, bundled to keep the
/// trait signature stable across future additions.
pub struct ToolContext {
    pub host:          Arc<dyn Host>,
    pub progress:      Arc<dyn ProgressSink>,
    pub cancellation:  CancellationToken,
    pub agent_id:      AgentId,           // which agent invoked this tool
}

pub enum ProgressUpdate {
    /// Plain text update (the default).
    Text(String),
    /// Structured payload — tool-defined. Reserved for future use.
    Structured(serde_json::Value),
}

pub trait ProgressSink: Send + Sync {
    fn send(&self, update: ProgressUpdate);
}

Four details worth pinning down:

  • Tools never touch the OS directly. They receive cx.host and route every filesystem or process call through it.
  • Tools never speak to the frontend directly; they emit progress through cx.progress, which the Session turns into EventKind::ToolCallUpdate.
  • Tools never return Result. They return ToolResult which has an is_error flag. Errors are reported back to the model as data, never as panics (Chapter 2).
  • The context is the extensible seam. ToolContext bundles every harness-provided capability so adding a future capability (timing budget, log tap, etc.) doesn't change the trait signature.

prompt — the builder

Direct translation of the Chapter 5 builder. Slot-based, deduplicated, cwd and date go last so the long stable prefix stays cacheable. 

pub struct SystemPromptBuilder {
    base: Cow<'static, str>,           // hard-coded identity
    tools: Vec<Arc<dyn Tool>>,         // active tools
    user_guidelines: Vec<String>,       // configured by user/extension
    user_append: Option<String>,        // free-form append
    skills: Vec<Skill>,                 // from SkillsCatalog
    context_files: Vec<ContextFile>,    // AGENTS.md tree walk
}

impl SystemPromptBuilder {
    pub fn build(&self, cwd: &Path) -> String { /* ... */ }
}

Cached on the Session; rebuilt only when one of its inputs changes (extension loads a tool, user toggles thinking budget, skills catalog refreshes, etc.). The cache key is structural: hash the inputs and reuse if unchanged.

persist — JSONL writer + reader

Append-only, one row per message, header row carries metadata. Same shape as Chapter 6 of the book. 

pub struct SessionWriter { fh: tokio::fs::File }

impl SessionWriter {
    pub async fn open(path: &Path, header: SessionHeader) -> io::Result<Self>;
    pub async fn append(&mut self, row: SessionRow) -> io::Result<()>;
    pub async fn close(self) -> io::Result<()>;
}

pub enum SessionRow {
    Header(SessionHeader),       // first line: model, tools, cwd, version
    Message(Message),            // role + content blocks
    Compaction(CompactionEntry), // recorded when compact() runs
}

pub async fn load_session(path: &Path) -> io::Result<LoadedSession>;

Each row carries an id (UUID v7) and an optional parent_id. We don't expose branching in V1, but we plumb the fields so it can land later without a format break.

compact — the summarizer

Token estimation by the 4-chars-per-token heuristic (cheap, ~20% slack); trigger at 75% of the model's window; replace history with a SUMMARY user-role message plus the last K turns. 

pub struct Compactor {
    pub trigger_ratio: f32,   // default 0.75
    pub keep_recent: usize,   // default 6
    pub prompt: Cow<'static, str>,
}

impl Compactor {
    pub fn should_compact(&self, hist: &[Message]) -> bool;
    pub async fn run(
        &self,
        hist: &[Message],
        runner: &AgentRunner,
    ) -> Result<Vec<Message>>;
}

Important constraint: only runs between turns. Compacting in the middle of a tool-call/tool-result pair breaks the protocol. The Session::prompt path calls should_compact only at the top of the loop.

usage — tokens and costs

Every turn produces a Usage snapshot from the provider. The session aggregates them into a CumulativeUsage the frontends display. Three states matter: priced (we know the cost), free (explicitly free, e.g. local models), and unknown (no pricing data). They are kept distinct end-to-end; unknown is never silently coerced to zero. 

// arnes-core/src/usage.rs

/// Identifies which model a turn ran against. The natural cost-accounting
/// unit: pricing is keyed by this pair, and the UI reports usage broken
/// down by it.
#[derive(Clone, Eq, PartialEq, Hash)]
pub struct ModelKey {
    pub provider: String,    // "gemini", "ollama", ...
    pub model_id: String,    // "gemini-2.5-pro", "llama3.2", ...
}

pub struct Usage {
    pub agent_id:           AgentId,    // who produced this turn (see frontend.rs)
    pub model:              ModelKey,   // which model billed for it
    pub input_tokens:       u64,
    pub output_tokens:      u64,
    pub cache_read_tokens:  u64,
    pub cache_write_tokens: u64,
    pub thinking_tokens:    u64,
    /// None: pricing not available for this model.
    pub cost: Option<Cost>,
}

pub struct Cost {
    pub input:       Micros,
    pub output:      Micros,
    pub cache_read:  Micros,
    pub cache_write: Micros,
    pub thinking:    Micros,
    pub total:       Micros,
}

/// Integer micros = millionths of a dollar. Six decimal places, no float drift.
pub struct Micros(pub i64);

pub enum ModelCostInfo {
    Priced(ModelPricing),   // bundled or user-supplied
    Free,                   // explicitly free (local Ollama, self-hosted)
    Unknown,                // default for unrecognized models
}

pub struct ModelPricing {
    pub input_per_mtok:        Micros,
    pub output_per_mtok:       Micros,
    pub cache_read_per_mtok:   Option<Micros>,
    pub cache_write_per_mtok:  Option<Micros>,
    pub thinking_per_mtok:     Option<Micros>,
}

/// One row of aggregated usage for a single (agent, model) bucket.
pub struct ModelUsage {
    pub model:                   ModelKey,
    pub input_tokens:            u64,
    pub output_tokens:           u64,
    pub cache_read_tokens:       u64,
    pub cache_write_tokens:      u64,
    pub thinking_tokens:         u64,
    pub turns:                   u32,
    /// Sum of priced turns for this (agent, model) bucket.
    pub known_cost:              Cost,
    pub turns_with_unknown_cost: u32,
}

pub struct CumulativeUsage {
    /// Single source of truth: indexed by (agent, model). A sub-agent that
    /// switched models mid-session has two entries. V1 only ever populates
    /// AgentId::root().
    by_agent_and_model: HashMap<(AgentId, ModelKey), ModelUsage>,
    pub turns_total: u32,
}

impl CumulativeUsage {
    pub fn record(&mut self, u: Usage);

    /// Flatten across agents: total per ModelKey.
    pub fn by_model(&self) -> HashMap<&ModelKey, ModelUsage>;

    /// Flatten across models: total per AgentId.
    pub fn by_agent(&self) -> HashMap<&AgentId, ModelUsage>;

    /// Sum of all priced turns across all (agent, model) buckets.
    pub fn total_known_cost(&self) -> Cost;

    /// Count of all turns whose pricing was Unknown.
    pub fn total_turns_with_unknown_cost(&self) -> u32;
}

Pricing registry

Bundled TOML asset at arnes-core/data/pricing.toml, merged with user overrides at ~/.arnes/pricing.toml. Two tables: [[model]] for exact (provider, model_id) entries and [[provider_default]] for the unmatched-model-on-this-provider fallback (used by self-hosted providers like Ollama where the harness can't enumerate model_ids ahead of time). 

# arnes-core/data/pricing.toml  (bundled; user overrides win)

[[model]]
provider             = "gemini"
id                   = "gemini-2.5-flash"
input_per_mtok       = 0.075
output_per_mtok      = 0.30
cache_read_per_mtok  = 0.01875

[[provider_default]]
provider = "ollama"
cost     = "free"

# Anything not listed defaults to Unknown.

A small fn load_pricing() -> PricingRegistry happens once at session start; registry.lookup(provider, model_id) returns the ModelCostInfo. The session uses that plus per-turn Usage token counts to compute the turn's cost field.

Where usage flows

Every EventKind::TurnEnd carries the turn's Usage, which itself carries agent_id and model. Session maintains cumulative_usage() as a running total accessible to frontends at any time. Persistence (M6) writes a Usage row per turn into the JSONL alongside messages; resume reconstructs the cumulative including the per-agent and per-model breakdowns.

Future-compatibility: sub-agents

Design rule. arnes V1 only ever runs a single (root) agent per session. But the design respects sub-agents as a first-class concept — agent-rig already supports them, and adding them post-V1 must be additive, not a breaking change. The implementation is deferred (see the roadmap); the design is not.

The V1 commitments that keep this true:

SurfaceWhat V1 does
AgentId Real type from M1. V1 only ever constructs AgentId::Root; SubAgent(Uuid) exists in the enum but is never minted.
SessionEvent Restructured as { agent_id, depth, kind: EventKind } from M1. New EventKind variants (e.g. SubAgentStart, SubAgentEnd) get added by sweeping match sites in the same PR — all consumers are in-tree.
Tool::execute Takes a single ToolContext parameter (bundling host, progress, cancellation, agent_id) so the trait stays stable across future capability additions. Sub-agents are not spawned through this context — they're registered as agent-rig AgentTools in the same ToolRegistry tools use, and the parent model invokes them like any other tool.
ProgressSink Carries typed ProgressUpdate (text or structured), not just &str. A tool that wants to stream richer progress payloads can use the Structured variant later.
Usage + CumulativeUsage Every Usage carries agent_id and ModelKey. CumulativeUsage indexes by (agent, model) so cost is reported per backend+model, with per-agent attribution available via by_agent().
PermissionAllowlist Entries are AllowEntry { tool_name, scope, principal } structs, not bare tuples (see M3 § Permission model). V1 only ever creates Principal::Any entries; the field is there.
JSONL SessionRow Message and Usage rows carry agent_id. Reader tolerates unknown variant tags (log + skip rather than fail) so a newer arnes writing rows V1 doesn't recognise can still be loaded.
ACP Outbound session/update notifications include agent_id in _meta from M1. Editors that ignore _meta see flat output; ones that read it can render attribution later.
HTTP/WS WS frames carry agent_id in every event/usage payload.

None of this enables sub-agents at V1. All of it means the post-V1 implementation is "fill in the unimplemented!() stubs and start emitting non-root events" — not "redesign the protocol surface."

extensions — the host

Deferred for V1. The architecture accommodates extensions — the host API below is the V1 design — but we are not building this module in the current roadmap. See Deferred for the rationale. The design is preserved here so that when we return to it, we start from a considered position.

Lifecycle and host API; the choice of how extensions are delivered (cdylib, sub-process, embedded scripting) is deferred to a sub-plan. The host API is fixed first: 

pub struct ExtensionHost {
    extensions: Vec<LoadedExtension>,
}

pub trait Extension: Send + Sync {
    fn register(&mut self, host: &mut ExtensionContext);
}

pub struct ExtensionContext<'a> {
    pub fn add_tool(&mut self, tool: Arc<dyn Tool>);
    pub fn add_command(&mut self, name: &str, handler: CommandHandler);
    pub fn append_system_prompt(&mut self, text: String);
    pub fn contribute_skill(&mut self, path: PathBuf);
    pub fn on_event(&mut self, listener: EventListener);
    pub fn disposable(&mut self, fn_: DisposeFn);
    pub fn cwd(&self) -> &Path;
}

Mirrors the Chapter 8 host API directly. Each register() gets a fresh context whose contributions can be cleanly torn down at shutdown.

Where agent-rig fits, and what it does not provide

agent-rig handles
  • The streaming agent loop (AgentRunner)
  • Provider connections (Gemini, Ollama)
  • Concurrent tool execution + result ordering
  • Auth hook for tool calls (AuthManager)
  • Structured output (JSON Schema constraint)
  • Agent composition (sub-agents as tools)
arnes-core adds
  • System prompt assembly from slots
  • Persistence (JSONL session logs)
  • Compaction
  • Built-in coding tools (read, write, edit, bash) in arnes-core::tools
  • Extensions and skills
  • The Host abstraction for tool I/O
  • The Frontend abstraction for multi-UI

We treat agent-rig as a stable dependency: pin a version, don't patch upstream from inside arnes. If agent-rig is missing something we need (e.g. an event we want to observe), we contribute it back rather than forking.

arnes-core non-goals

  • No UI code. If it touches a terminal escape sequence, a window, or a websocket frame, it belongs in an adapter crate.
  • Coding tools are first-class, not a non-goal. Because arnes-core is specifically a coding-harness library (the general-agent layer is agent-rig below us), the built-in coding tools live here as arnes-core::tools. Custom tools an embedder writes implement the same trait and register through ToolRegistry; the built-ins are not privileged.
  • No CLI parsing. Each binary (arnes, arnes-acp, arnes-serve) handles its own flags. Shared options can live in arnes-core::cli as a reusable CommonOpts clap struct.
  • No HTTP / JSON-RPC. Both live in their respective adapter crates.

The acid test

You should be able to write a fn test_agent_loop() in arnes-core/tests/ that constructs a Session with a mock Frontend, a mock Host, a mock LLM, and verify a complete round-trip without compiling a single line from any adapter crate. If a refactor breaks that, we have leaked the wrong abstraction.
