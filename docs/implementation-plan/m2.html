Milestone 2 · First tool

read

Wire tool-calling end-to-end with a single, simple tool. By the end the model can call read; the TUI shows a tool-call card; the ACP client receives a tool_call update and an outbound fs/read_text_file request. Same agent, two completely different filesystem implementations.

Why one tool, in isolation

M2 is a vertical slice. It touches every part of the system — Tool trait, ToolRegistry, agent-rig wiring, SessionEvent additions, the two Host impls, the two frontends — but at minimum width. Get the loop working with one tool and adding more (M3) is mechanical.

New module: arnes-core::tools

crates/arnes-core/src/tools/
├── mod.rs        # Tool trait, ToolRegistry, register_defaults() helper
└── read.rs       # the read tool

Built-in tools live next to the Tool trait inside arnes-core. They take &dyn Host — they do not know whether they run against LocalHost or AcpHost. New dependencies in arnes-core/Cargo.toml: schemars (for JSON Schema generation) and serde (already there).

Tool trait, M2 version

Move the Tool trait from "sketched" to "implemented". M2 sticks to the essentials; M3 adds the permission API (scope-based allowlists) and progress streaming. 

// arnes-core/src/tools.rs

pub trait Tool: Send + Sync {
    fn name(&self) -> &str;
    fn description(&self) -> &str;
    fn parameters(&self) -> serde_json::Value;  // a JSON Schema

    async fn execute(
        &self,
        input: serde_json::Value,
        host: &dyn Host,
    ) -> ToolResult;
}

pub struct ToolResult {
    pub content: String,        // M2: text only. M3 adds typed blocks.
    pub is_error: bool,
}

#[derive(Default)]
pub struct ToolRegistry {
    tools: Vec<Arc<dyn Tool>>,
}

impl ToolRegistry {
    pub fn register(&mut self, tool: Arc<dyn Tool>);
    pub fn get(&self, name: &str) -> Option<&Arc<dyn Tool>>;
    pub fn all(&self) -> &[Arc<dyn Tool>];
}

The read tool

// arnes-core/src/tools/read.rs

#[derive(serde::Deserialize, schemars::JsonSchema)]
struct ReadInput {
    /// Absolute or relative path to the file to read.
    path: String,
    /// 1-based starting line (inclusive). Optional.
    #[serde(default)]
    line: Option<u32>,
    /// Max lines to return. Optional; default unlimited.
    #[serde(default)]
    limit: Option<u32>,
}

pub struct ReadTool;

#[async_trait]
impl Tool for ReadTool {
    fn name(&self) -> &str { "read" }
    fn description(&self) -> &str {
        "Read the contents of a UTF-8 text file. Use for source files, configs, \
         and logs. Optionally narrow by line/limit. Output is truncated to 1000 \
         lines or 200KB, whichever hits first."
    }
    fn parameters(&self) -> serde_json::Value {
        serde_json::to_value(schemars::schema_for!(ReadInput)).unwrap()
    }

    async fn execute(&self, input: serde_json::Value, host: &dyn Host) -> ToolResult {
        let input: ReadInput = match serde_json::from_value(input) {
            Ok(v) => v,
            Err(e) => return ToolResult::error(format!("invalid arguments: {e}")),
        };
        match host.read_text_file(Path::new(&input.path)).await {
            Ok(text) => ToolResult::ok(truncate(text, input.line, input.limit)),
            Err(e) => ToolResult::error(format!("read failed: {e}")),
        }
    }
}

Host implementations, fleshed out

LocalHost
impl Host for LocalHost {
    async fn read_text_file(&self, p: &Path) -> io::Result<String> {
        tokio::fs::read_to_string(p).await
    }
}
AcpHost
impl Host for AcpHost {
    async fn read_text_file(&self, p: &Path) -> io::Result<String> {
        let req = FsReadTextFileRequest {
            path: p.to_path_buf(),
            line: None, limit: None,
        };
        let resp: FsReadTextFileResponse =
            self.rpc.call("fs/read_text_file", req).await?;
        Ok(resp.content)
    }
}

Note: AcpHost's outbound calls flow through the same bidirectional JSON-RPC channel the M1 server uses for inbound requests. This is precisely why the M1 library spike mattered.

Wiring tools to agent-rig

agent-rig already supports concurrent tool execution and tool-result pairing — we lean on it. Each arnes::Tool wraps as an agent_rig::Tool by:

  1. Implementing agent-rig's tool trait via an adapter struct that owns an Arc<dyn arnes::Tool> plus an Arc<dyn Host>.
  2. Translating agent-rig's tool-call lifecycle events into our SessionEvent variants.
  3. Forwarding ToolResult back to agent-rig as the tool message body.
struct ToolAdapter {
    inner: Arc<dyn arnes::Tool>,
    host:   Arc<dyn arnes::Host>,
}

#[async_trait]
impl agent_rig::Tool for ToolAdapter {
    fn name(&self) -> &str { self.inner.name() }
    fn description(&self) -> &str { self.inner.description() }
    fn parameters(&self) -> serde_json::Value { self.inner.parameters() }

    async fn execute(&self, input: serde_json::Value) -> agent_rig::ToolResult {
        let r = self.inner.execute(input, self.host.as_ref()).await;
        translate(r)
    }
}

What the frontends do

TUI at M2
  • Introduce a ToolCallCard widget — one row per active tool call.
  • States rendered: pending → running → done / error.
  • Card shows tool name and a one-line preview of the input (e.g. read src/main.rs).
  • On error, expand to show the error text inline.
ACP at M2
  • Emit session/update variants: tool_call (pending), tool_call_update (running/completed/failed).
  • Map fields per the ACP schema; carry tool-id, name, input, status, result.
  • AcpHost::read_text_file issues outbound fs/read_text_file when the read tool fires.
  • Capability check: if the client didn't advertise fs.readTextFile, the host returns Unsupported and the tool surfaces a clean error.

Implementation tasks

  1. Create the arnes-core::tools module; add schemars to arnes-core/Cargo.toml.
  2. In arnes-core::tools, define Tool, ToolResult, ToolRegistry.
  3. Extend SessionEvent with the three tool-call variants.
  4. Update Session::prompt: configure AgentRunner with the registered tools (wrapped via ToolAdapter); translate agent-rig's tool-call events into SessionEvents.
  5. Implement LocalHost::read_text_file (one line).
  6. Implement AcpHost::read_text_file using the bidirectional JSON-RPC client.
  7. Write the read tool in arnes-core::tools.
  8. Register read by default in both binaries (arnes and arnes-acp) via the arnes_core::tools::register_defaults(&mut registry) helper.
  9. In arnes-tui: add ToolCallCard widget; wire to event stream.
  10. In arnes-acp: emit tool_call session/update variants; wire AcpHost into Session construction.
  11. Land the testing-infra workstream (see below).

Testing infrastructure (lands now)

M2 is the first milestone with multiple moving parts; build the test scaffolding here once, reuse for every subsequent milestone.

PieceCratePurpose
RecordingFrontend arnes-core/tests/support/ Captures every SessionEvent; assert on the sequence.
InMemoryEnv same Fake filesystem: HashMap<PathBuf, String>. Will grow with M3.
Scripted LLM arnes-core/tests/support/scripted_llm.rs Implements agent-rig's LlmModel; returns canned tool-call + text sequences. Deterministic loop testing.

Testing checklist

  • Unit: read tool against InMemoryEnv — happy path, missing file, permission denied (synthetic).
  • Loop: Scripted LLM that emits a read tool_use, harness executes it via InMemoryEnv, verify the second turn receives the tool_result and emits a final text reply.
  • ACP golden: Replay a transcript where the client serves fs/read_text_file; assert the harness issues the right outbound request with the right path and produces the right outbound session/updates.
  • TUI smoke: Manual. "what's in Cargo.toml?" — card appears, transitions, completes.

Risks specific to M2

  • JSON Schema generation. schemars output for nested types may not match what the model providers expect. Verify with each model used; tweak via #[schemars(...)] attributes.
  • Streaming tool input. agent-rig may surface tool_use input as a stream of partial JSON. M2 can accumulate and parse at end; M3 may want true streaming for long inputs.
  • Path resolution. Relative paths in tool calls must resolve against the session's cwd, not the harness's working directory. Pin this in Session::cwd from M2 on.

End state of M2

Ask either frontend "what is in my Cargo.toml?": the model calls read; the TUI shows a card; the ACP client receives a tool_call update and a corresponding fs/read_text_file request. Two completely different filesystem implementations behind one tool, with the harness aware of neither.
